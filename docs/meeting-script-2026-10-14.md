### 1-5　7 個 pattern 的全貌 ── 第 5 頁，上方到中間

📍 **指**圖 2：先指左邊「背景：三個證據來源」，再沿上排 ①→④、下排 ⑤→⑦ 移動。然後**圈**表 4，一列一列往下指。

📖 7 個 pattern 分兩組。上排「建圖」處理怎麼拼出可信的圖；下排「交付」處理把圖變成數字和報告時怎麼不走樣。箭頭上的字是前一個 pattern 留下、由下一個接手的問題，這種一個引出下一個的關係，就是 pattern language 和一般 pattern 清單的差別。每個 pattern 的內容：

| # | 名稱 | 解決的問題 | 做法（用商店舉例） |
|---|---|---|---|
| ① | 以流量走遍路徑 | 執行期只看得到被走過的路 | 主動送流量；靜態看到 orders → payment 但執行期 0 次，就在下一輪加一筆結帳 |
| ② | 混合重建 | 每個來源都不完整 | 把各來源的邊以「來源 → 目標」為鍵合成一張圖，每條邊記住它從哪個來源來 |
| ③ | 實測優先於推測 | 合起來之後所有邊長得一樣 | 量測到的畫實線、推測的畫虛線；一條邊被量測到就取代推測的版本 |
| ④ | 請人確認名稱對應 | 名稱對不上時，丟掉或亂猜都會錯 | 列出候選問熟悉系統的人（basket-service 是不是 cart），答案存起來下次不再問 |
| ⑤ | 一份目錄、多個視圖 | 圖、數字、報告各自推導，互相矛盾 | 先建一個統一模型，所有產出物都從它產生 |
| ⑥ | 先算事實，再讓 AI 解釋 | LLM 重述事實會漏、會加、會換詞 | 事實由程式產生，LLM 只寫詮釋和建議 |
| ⑦ | 無資料不等於零 | 沒收集的資料被當成 0 | 沒量測就寫「未量測」，不要寫 0% |

💬
> 這張圖是 7 個 pattern 的全貌，分兩組。上排四個是「建圖」：怎麼把來源拼成一張可信的圖。下排三個是「交付」：把圖變成數字和報告時怎麼不走樣。箭頭上的字是前一個 pattern 解決之後留下的問題，由下一個接手，所以它是一套 language，不只是一份清單。
>
> 下面表 4 是每個 pattern 的一句話。我簡單講一下：
> - ① 執行期只看得到被走過的路，所以要主動送流量，而且用「靜態有、執行期還沒量到」的邊決定下一輪送什麼。
> - ② 每個來源都不完整，所以合成一張圖，每條邊記住它從哪個來源來。
> - ③ 合起來之後要讓讀者分得出哪條是量到的、哪條是推測的。
> - ④ 名稱對不上時，不要丟掉也不要亂猜，問熟悉系統的人。
> - ⑤ 圖、數字、報告都從同一個模型產生，就不會互相矛盾。
> - ⑥ 報告的事實由程式寫，LLM 只負責解釋。
> - ⑦ 沒量測就說沒量測，不要寫成 0。

### 1-6　完整講一個 pattern：③ 實測優先於推測 ── 第 8 頁中間 → 第 9 頁中間

這段放慢講，讓老師看到一個 pattern 的完整寫法。選這個是因為它的業界例子最直接。

1. 📍 **第 8 頁，中間偏上**：**指**標題「5.3 實測優先於推測（Observed over Inferred）」和下面的「別名」。
   📖 英文名稱沿用業界說法。AWS X-Ray 叫 inferred segment，Datadog 叫 inferred services，Grafana Tempo 叫 virtual nodes。別名欄就是在說明不同工具怎麼稱呼同一件事，證明它是通用做法。
   💬 「英文名稱直接用業界的叫法，別名這一欄列出 AWS、Datadog、Grafana 各自怎麼叫它，代表大家都在做同一件事。」

2. 📍 **第 8 頁，中間**：**劃**「Context。你已經合併出一張多來源的圖……」。
   📖 Context 交代讀者現在在哪一步：上一個 pattern ② 已經把來源合成一張圖，每條邊都有出處；讀者會拿這張圖做決策，但通常不會回頭查出處。
   💬 「Context 說明讀者現在的處境：已經用上一個 pattern 把來源合成一張圖了，但讀者只看圖、不會回頭查每條邊的出處。」

3. 📍 **第 8 頁，中間**：**圈** Problem 底下的粗體引文。
   📖 兩難：全部畫一樣，讀者會以為每條都一樣真；只畫量測到的，又會丟掉量測不到但確實存在的相依關係（例如只在月底才跑的流程）。
   💬 「Problem 是一個兩難：全部畫成一樣，讀者會以為每條都是真的；只畫量測到的，又會漏掉量測不到但真的存在的相依關係。」

4. 📍 **第 8 頁，中間偏下**：**指** Forces 的五個粗體名稱。
   📖 Forces 是互相拉扯、讓這個問題不好解的力量：可靠度和完整度此消彼長；讀者要一眼看懂，分太多級看不懂；同一條邊會被多個來源提到；視覺通道（線型、顏色、粗細）有限；標出「推測」可能讓讀者覺得整張圖不可靠。
   💬 「Forces 是讓這個問題不好解的幾個因素，例如可靠度和完整度此消彼長、圖上能用的線型顏色有限、標出『推測』可能反而讓讀者不信任整張圖。這一欄是 pattern 論文審稿最在意的地方。」

5. 📍 **第 8 頁，下方**：**劃**「Solution。因此：」底下第 1 條和第 3 條，再**指**最後的「例如」那一句。
   📖 解法：每條邊帶「實測」或「推測」標記，畫成實線和虛線；同一條邊一旦被量測到，就取代推測的版本。商店的例子：orders → payment 原本是虛線，下一輪流量量測到之後變實線。
   💬 「解法是每條邊帶一個標記，量測到的畫實線、推測的畫虛線；同一條邊一旦被量測到，就改成實線。像商店例子裡的 orders → payment，送了一筆結帳之後就從虛線變實線。」

6. 📍 **第 9 頁，上方**：**指**「Resulting Context」和「Consequences」。
   📖 Resulting Context 說明套用之後留下什麼新問題：有些名稱根本對不上（basket-service 是不是 cart），標記也幫不上忙，所以接到下一個 pattern ④。Consequences 寫好處和代價，例如讀者要學會看圖例。
   💬 「Resulting Context 說明解決之後還剩什麼問題，這裡剩下的是名稱對不上，就接到下一個 pattern。Consequences 是好處和代價，兩邊都要寫。」

7. 📍 **第 9 頁，中間**：**圈**表 7「實測優先於推測：Known Uses」，依序**劃**：
   - AWS X-Ray 那一列。
     📖 X-Ray 會用下游呼叫推測出一個 inferred segment；等那個服務自己送出追蹤資料，就用真的資料取代推測的區段。這就是「量測到的取代推測的」。
   - AWS CloudWatch Application Map 那一列。
     📖 沒有被量測的服務畫成虛線框或不同顏色，就是「推測的畫成不同樣子」。
   - **指** DepWeaver 那一列。
     📖 DepWeaver 多分一級：量測到畫實線、有使用證據畫虛線、僅推測畫點線。這是我們自己的變化，細節寫在 COMPSAC。
   💬
   > Known Uses 分成論文、業界、我們的工具三類。業界這兩列最直接：AWS X-Ray 的官方文件寫，服務自己送出資料之後，會取代原本推測出來的區段；CloudWatch 則把沒有被量測的服務畫成虛線框。DepWeaver 只是這 5 列裡的 1 列，我們多分了一級，細節放在 COMPSAC。

## 2. COMPSAC（右邊，約 13 分鐘）

### 2-1　問題與貢獻 ── 第 1 頁右欄上方到下方

📍 **劃**「A. 動機」底下列出的三個問題（1）等級被抹平、2）產出物互相矛盾、3）有些缺口只有人知道答案）。再**指**「B. 方法概要與貢獻」的 1)～4)。

📖 COMPSAC 這篇的主角是 DepWeaver。它要解決多來源融合之後的三個問題：
- **等級被抹平**：文件提一句的關係和量測到幾千次的關係畫得一樣。
- **產出物互相矛盾**：圖、覆蓋率、報告各說各話，例如報告把資料庫邊寫成「執行期是否觀測：未知」，圖卻畫實線。
- **有些缺口只有人知道**：例如部署的密碼、某個名稱指哪個服務。

四個貢獻剛好對應：三級信心等級的融合模型、彼此一致的產出物、最後才詢問操作者的缺口補齊、在 14 個開源系統上的評估。

💬
> COMPSAC 這篇在講 DepWeaver 自己怎麼做。動機這段列出把多個來源合起來之後會遇到的三個問題：第一，可信度不同的邊畫得一樣；第二，圖、覆蓋率、報告互相矛盾；第三，有些缺口只有人知道答案。
>
> 下面四個貢獻就是分別解決這三個問題，再加上評估：三級信心等級、讓所有產出物從同一個模型產生、自動手段用完才問人，以及在 14 個開源系統上的實驗。

- RQ3：詢問操作者能補回多少。

### 2-3　方法流程 ── 第 3 頁，左欄上方

📍 **圈**圖 1，照著圖由上往下**指**。

📖 流程分四段：
- **① 收集三個來源**：靜態分析（tree-sitter 解析程式碼，加上設定檔和部署描述檔）、DeepWiki 文件、叢集資訊。
- **② 產生流量、查量測指標**：從 Istio 查請求數和 TCP 連線數。
- **檢查點**：覆蓋不夠就針對缺口再送一輪流量；需要只有人知道的值時，暫停並在 Discord 問操作者（③）。
- **④ 融合**：使用者按 Generate report 之後，才融合成統一模型，再產生分層相依圖、覆蓋率、報告和事後問答。

沒有叢集時也能跑，但只會產出靜態草圖，所有執行期欄位都標「未量測」。

💬
> 這是 DepWeaver 的流程。第一步收集三個來源：程式碼和部署描述檔、DeepWiki 的文件、叢集的資訊。第二步產生流量，從 Istio 查到底有哪些呼叫真的發生。中間有一個檢查點：覆蓋不夠就針對缺口再送一輪；需要密碼這種只有人知道的值，就暫停在 Discord 問操作者。最後按 Generate report，才融合成一個統一模型，圖、覆蓋率、報告都從這個模型產生。

### 2-4　三級信心等級 ── 第 3 頁，右欄上方到中間

📍 **圈**表 I「三級信心等級」；**指**圖 2 三種線型。

📖 每條邊有一個信心等級，由低到高：
- **僅推測**（點線）：只有文件提到、只有連線設定，或是從變數名推出來的。
- **有使用證據**（虛線）：程式碼裡真的有發出呼叫的地方，例如某一行 Feign client。
- **量測到**（實線）：執行期真的記錄到這條呼叫，例如 petclinic 裡 ingress 到 api-gateway 共 95 次。

合併規則（演算法 1）很簡單：同一條邊被多個來源提到時，等級取最高、出處全部保留。我們選三個離散等級而不是 0 到 1 的分數，是因為不用調參數，也能直接對應三種線型。

💬
> 這張表是我們的三級信心等級。最低是「僅推測」，例如只有文件提到；中間是「有使用證據」，程式碼裡真的有呼叫；最高是「量測到」，執行期真的看到這條呼叫。圖上分別畫點線、虛線、實線。同一條邊被好幾個來源提到時，等級取最高、出處全部留著。我們沒有用 0 到 1 的分數，因為不用調參數，而且剛好對應三種線型。

### 2-5　讓產出物一致與「未量測」（可略）── 第 4 頁，右欄上方到中間

📍 **指**「E. 讓產出物彼此一致」底下的四個粗體小標，再**指**演算法 2。

📖 四條設計規則：
1. **一個模型、多個視圖**：圖、覆蓋率、報告、問答都從同一個模型產生。
2. **事實段落由程式產生**：報告裡列出相依關係的兩節由程式寫，再插進 LLM 寫的報告；其餘章節（收集狀態、元件、未解項目等）才由 LLM 寫。
3. **只計可量測關係的覆蓋率分母**：沒部署的、控制平面的、行程內快取這種量不到的不算分母；只有僅推測的邊也不算，但會把數量寫在旁邊（演算法 2）。
4. **未量測不是零**：沒連叢集就寫「not measured」，不寫 0%。

💬
> 這一節是讓圖、覆蓋率、報告不會互相矛盾的四條規則：所有東西從同一個模型產生；報告裡的事實由程式寫；覆蓋率的分母只算量得到的關係；沒量測就寫「未量測」，不寫 0%。AsianPLoP 那篇裡「覆蓋率分母」沒有收進 pattern，就是放在這裡。

## 3. 兩篇的差別（1 分鐘）── 兩邊並排，不用動

💬
> 兩篇的分工是：AsianPLoP 不放任何實驗數字，DepWeaver 在每個 pattern 裡只是 Known Uses 的一列；COMPSAC 才放我們自己的方法和實驗。兩篇的主張和證據都不一樣，所以應該不會被當成一稿多投。兩篇的用詞我也統一過，例如都用「架構重建」「統一模型」，三個等級都叫「僅推測、有使用證據、量測到」。
