## P2 · 一條邊 A → B 成立，要回答四個問題

📍 先指右下「為什麼說 11 條錯邊都是沒統一」，再回到上排四張卡 ①②③④，最後左下外部依據。

💬
> 先講為什麼不再加規則。上次說請 AI 網羅案例找規則，我做了：100 個公開 repo，探勘加 LLM 審查，補到第 61 條。然後審查確定錯的 11 條錯邊逐條看——沒有一條是缺規則，全部是同一個判斷只在某幾種檔案格式做了。
>
> 7 條是這樣：「整包 ConfigMap 塞給一堆服務的位址，不能算每個服務都有用」這條判斷，只套在 Kubernetes 的服務類目標；資料庫的位址照畫，Compose 的 env_file 完全沒套。結果連 postgres 容器都有線連出去——資料庫自己去連別的服務。另外 4 條：「程式碼裡的 URL 字串要在呼叫的地方才算」只套了 JS、Go、PHP；Java 和 C# 是抓任何地方的 http 字串再一條一條排除，排除清單漏了 RFC 文件的連結、錯誤回應裡的型別網址、API 說明頁上的授權條款連結——這些是給人在瀏覽器點的，服務從來不會連過去。
>
> 所以問題不是規則不夠，是同一件事寫了好幾份、各寫各的。我把 61 條逐條問「它在回答什麼問題」，歸出來只有四個，每個問題各寫成一份實作、所有檔案格式共用。統一之後這 11 條全部消失，AICS 畫對的比例從 0.90 到 0.97，100 個語料系統拿掉 137 條線，查證過約 121 條本來就是錯的。
>
> 四個問題是這樣。
>
> ① 名字表：部署檔宣告了哪些名字？Compose 的服務名、Kubernetes 的 Service 名、別名。一個位址出現，先查它是不是這些名字之一。順序固定：先排除保留網域——`.test`、`.example`、`example.com`、`.local` 這些是網路規格保留給寫範例、測試用的，保證不會有真的機器叫這個名字，repo 裡看到 `api.example.com` 就是範例值，不畫、也不問人；別名換回本名；localhost 是自己；有點的網域是外面的服務；最後才對宣告過的名字，都不是才准新開一個節點。
>
> ② 位址形狀：什麼值算位址？看 scheme，看鍵名最後一個字是不是 host、url、addresses，看是不是連線字串、是不是 host 加 port。一個反例：URL 是 `http://主機/路徑`，兩條斜線後面才是主機；E 的 jaeger 設定寫 `http:${PROMETHEUS_ADDR}`，沒有斜線，依規格這種寫法整段都不是主機。舊的解析看到冒號就把前面的 http 當主機名，畫了 jaeger 連到一個叫「http」的服務。
>
> ③ 歸屬：這個值是送到誰手上的？寫在服務自己 env 區塊的，是它的。整包注入的——envFrom 把整個 ConfigMap 塞給十個服務、Compose 的 env_file——沒有替誰選，要服務的程式碼或設定裡真的讀了那個鍵，才算它的。
>
> ④ 使用：程式有沒有在呼叫的地方用它？一個 URL 字串只在呼叫那一行附近、或透過變數名追到呼叫那一行，才算。沒人引用的常數、死掉的函式裡的 URL、剛才那種給人點的連結，都不是。
>
> 程式碼處理一列資料時是倒著問的：先④有沒有用，沒用就丟掉；再③是誰的；再②是不是位址；最後①查名字表。
>
> 61 條規則分下去：名字表 18 條、形狀 9 條、歸屬 15 條、使用 13 條，剩 6 條只是「讀得懂某種檔案」，像 Helm 要先渲染、一個 YAML 裡有好幾份文件。
>
> 每個慣例都有外面的依據：名字表是 Compose 網路和 Kubernetes DNS 的文件；形狀是 URI 的 RFC 和連線字串的格式；歸屬是 Compose 和 Kubernetes 怎麼注入環境變數、Spring 和 ASP.NET 怎麼綁定設定的文件。只有④是我們自己的方法。

🛡 **「這四個是怎麼歸出來的？」** → 把 61 條逐條問「它改變結果的那一步在回答哪個問題」，一條只歸一個；表在 conventions.md。
🛡 **「6 條格式轉接器算不算特例？」** → 它們不判斷相依，只是讓某種檔案讀得進來；少了它那種檔案是空白，不會畫錯。

## P3 · Compose 的 depends_on 是「先啟動」，不是「我呼叫你」

📍 左表三列，右邊效果，右下兩條順手補的。

💬
> 歸屬慣例的一個具體案例。先交代用到的東西：線本來就分兩個等級，documented 是設定檔和程式碼兩邊都說了，inferred 是只有一邊說了、畫虛線，這是之前就有的。這次新加的是**第三種關係，叫「啟動順序」**：它不是呼叫，另外列、不計分，覆蓋率也不算。為什麼要加——
>
> Compose 檔的 depends_on 意思是「它先起來我再起來」，不是「我會連它」。舊做法是來源沒寫位址就把 depends_on 畫成呼叫：61 條對、9 條錯，錯的 8 條全在 skywalking-showcase——node-exporter 寫了 depends_on oap，意思只是等 oap 起來，從頭到尾沒連過 oap。這種「先起來」的關係以前要嘛畫成呼叫（錯），要嘛丟掉（部署順序的資訊就沒了），所以給它自己的一類。
>
> 現在 depends_on 分三種結局。
>
> 第一種：來源自己的 env 也寫了同一個目標的位址，兩個地方說的一樣，畫呼叫、documented。robot-shop 的 web 連 cart：env 裡有 CART_HOST=cart，depends_on 也有 cart。
>
> 第二種：這個容器跑的是我們 repo 自己的程式碼（Compose 寫了 build:，或 repo 裡有個目錄就是它的程式碼），而且它的 env、設定檔、程式碼裡都沒寫任何位址。這時 depends_on 是作者唯一一處說「我需要它」的地方，畫呼叫、但只有一邊說所以 inferred。hotelReservation 的 search 連 geo 就是這樣：search 的程式碼從根目錄一個 config.json 讀 geo 的位址，但那個檔案不在任何服務的目錄下，程式碼層歸不到 search，search 連 geo 只剩 depends_on 這一處證據。
>
> 第三種：來源是第三方映像（它的接線在映像裡，repo 讀不到），或者來源的位址明明指的是別人、就是沒指它——只留啟動順序。node-exporter 等 oap 就是這種。
>
> 先試過更乾淨的版本，depends_on 一律不當呼叫：hotelReservation 掉 22 條真線、robot-shop 掉 5 條、第三方資料集掉 6 條。這些線的程式碼證據都在沒人擁有的共用設定檔，depends_on 一直在替那個缺口撐著。所以第二種留下來，而且把它寫成「作者對自己容器的陳述」，不是「沒位址就畫」。
>
> 效果：hold-out D 的 skywalking 畫對的比例 0.44 到 0.73，錯邊 10 條到 3 條；整組 P 從 0.71 到 0.87。
>
> 順手補的：`http:${PROMETHEUS_ADDR}` 沒有斜線是 opaque URI，E 原本多畫 jaeger 連到一個叫 http 的節點；Python 的 smtplib 進呼叫詞彙，AICS 的 mail-service 連 smtp.gmail.com 補上了。

🛡 **「第二種不也是猜？」** → 是，所以畫 inferred，而且條件是「自家程式碼的容器」；第三方映像一律不猜。

## P4 · 「只畫對的、不畫錯的」要先讓④追得到：補三個綁定轉接器

📍 上方一句話，三張卡，底下結果。

💬
> 上次問「沒辦法只畫對的不畫錯的嗎」。想做的事是：程式碼讀得到的容器，env 區塊裡的服務位址交給程式碼層畫，描述檔不畫。目標是 yas 的 storefront——Compose 把十個服務的位址塞給它，程式碼一個都沒用，描述檔卻畫了十條。
>
> 第一次開，yas 的錯邊消失，但掉了 27 條真線：yas 16 條、TeaStore 5 條、otel-demo 4 條。程式碼確實有用這些位址，只是④追不到。逐條看是三種寫法。
>
> 第一種，Spring 的三段式綁定。環境變數 YAS_SERVICES_PRODUCT，依 Spring 的寬鬆綁定等於屬性 yas.services.product；`@ConfigurationProperties(prefix="yas.services")` 把它綁到 ServiceUrlConfig 這個 record 的 product 欄位；呼叫那一行寫 `fromUriString(serviceUrlConfig.product())`。現在這三段都接起來，而且要求存取子出現在呼叫點那幾行。所以 cart 連 product 畫——它的 product() 進了呼叫；storefront 不畫——它綁了整包但沒人呼叫。
>
> 第二種，映像的命令列。Online Boutique 和 Bank of Anthos 的 loadgenerator 位址寫在 Dockerfile 的 ENTRYPOINT：`locust --host=http://${FRONTEND_ADDR}`。現在 ENTRYPOINT、CMD 和同目錄的 .sh 裡的 URL 當程式碼層的列，佔位符用那個容器的 env 填。
>
> 第三種，FROM 鏈。TeaStore 五個服務的 Dockerfile 都 FROM 同一個基底映像，基底目錄的 start.sh 把 `http://${REGISTRY_HOST}:${REGISTRY_PORT}` 寫進 Tomcat 設定。現在基底目錄的腳本會分派給每個建在它上面、而且有部署的服務，各自用自己的 REGISTRY_HOST 解成 teastore-registry。all-in-one 映像也建在基底上，但沒有 manifest 跑它，不繼承。
>
> 三個都是「值從哪裡來」的新路徑，不是新規則。做完再把那條延伸打開：hold-out C 從 0.87／0.97 到 0.98／0.98，yas 錯邊 13 條剩 2 條，其他組沒掉。

🛡 **「為什麼不做 JNDI？」** → TeaStore 的 web.xml 只有 localhost:8080 預設值，五個服務都在 8080，解不出來；真正的位址在 start.sh，FROM 鏈已經拿到。
🛡 **「其他語言不用補？」** → 掉的 27 條逐條看，就這三種寫法；Go、Python、.NET 的位址都在 env 或呼叫點，原本就追得到。

## P6 · 程式碼照四個慣例重整

📍 左白卡「之前」、右漸層卡「現在」的目錄樹；左下怎麼保證、右下 bug。

💬
> 上次問「現在都是慣例、沒有特例嗎」。我答判斷邏輯是四個慣例，但程式碼的切法還是照檔案格式、照資料的種類切：合併器三千行，一個方法五百行建索引、一個方法五百行合併，用二十幾個分支分；設定檔讀取器兩千行，九種格式在一個類別裡，還夾著判斷；二十份字詞表散在六個類別。四個慣例只存在於文件。
>
> 這次把程式碼切成跟文件一樣。Conventions 目錄放四個慣例的判斷和集中起來的字詞表；CodeExtraction 只剩格式轉接器——tree-sitter 讀程式碼、四個讀取器讀 Compose、Kubernetes、Docker、應用設定檔，它們只把檔案讀成一列一列，不判斷；Graph 裡 DeployedNames 是這個部署的名字表、Ownership 是「誰的值」，合併器從三千行剩一千四，每一列照④③②①的順序問，派給 14 個處理器。RuleTrace 的 61 條也按慣例分組。
>
> 怎麼保證沒改到行為：每一步都跑 23 個系統加 AICS 逐邊比對，same 23、different 0，一條邊都沒變；全套 361 個測試。搬法是用腳本逐行搬、搬之前檢查錨點，搬完讓編譯器指出每個跨類別的引用。
>
> 路上抓到一個真的 bug。Java 的 Set.of 迭代順序每次 JVM 啟動都不一樣。叢集 DNS 字尾清單有三項，.svc.cluster.local 必須先試，一旦順序變成 .cluster.local 先，web.robot-shop.svc.cluster.local 就被剝成「web.robot-shop」，istio-ingressgateway 連 web 這條線就不見了。單跑一次抓不到，第二步回歸過了，第三步才炸。已經改成保留宣告順序，加測試守著。

🛡 **「重整的價值是什麼？」** → 論文的方法節可以直接對到程式碼：每個慣例一個類別，字詞表一個檔；審查者問「這條判斷在哪」答得出來。
🛡 **「一千四百行還是大」** → 剩下的是流程和畫邊，判斷都搬出去了；再拆沒有新的邊界。

> 慣例之下還有兩層東西，要老實列。
>
> 第一層，29 份字詞表、306 個詞。例如哪些 scheme 代表資料庫（jdbc、mongodb、redis，17 個），鍵名最後一個字是 host 就是主機（host、addr、server-addr，8 個），哪些字代表「誰能連我」而不是「我連誰」（CORS origins、OAuth redirect，18 個），哪些呼叫會發出連線（RestTemplate、HttpClient、requests，45 個），哪些目錄名不是服務（src、cmd、node_modules，35 個）。這些不是從慣例推出來的，是各生態系的拼法。每份寫清楚三件事：原則、來源生態系、新增一個詞的條件——條件一律是「某生態系的文件這樣拼」，不是「某個受測系統需要」。清單由程式碼產生，測試保證文件跟程式碼一致。
>
> 第二層，五條靠資料決定的子句，審查者可以指著說是特例：depends_on 的自家容器條款，純慣例會掉 hotelReservation 22 條；links 和 depends_on 不同待遇，有 Compose v1 的文件；程式碼產生工具有 main 就算服務，mall-mbg 那條錯邊就是它留的；FROM 鏈只給有部署的子映像，TeaStore 的 all-in-one 逼出來的；server.port 贏過 Compose 發佈的 port，Tap-And-Eat 逼出來的。每一條我都寫成「這一類寫法怎麼看」，程式碼裡沒有任何系統的名字，但「為什麼存在」的答案都是某個系統。
>
> 我的想法是論文直接把這兩層列成表，不說「沒有特例」。

🛡 **「字詞表會不會一直長？」** → 會，但長的是詞不是判斷；每加一個詞要有生態系文件的出處，PR 看得出來。

## P8 · 還會漏、還會錯的，寫成界線

📍 左欄「刻意不補」四項，右欄「還能做、但這次沒動」四項。

💬
> 左邊四項是我判斷不該補的，每一項講它是什麼、為什麼工具沒有依據畫。
>
> 第一項，套件自己讀環境變數。otel-demo 的 load-generator 是用 locust 寫的壓測程式，Compose 給它 `LOCUST_HOST=http://frontend-proxy:8080`，但 repo 裡沒有任何一行程式碼讀 LOCUST_HOST，是 locust 這個套件自己去讀的。fraud-detection 也一樣，用 OpenFeature 的 flagd provider，provider 自己讀 FLAGD_HOST。所以這兩條線在 repo 裡找不到「讀取」，歸屬慣例判定值沒有送到程式碼手上。要補，得維護一份表：「哪個套件會讀哪個環境變數」，每多一個套件加一列。我們對資料庫和訊息中介其實已經有這種表——Spring 的 SPRING_DATASOURCE_URL、.NET 的 ConnectionStrings__X，因為那是框架文件寫明的、整個生態系共用的綁定。locust 和 flagd 是單一套件自己的變數名，語料一百個系統只碰到這兩例，為兩例開一份會無限長的表不划算，所以寫成界線。哪天案例多了，做法跟 db／broker 那份表一樣，有文件出處就能加。
>
> 第二項，第三方映像裡的接線。例子是一個系統用現成的 nacos 映像當註冊中心，用一個共用的 env_file 把 MYSQL_SERVICE_HOST 給所有容器，nacos 映像裡的程式會讀這個變數去連 mysql。但那段程式在映像裡，repo 裡看不到。整包注入的規則是「讀了才算」，nacos 在 repo 裡讀不到，所以不畫。如果改成「第三方映像收到什麼就算什麼」，就會回到審查抓到的那 7 條錯邊——postgres 容器也收到整包，它也會被畫成連別人。只留啟動順序是對的。
>
> 第三項，叢集外。AICS 漏的 9 條線，目標是外部 SaaS 或在瀏覽器端發生的呼叫：位址不在 repo 裡當成 URL 出現——要嘛在 SDK 裡面，SDK 自己知道要連哪個端點，程式碼只呼叫 SDK 的函式；要嘛是瀏覽器端的程式在使用者的瀏覽器裡發出去的，不是服務發的。靜態層的原則是只主張 repo 裡寫明的，這種留給執行期那一層：真的跑起來，從出口流量看到它連了誰，再補上。這本來就是三層設計的分工，不是靜態層的缺陷。
>
> 第四項，URL 經過自己寫的函式參數才到 client。語料裡有一個爬蟲，寫 `scrapeFromPlatform("Amazon", "https://amazon.com/...")`，函式裡面才呼叫 requests.get。使用慣例是「字串要在呼叫那一行附近、或透過變數名追到呼叫那一行」，追的是變數，不追函式參數。要追參數，就是跨函式的資料流分析，每個語言都要做一份。Go 的註冊名那條我做過一次，為的是一個很常見的寫法；這個寫法一百個系統只有 4 條，不值得。
>
> 右邊四項是還能做的，都是個位數的線，每一項講為什麼做得到。
>
> 第一項，yas 剩兩條錯邊：backoffice 連 order、storefront 連 payment。位址寫在模組自己的 application-dev.yaml，`yas.services.order: http://order`，程式碼沒有用這個鍵。歸屬的延伸——程式碼讀得到的容器，env 區塊裡沒用到的服務位址不畫——這次只套在 Compose 和 Kubernetes 的 env 區塊，模組自己的設定檔那一路沒套。同一個檢查搬過去就好：鍵在程式碼的呼叫點沒出現，就不畫。
>
> 第二項，skywalking 三條。loadgen 連 app：loadgen 真正打的是 frontend，loadgen.py 寫了 http://frontend/index.html，那條有畫、documented；錯的是 Compose 裡 loadgen 寫了 depends_on app（等 app 健康），第二種結局只檢查「env 區塊有沒有位址」，沒看程式碼層已經說了它打誰，就多畫一條 inferred。補法很直接：來源的程式碼層已經有呼叫邊，depends_on 就只留啟動順序。songs 連 gateway：songs 的程式碼宣告了一個 rootUri 是 http://gateway 的 RestTemplate bean，但整個專案沒有任何類別注入或使用它，是死的；要求「bean 要有人用」就能排除，這其實是④的延伸。executejob：同一個東西 Compose 叫 executeJob、Kubernetes 叫 execute-flink-job，目標 jobmanager 是對的，只是名字對不上參考答案的拼法；名字表要認得這種兩個部署檔各一種拼法的對應。
>
> 第三項，來源歸到目錄名。一個檔案不在任何模組目錄底下，工具退而用它的第一層目錄名當來源，結果圖上多了叫 resources、quickstart 的節點。名字表慣例已經有「不在模組裡的檔案，只有目錄名恰好等於部署宣告的服務才歸它」這條，差在最後那個退路還留著；把退路拿掉，不在模組裡又對不上宣告名的檔案就不發明來源。
>
> 第四項，給瀏覽器的連結網址。.NET 的 appsettings 有 `Url:Website`、`SpaBaseUrl` 這種鍵，值是網站自己的網址，服務把它塞進網頁或信件裡給使用者點，不是服務要連的對象。鍵名的「誰能連我」字詞表有 site、public 這些字，但 website、spa 不在；加字會誤傷，更穩的做法是走使用慣例：這個鍵被讀的地方是網頁範本或信件範本、不是 HTTP client，就不是呼叫。這等於把④從程式碼的 URL 字串推廣到設定鍵，是下一輪可以做的。

🛡 **「左邊第一項和 db／broker 的表有什麼不一樣？」** → db／broker 那份是框架文件規定的通用綁定（任何 SPRING_* 鍵），一份表管整個生態系；locust、flagd 是單一套件自己的變數名，一套件一列。
🛡 **「右邊既然做得到為什麼不做？」** → 每項一到三條線，而且都在已經看過的系統上；先抽 hold-out F 量一次，再決定哪些值得做，不然又變成測一次修一次。
