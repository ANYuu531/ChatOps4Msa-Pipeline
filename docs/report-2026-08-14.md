### A2：NL → 圖查詢 → 確定性執行 → LLM 講結果

核心原則沿用專案既有哲學（`CodeGraphMerger`：「prefer not to use the LLM, only where necessary」）：
**LLM 只負責兩端——理解問題、講白話；中間的圖上事實由確定性引擎回答，杜絕幻覺。**

```
使用者問句
   │  (LLM：理解意圖 → 產出結構化查詢)
   ▼
圖查詢 DSL / function-call
   │  (確定性執行器，直接跑在 DependencyGraph 上)
   ▼
精確的節點/邊集合  ──►  (LLM：把結果講成人話 + 附證據 file:line / runtime count)
```

- **grounding 來源已存在**：`DependencyGraph.toJson()` 就是現成的 Canonical Graph JSON，每次分析都有；`DependencyAnalysisStateStore` 已有 checkpoint 持久化，查詢時載入即可。
- **確定性執行器要提供的查詢原語**（對應圖上實際欄位 source/target/type/provenance/confidence/runtimeObserved/count/deployed）：
  - `dependencies-of(X)` / `dependents-of(X)` — X 依賴誰 / 誰依賴 X
  - `impact-of(X)`（transitive dependents）— 「改 X 會波及哪些服務」
  - `startup-needs(X)`（transitive dependencies）— 「X 起來前要先起哪些」
  - `really-uses-db()` — confidence=documented 的 db 邊（已由持久化層判定「真的用到 DB」）
  - `edges-of-type(db|async|external|sync-http)`、`undeployed()`、`coverage()`
  - `deploy-order()` — 硬依賴子圖拓樸排序 → 直接餵給 DeployPlanner（與 C 的接點）
- **與既有基礎設施的接點**：
  - ChatOps bot 已有 NLP capability 路由（capability YAML）；新增一個 `dependency-query` capability 即可掛上對話入口。
  - 團隊已實作過通用運算子引擎 + `#when?` 表達式直譯器（`PredicateEngineTest`，12 測試）——圖查詢執行器是同一種「小型確定性求值器」的精神，可沿用其設計思路。

## 任務 2 — 用 Bank of Anthos 驗證依賴圖（全程零 port）

### 為何選 Bank of Anthos
Google 的 microservices demo，**Java(Spring Boot) + Python(Flask) 混合**、用 PostgreSQL、且**原生 k8s service discovery（不靠 Eureka）**，正對上我們的 k8s-native 方向，是理想的「沒看過的多語言專案」樣本。

### 怎麼跑到零 port
依賴圖四層裡只有 C(Istio 執行期)、D(涵蓋率) 需要叢集/port；**A(tree-sitter 靜態碼) + B(靜態設定) 純靜態**，只 `git clone` + 本地解析。本次只跑 A+B，**不碰叢集、不開 port，共用機器安全**。

驅動：`src/test/java/.../StaticExtractionProbeTest.java`（可重複用的通用 probe，之後測任何 Java/Python 專案都能用）：

```
mvn -o test -Dtest=StaticExtractionProbeTest -Dprobe.repo=/path/to/checkout
```

刻意跳過 LLM tier（BoA 有 11 個 .js 檔會被判成 LLM stack），只跑 java/python tree-sitter + config，全程離線確定性。無 `-Dprobe.repo` 時自動 skip，不影響一般 `mvn test`。

| **Python DB 判定（老師點名）** | `contacts`(table=contacts)、`userservice`(table=users) 經 SQLAlchemy `Table()` 判為「真的有用到 DB」✅ |

| 服務間呼叫 | frontend 的 `http://{}/...` + env(`TRANSACTIONS_API_ADDR / USERSERVICE_API_ADDR / BALANCES_API_ADDR / HISTORY_API_ADDR / CONTACTS_API_ADDR`) → frontend 對 5 個後端；ledgerwriter→balancereader 也在 |

> 附記：原本假設 BoA 的 Java 帳本服務用 Spring Data JDBC（非 JPA）會被漏判，實測發現它其實用 JPA 標註，**判定正確命中**——反而佐證 JPA 偵測能泛化到非 petclinic 的 Java 專案。

### 成果 B：圖層(ledger→graph)原本**不泛化**，本次**已修好** ✅

先講發現(實測)：把 BoA 的 edgesJson 餵進 `CodeGraphMerger.merge`（空 runtime graph，模擬純靜態 greenfield），**整張圖塌成零邊**：

```
修前：resolved nodes = 0 | resolved edges = 0 | UNRESOLVED = 50 → Mermaid 空圖
```

根因兩個，都有實測證據：
1. **來源歸屬假設扁平模組 layout**：`resolveSource()` 取 file 第一層路徑段。petclinic 是 `spring-petclinic-customers-service/...`（第一段就是服務）；BoA 是 `src/ledger/balancereader/...`，第一段 `src` 命中 `SOURCE_STOP` → source 全 null。
2. **合併以 runtime graph 節點為詞彙表**：純靜態沒 runtime 層 → 無詞彙表 → env 間接目標（`TRANSACTIONS_API_ADDR`）無從解析。

**修法（附加式，不動 petclinic 現行 runtime 路徑；`greenfield = runtime 節點為空` 才啟用新邏輯）：**

| 缺口 | 修法 | 檔案 |
|---|---|---|
| ① layout-aware 服務根 | 新 `ServiceRootScanner` 掃出「含 build manifest/Dockerfile 的目錄」→ `service-root` meta-section(dir→name);合併層以「最深的服務目錄前綴」歸屬來源 | `ServiceRootScanner.java`、`CodeGraphMerger.resolveSource/serviceForFile` |
| ② 靜態節點詞彙表 + env 解析 | `ConfigExtractor` 讀 k8s ConfigMap/Deployment 的 `env→host`(如 `TRANSACTIONS_API_ADDR→ledgerwriter`)→ `env-address` meta-section;合併層 greenfield 時用它 seed 詞彙表,並把 code 的 config-env 邊 + url 裡的 `${ENV}` 佔位解析成具體服務 | `ConfigExtractor.extractK8sEnvAddresses`、`CodeGraphMerger.indexMeta/hostFromEnvPlaceholder` |

**修後(實測,同一支 probe)：**

```
修後：resolved nodes = 11 | resolved edges = 6 | Mermaid 非空
```

產出 BoA 的實際服務呼叫圖(見 [bank-of-anthos-greenfield-graph.mmd](bank-of-anthos-greenfield-graph.mmd))，**與 BoA 真實架構一致**：

```
frontend → ledgerwriter · userservice · balancereader · transactionhistory · contacts
ledgerwriter → balancereader     （寫交易前先驗餘額）
節點含 accounts-db / ledger-db（依命名判為 :::db）
```

全程**零 port、零叢集**——正是 greenfield 的前提。

**測試**：`DependencyGraphTest` 加 4 個 greenfield 測試(用 BoA 形狀的 fixture、免網路,CI 可跑),40→**44 全過**;petclinic runtime-anchored 路徑不受影響(既有測試全綠)。`StaticExtractionProbeTest` 為可重複用的真專案 probe。

**仍留的下一步細節(honest)**：`service→db` 的**箭頭**還沒畫(DB 節點已在)。BoA 的 DB 連線在服務的 Deployment 透過 `configMapRef: ledger-db-config` 掛入、三個 ledger 服務共用同一個 `SPRING_DATASOURCE_URL`,要畫箭頭需再做「Deployment→configMapRef→db」的解析,是一條乾淨的後續。另 `ui-tests`(UI e2e 測試目錄含 package.json)被當成孤立服務節點,是小的偽陽性。

### 成果 C：入口行為——**沒給 namespace 就自動走 greenfield**

把上面「greenfield 可出圖」接到使用者入口:呼叫依賴分析指令時**若不輸入 namespace,就自動判定為 greenfield**(專案尚未部署),整條流程**跳過所有需要叢集的步驟**、只跑靜態(程式碼 + 文件 + 靜態依賴圖)。

- `toolkit-depstate-start` 依 namespace 空/`none` 判 `analysis_mode = greenfield|runtime`([DepstateToolkit.isGreenfield](src/main/java/ntou/soselab/chatops4msa/Entity/ToolkitFunction/DepstateToolkit.java))。
- orchestrator 在派工迴圈用 `analysis_mode` gate 掉**需要叢集的步驟**([CapabilityOrchestrator.requiresLiveCluster](src/main/java/ntou/soselab/chatops4msa/Service/CapabilityOrchestrator/CapabilityOrchestrator.java)):k8s MCP(connect/kubectl,以 `server_name=k8s` 區分,**DeepWiki 文件 MCP 照跑**)、Istio Prometheus 查詢、流量驅動、Apply ServiceEntry 按鈕。
- 設計取捨:low-code 的 `flow-if` sub-list 跑在**變數表的深拷貝**上,包整段 runtime 會讓後續 health-check 在正常模式拿不到 runtime 變數(regression);故改用**派工迴圈的 gate**(共用變數表、不隔離),只在 greenfield 時 skip,對現行 runtime 路徑零影響。
- 測試:`GreenfieldModeTest`(namespace→模式)+ `GreenfieldGatingTest`(哪些步驟被 gate),純函式免網路。

> 殘留(小):greenfield 時 runtime 區塊裡穿插的幾個 `toolkit-llm-call`/DEBUG 訊息仍會跑(輸入為空、產生無害的「無資料」摘要),之後可再收斂。
