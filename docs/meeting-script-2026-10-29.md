## P3 · recall 低的原因：逐條追下去都是規則缺口

📍 一列一列講。每列先講「漏的是什麼線」，再講「為什麼沒畫」。最後指「7 個平均」那列和右下的框。

💬
> 先講 recall：一個系統該有的線，工具畫出了幾成。上次有三個系統很低：ecommerce 只畫出 54%、TeaStore 46%、robot-shop 86%。論文原本說原因是靜態分析做不到。我一條一條去看漏掉的線，結果不是。
>
> **ecommerce** 是一個網路商店，有 8 個業務服務：會員、商品、訂單、付款、運送、收藏，加上入口的 gateway 和 proxy。每個服務啟動時都要做兩件事：第一，去**設定中心** cloud-config 拿自己的設定；第二，去**註冊中心** service-discovery 登記自己在哪。所以每個服務應該都有兩條線，一條連設定中心、一條連註冊中心。漏掉的 17 條就是這些線：8 條連設定中心，9 條連註冊中心（設定中心自己也要去登記）。
>
> 為什麼沒畫？設定中心那 8 條，設定檔裡寫的位址是 `localhost:9296`。localhost 的意思是「我自己這台機器」，工具原本的規則是 localhost 不畫，因為通常是指自己。可是 9296 這個 port，在整個 repo 裡只有設定中心宣告自己用它，所以這行其實就是在指設定中心。註冊中心那 9 條更隱藏：設定檔裡根本沒寫註冊中心在哪，只在建置檔裡裝了 Eureka 的套件。Spring Cloud 的規定是，沒寫就自動連 `localhost:8761`，也就是 repo 裡那台註冊中心。所以兩種線的資訊都在 repo 裡。
>
> **TeaStore** 也是網路商店。網頁服務要呼叫登入、圖片、推薦、資料存取四個服務；登入、圖片、推薦又都要呼叫資料存取去讀寫資料庫。這 7 條是整個系統最主要的業務呼叫，工具一條都沒畫。
>
> 為什麼？程式碼裡不是寫「呼叫 http://persistence」，而是寫「呼叫 `Service.PERSISTENCE`」，再由 TeaStore 自己寫的註冊中心在執行時查位址。原本以為這是「跑起來才知道呼叫誰」，靜態分析看不到。但點進 `Service.PERSISTENCE` 這個常數，它的值是 `tools.descartes.teastore.persistence`，剛好就是資料存取服務的資料夾名稱。執行時查的只是「它現在在哪台機器」，要呼叫誰，程式碼裡早就寫好了。
>
> **robot-shop** 漏 3 條：運送服務要問購物車裡有什麼、購物車要問商品目錄拿價格、評分服務也要問商品目錄。後兩條寫在 Node.js 和 PHP 裡，工具當時讀不懂這兩種語言，這 2 條才是真的「沒有文法」。第一條是 Java，寫的是 `getenv("CART_ENDPOINT", "cart")`：讀環境變數，沒設就用 cart。這個 cart 就是購物車服務的名字，工具只是沒去讀這個預設值。
>
> **piggymetrics** 剛好相反，是多畫了 8 條錯的線。例如 gateway 被畫成連到 RabbitMQ 訊息佇列、註冊中心被畫成連到登入服務。原因是 piggymetrics 有一份所有服務共用的設定檔，裡面寫了 RabbitMQ 和登入服務的位址，工具就以為每個讀這份設定的服務都會連過去。但 gateway、註冊中心、監控這幾個服務根本沒裝 RabbitMQ 的套件，設定寫了它們也不會用。
>
> 所以原本說的三個「做不到」：主機名不在 repo 裡、跑起來才知道呼叫誰、沒有文法，前兩個都不成立，第三個只佔 2 條。補完之後這 7 個系統都是滿分。但要先講清楚：規則就是看著這 7 個系統的錯誤寫出來的，這個滿分不能拿來說「對新系統也這麼好」。對新系統好不好，要看後面那幾組補規則時沒看過的系統。

🛡
- 「刪掉兩條參考答案，是不是改答案讓分數好看？」→ 刪的 2 條都查過沒有證據：註冊中心 → 設定中心這條，註冊中心的建置檔根本沒裝設定中心的套件；監控 → 註冊中心這條，監控沒裝 Eureka。而且兩條的效果一正一負：前一條工具本來就沒畫，刪掉讓 recall 變好；後一條工具**有畫**，原本算對，刪掉後變成錯的線，讓 precision **變差**。
- 「參考答案是你自己寫的？」→ 每條都附檔案路徑和行號，有自動測試檢查 114 筆出處都打得開、內容對得上；另外有第三方資料集 MicroDepGraph 的 95 條，工具畫出 93 條；還請一個沒看過答案的 LLM 獨立標一次，它多出來的 40 條逐條查過，沒有一條是我們漏的。

## P4 · 解法細節：repo 裡寫了什麼、規則怎麼讀、什麼時候不畫

📍 一列一列往右讀：左欄原文 → 中欄規則 → 右欄什麼時候放棄。第一列講完整，其他各一句；最後指下面的框。

💬
> 上一頁講漏了什麼，這頁講規則長什麼樣子。重點是中間那欄：規則裡沒有「ecommerce」「TeaStore」這些名字，寫的是一般的道理；右邊那欄是它什麼時候**不畫**。
>
> 第一列：「localhost 加 port 時，去找整個 repo 裡**唯一**宣告這個 port 的服務」。ecommerce 只有設定中心宣告 9296，所以讀回設定中心。如果沒人宣告，或兩個服務都宣告 9296，就不畫，因為無法確定是誰。就算畫了，也標成「推測」畫虛線，因為設定中心的名字從頭到尾沒被寫出來。
>
> 第二列：「裝了 Eureka 套件、卻沒寫註冊中心位址的服務，連到 repo 裡**唯一**的那台註冊中心」。如果有兩台註冊中心、或服務自己寫了位址，就不套。
>
> 第三列：「一個常數的值剛好等於某個服務的資料夾名稱，而且被拿去當呼叫的參數，就是在呼叫那個服務」。值對不上任何服務名稱，就不畫。
>
> 第四列：「程式讀環境變數拼網址時，先查部署檔裡有沒有設這個變數，沒有才用程式碼裡的預設值」。兩邊都沒有就不畫。
>
> 第五列：「共用設定裡的 RabbitMQ、登入服務設定，只對有裝對應套件的服務有效」。這條是拿掉錯的線，不是多畫線。
>
> 最下面是共同點：每一條規則做的都是把 repo **已經寫明**的事讀出來，不確定就不畫，畫出來的線都附出處和等級。

🛡
- 「畫成推測的線，計分時算不算？」→ 算。計分只看線在不在；實線虛線是讓讀者知道可信度。ecommerce 現在 37 條線裡有 17 條是虛線，就是這批讀回來的。
- 「為什麼不乾脆把 localhost 都當成某個服務？」→ 那就是用猜的。以前 piggymetrics 和 TeaStore 就因此多出一個叫「localhost」的假節點；只有 port 能指認到唯一一個服務時才讀回去。

## P5 · 為什麼純程式碼做得到：相依關係本來就寫在 repo 裡

📍 左表四種檔案 → 「工具只做兩件事」那句 → 左下的框；右上四點 → 右下兩點。

💬
> 老師一定會問：只靠讀程式碼，怎麼可能這麼準？原因很簡單：系統要能部署、要能跑，每個服務要連誰，就一定得寫在某個檔案裡，不然它自己也連不上。部署檔寫了有哪些服務、每個服務的環境變數裡放了誰的位址；設定檔寫了資料庫連線、gateway 轉到哪裡；建置檔寫了裝了哪些套件；程式碼寫了呼叫哪個網址。工具只做兩件事：把這些讀出來，再把名字對起來。它不推論。
>
> 左下是佐證：叫 LLM 直接畫圖，有給檔案能畫對 90%，不給檔案只有 70%；換成 LLM 一定沒看過的私有系統 AICS，不給檔案只剩 42%。答案在檔案裡，不在模型的記憶裡。我們的規則是把同一批資訊用固定的方式讀出來，每次結果都一樣，而且每條線都能指回是哪個檔案哪一行。
>
> 為什麼畫出來的線很少錯？因為規則很保守。右上四點：對不到唯一一個服務就不畫；只是宣告、沒人用的就不畫，像 ecommerce 有一個常數檔列了 25 個網址，其中 19 個整個程式都沒用到，這 19 個不畫；localhost 不畫，除非 port 能指認；真的判斷不了的，列出來給人確認。
>
> 純程式碼也有做不到的，右下兩點。程式用某個名字去註冊中心找服務，可是 repo 裡找不到是誰用這個名字登記的，或是程式用的語言工具讀不懂，這時候就交給人確認，這是 pattern ③。哪些線實際上真的有流量、跑了幾次，只有系統跑起來才看得到，這是 pattern ①②。所以靜態分析本來就只是三個來源之一。

🛡
- 「既然 LLM 有給檔案也能畫對 90%，為什麼還要工具？」→ 三件分數看不出來的事：LLM 畫的線沒有出處，沒辦法逐條檢查；同一個問題問三次答案不一樣，TeaStore 那組該有的線最多畫出 100%、最少只有 46%，還有幾次一直重複輸出同樣的線停不下來；名字也不一定對得上，ecommerce 不給名稱時三次都是 0。而且在沒看過的系統和 AICS 上，我們比有給檔案的 LLM 好（P13）。
- 「那 LLM 就不用了嗎？」→ 會用，是下一步：當成第四個來源接進來，它畫的線最多只算「推測」，名字一樣要經過確認（P15）。

## P6 · 怎麼避免「只對看過的系統有效」：每批規則用下一組沒看過的系統量

📍 上方四個框從左到右；左下三組系統；右下回歸檢查。

💬
> 這頁是方法，也是回答「是不是窮舉」最重要的一頁。
>
> 做法分四步。第一步，在補規則**之前**，先另外選好幾個系統，這組叫 hold-out。第二步，把這幾個系統正確的相依圖一條一條寫好：哪個服務連哪個服務、根據是哪個檔案哪一行。第三步，用當時的工具跑一次，記下分數。第四步，開始補規則，這時候只看別組系統的錯誤，這組系統的圖和錯誤完全不打開看。等規則補完，再用新版工具把這組系統重跑一次，跟第二步寫好的答案逐條比對。分數變好，代表新規則對沒看過的系統也有用；分數沒變，就代表沒用。
>
> 上方四個框是四批規則的順序。第一批規則 15 到 23，是從剛才那 7 個系統和 AICS 的錯誤歸納出來的，用 B 組三個系統來測。第二批 24 到 35，是看 B 組的錯誤歸納的，用 C 組來測。第三批 36 到 46，看 C 組的錯誤歸納，用 D 組來測。第四批 47 到 56 換了做法，第 10 頁講。規則各在做什麼，下兩頁會講。
>
> 系統都是 GitHub 上公開的開源微服務專案，選的條件寫在左下：公開、沒有封存、至少 6 個服務、技術跟前面各組不一樣，並且鎖定在某一個版本。不符合條件的也有留紀錄，例如有一個 .NET 專案，抓下來才發現實際只部署 4 個服務，就換掉了。
>
> 三組刻意挑跟前面不一樣的系統：B 組有 OpenTelemetry 官方的示範系統，十種語言混在一起；一個用阿里巴巴那套 Spring Cloud 框架的電商；一個學界常用的效能測試系統 DeathStarBench 裡的訂房服務，Go 加 Consul。C 組有新版 Spring Boot 的電商 yas，和全部用 .NET 寫的電商。D 組有 Kiali（Istio 的監控工具）官方的旅遊示範系統，純 Kubernetes 加 Istio、分三個 namespace；還有 Apache SkyWalking 的示範系統，用 Helm 模板和 20 份 Compose 檔部署。
>
> 右下：每補一批，前面所有系統都重新跑一次，一條一條比，沒有一個變差。邊有變動的只有兩個系統：train-ticket 拿掉一條假的線、多了 38 條入口路由；hotelReservation 多了 9 條服務之間的呼叫，就是第 10 頁講的那 9 條。

🛡

## P7 · 新增的 42 條規則在做什麼（一）：找到位址、對上名字

📍 先指最上面那行（1–14 是之前的），再指左表標題、念三四列，再指右表、念 36 那列和下面的框。

💬
> 這兩頁把這次新增的 42 條規則全部列出來。規則 1 到 14 是之前報告過的基本讀法，例如讀部署檔裡有哪些服務、設定檔裡寫的位址。新的 42 條，我照「在解決什麼問題」分成四類，每條後面括號是第一次遇到這個問題的系統。
>
> 第一類是**找到位址**。最直覺的情況是程式碼直接寫「呼叫 http://cart」，但很多系統不是這樣寫，位址寫在別的地方。15、16、17、18 就是剛才講過的 localhost 加 port、Eureka 沒寫位址、常數值、環境變數預設值。其他的例如 24：Compose 檔裡只寫了變數名 `CART_ADDR`，值放在旁邊的 `.env` 檔，要去 `.env` 找。47：程式先把網址存進一個變數，隔幾行才拿去呼叫，要往回追這個變數。55：一個設定裡用逗號列了好幾個網址，每個都要算一條線。
>
> 第二類是**對上名字**。同一個服務常常有好幾種叫法，名字對不上，線就算畫了也不算數。例如 19：`order-v1`、`order-v2` 是同一個服務的兩個版本，不是兩個服務。25：Compose 可以幫 mysql 取別名叫 `db`，設定裡寫連到 db，其實是連 mysql。36 就是 .NET 系統那個 bug：服務叫 `catalog.api`，工具以為 `.api` 是網域名稱把它切掉，名字全部對不上，整張圖 0 分。最後一列 49 是 Consul：hotelReservation 的 frontend 程式寫「去 Consul 找 `srv-search`」，而 search 服務自己的程式碼寫「我用 `srv-search` 這個名字向 Consul 登記」。兩邊的名字一樣，就知道 frontend 是在呼叫 search，不用猜；如果 repo 裡沒有人用這個名字登記，才列出來問人。

🛡
- 「42 條會不會太多？」→ 分成四類看，每一類是同一個道理在不同寫法上的展開；而且第 12 頁的觸發計數顯示，大部分在很多系統上都用得到。

## P8 · 新增的 42 條規則在做什麼（二）：不該畫的不畫、讀得懂更多格式

📍 左表念三四列，右表四列，最後指右下的框。

💬
> 第三類是**不該畫的不畫**。有些東西看起來像連線，其實不是，畫了就是錯的線。23 就是剛才 piggymetrics 的共用設定。其他例子：29，API 文件裡會寫授權條款的網址、作者的聯絡網址，那不是服務在呼叫誰；31，測試用的 Compose 檔和測試資料夾，裡面的假服務不是系統的一部分；35，Compose 的 depends_on 意思是「等它先啟動好我再啟動」，不一定真的有網路連線，所以規則是：服務自己寫了別人的位址、卻沒寫到它，就不畫；服務完全沒寫任何位址時，depends_on 是唯一的線索，才畫成虛線；51，網頁裡 `<script>` 載入的程式是在使用者的瀏覽器裡跑的，它呼叫 Google API 不代表伺服器在呼叫 Google。
>
> 第四類是**讀得懂更多格式與語言**。28、40 讓工具讀得懂 Kotlin 和 C#，第四批再加上 JavaScript、TypeScript、Go、PHP。34、38、56 是各種閘道的設定檔：Envoy、YARP、Istio、APISIX 的寫法不同，但內容都是「外面進來的流量轉給誰」。52 是 Helm：它是填空式的部署檔，要先把預設值填進去才讀得懂。
>
> 右下總結：前兩類讓該有的線畫出來，提高 recall；第三類讓錯的線不要畫，提高 precision；第四類讓前三類能用在更多語言和部署方式上。每一條都沒有寫死專案名。

🛡
- 「35 條 depends_on 為什麼不直接不畫？」→ 在第三方資料集那 7 個系統裡，只靠 depends_on 畫出來的線有 100 條，90 條是對的；全部不畫會丟掉這 90 條（第 14 頁）。

## P12 · 是不是窮舉？證據二：每條規則在 22 個系統裡用到幾個

📍 最上面那段 → 四個數字 → 左表，先講表頭再念三列 → 右上兩點 → 右下第 26 條的框。

💬
> 證據二是量出來的。每條規則都是看 1 到 3 個系統的錯誤寫出來的。如果它在**其他系統**也會改變畫出來的圖，就代表它抓到的是大家共通的寫法，不是某個系統的特例。所以我在程式裡加了記錄：每條規則在每個系統上，實際讓圖改變了什麼，多畫一條線、少畫一條線、實線改虛線、或把兩個名字合成一個節點，都記下來。
>
> 四個數字：56 條裡，23 條在 5 個以上的系統用到；21 條在 2 到 4 個系統用到，而且每一條都至少有一個是寫規則時沒看的系統；11 條只在寫出它的那個系統用到；1 條從來沒用到。
>

>
> 右上是只在 1 個系統用到的 11 條：6 條是那種技術在 22 個系統裡只出現一次，像 Kotlin、Envoy；另外 5 條是某種寫法只出現一次，要再遇到一個系統才知道是共通寫法還是特例。
>
> 右下是從沒用到的第 26 條：看連線字串的開頭判斷對方是什麼。開頭是 `jdbc:`、`mongodb://` 就是資料庫，`amqp://` 就是訊息佇列，不管主機叫什麼名字。工具平常是看名字判斷，名字裡有 mysql 就當資料庫。我們 22 個系統的資料庫都老老實實叫 mysql、mongodb 這類名字，看名字就判對了，這條一直沒機會改變結果。留著是當保險：真實系統常有人把資料庫取成看不出來的名字，例如 `jdbc:postgresql://orders-store`，看名字會被當成一般服務，這時候就靠這條。

🛡
- 「只在 1 個系統的 11 條，不就是窮舉？」→ 這 11 條一樣沒有寫死專案名，寫的還是技術上的道理；只是我們的系統裡剛好只有一個用到那種技術。論文把它們分開列，沒有混在「共通寫法」裡算。
- 「第 26 條既然沒用過，怎麼知道它是對的？」→ 它的延伸第 39 條有單元測試，測過 `amqp://` 開頭的會被改判成訊息佇列；但「`jdbc:` 開頭、主機名看不出是資料庫」這個情況目前沒有專門的測試，會後補一個。論文把它單獨列為從未觸發。

## P13 · 假想敵擴大到 hold-out 與私有系統

📍 左表三欄 → 表下小字 → 右上框 → 右下三點。

💬
> 上次「直接叫 LLM 畫圖」的對照只跑了那 7 個系統。這次加跑 B、C 組 5 個系統和私有的 AICS，在機器 B 跑。

> 最有說服力的是 AICS，它是私有的，LLM 不可能看過。不給檔案時，LLM 畫對的幾乎都是看名字就猜得到的線，例如「X 服務連 X 服務的資料庫」、「爬蟲連外部網站」；服務跟服務之間的呼叫，畫出來的只有兩成對、該有的也只畫出兩成。也就是說，沒有事實，LLM 只能看名字猜。
>
> 有給檔案也有天花板：yas 檔案太多，超過能塞進去的量，三次都只畫出一半；AICS 從外部進來的 6 條入口路由，三次全漏；還有三次一直重複輸出同樣的線停不下來。LLM 唯一明顯贏我們的是 hotelReservation：它把呼叫端的 srv-search 跟 search 服務登記的名字對起來了。這個比較是拿第三批規則時的靜態層，那時 hotelReservation 是 0.71；現在靜態層也做同一件事，第 49 條，所以也是 1.00。表上我們那一列已經換成現在的規則，hold-out 5 個系統是 0.97。
>
> 表下有一句要誠實講：我們那一列，是在這些系統上補過規則之後的分數，不是第一次測的成績。

🛡

## P14 · 還沒解決的，以及刻意不做的

📍 左表四列 → 右邊三點 → 右下框。

💬
> 還沒解決的，每一個都知道原因。第一個就是剛才說的 skywalking：該有的線都畫出來了，但多畫了 10 條錯的線，其中 8 條是 Compose 裡的 depends_on：它的意思是「等某個服務先啟動好我再啟動」，例如等資料庫健康檢查通過、或兩個容器共用一個資料夾，不一定真的有網路連線，但工具把它畫成了虛線。讀不懂的語言只剩 Rust 和 Ruby。AICS 剩下漏的，多半是叢集外面的元件，和透過雲端 SDK 呼叫的外部服務。
>
> 有三件事刻意不做。第一，depends_on 不再降級：在第三方資料集那 7 個系統裡，只靠 depends_on 畫出來的線有 100 條，其中 90 條是對的；為了拿掉 skywalking 這 8 條錯的，會連那 90 條對的一起丟掉，不划算。第二，雲端套件和叢集外的元件。例如 AICS 呼叫 OpenAI，程式碼只寫 `openai.ChatCompletion.create(...)`，網址 `api.openai.com` 藏在 openai 這個套件裡面，不在我們的 repo；要畫出來，工具就得內建「哪個套件連到哪個網址」的對照表，世界上的套件那麼多，一個一個列就是窮舉。叢集外的元件也一樣：AICS 有一個爬蟲跑在另一台 VM、一個備份程式跑在備份機上，部署檔裡沒有它們，要補就得一台一台告訴工具。第三，名字不憑相似來猜：srv-search 看起來很像 search，但我們不是因為長得像才畫，是因為對到 search 登記那一行程式碼才畫。
>
> 論文會這樣寫：只有黃底才算泛化成績，修過的分數都標明「在這個系統上補過規則」；而且「每組新系統都會冒出新寫法」這件事本身也照實寫。

🛡
- 「skywalking 修完 precision 為什麼還是只有 0.44？」→ 三個原因疊在一起：
  - **答案很少，一條錯就差很多**：skywalking 真正的應用只是一個小小的音樂網站，算分的線只有 8 條（網頁 → gateway、推薦 → 歌曲、推薦 → 評分、gateway 的兩條路由等）。工具畫了 18 條，對 8 條、錯 10 條，8 ÷ 18 = 0.44。
  - **錯的 10 條裡有 8 條是 depends_on**：這個 repo 另外附了 20 份「監控示範」的 Compose 檔，裡面大量用 depends_on 表示「等它先啟動」，例如 vm1、vm2 這兩台被監控的假機器 depends_on 監控主機 oap，只是要等 oap 先起來，它們自己根本不連 oap，是另一個服務 otel-collector 來抓它們的資料；es-mock depends_on es-exporter 也只是等它健康。這些服務的設定裡完全沒有位址，第 35 條就照規則畫成虛線。拿掉這 8 條，precision 是 8 ÷ 10 = 0.80。
  - **剩下 2 條不算真的錯**：一條是 executeJob → jobmanager，目標對了，但答案用 Kubernetes 那邊的名字 execute-flink-job，名字對不上；另一條 songs → gateway，程式宣告了一個指向 gateway 的 RestTemplate 卻從沒用它，答案本身也有爭議。
- 「那為什麼不修 depends_on？」→ 在第三方資料集那 7 個系統裡，只靠 depends_on 畫出來的線有 100 條，90 條是對的；直接不畫，會為了 skywalking 的 8 條丟掉那 90 條。
- 「有沒有更聰明的分法？」→ 試過一個（10/28）：「depends_on 的來源在 repo 裡沒有自己的程式碼（直接用現成映像），而且設定裡也沒有任何位址，就不畫」。skywalking 的 8 條錯線確實拿掉 7 條，precision 會從 0.44 升到 0.73。但在 23 個 checkout 上逐邊比對，代價太大：
  - hotelReservation 的 22 條線全部消失，其中服務 → 自己的資料庫、服務 → Consul 都是對的。原因是它所有服務都從同一份程式碼建成同一個映像，只是啟動指令不同，工具看不出每個服務「有自己的程式碼」。
  - 第三方資料集的吻合率從 93/95 掉到 90/95（spring-cloud-microservice 的 simple-service2 → 註冊中心、設定中心、zipkin 三條）。
  - skywalking 自己也丟掉好幾條真的連線，例如 fluent-bit → oap、壓測工具 → pulsar broker：現成映像不是不連線，只是位址寫在掛進去的設定檔或預設值裡。
  - 所以這個訊號不成立，程式沒有改。結論是：光看部署檔，分不出「等它啟動」和「真的會連」，這正是要靠系統跑起來看實際流量的地方。那 8 條是虛線，跑起來沒有流量，就會一直留在虛線。
- 「錯的線讀者會被誤導嗎？」→ 那 8 條都畫成虛線，讀者看得出來是推測；系統跑起來之後，沒有實際流量的線不會被升成實線，會一直留在虛線。
