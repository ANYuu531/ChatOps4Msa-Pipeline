!title DepWeaver：以多來源融合、信心分級與對話式缺口補齊建構微服務相依圖
!subtitle DepWeaver: Multi-Source Fusion with Confidence Grading and Conversational Gap-Filling for Microservice Dependency Graph Construction
!abstract 微服務系統的相依圖是部署排序、變更影響分析與測試規劃的基礎，但單一來源難以完整重建它：執行期觀測只看得到被觸發的呼叫，靜態分析處理不了動態分派，也處理不了尚未支援文法的語言，專案文件則可能過時或錯誤。把多個來源合在一起可以提高完整度，卻帶來新的問題：讀者分不出圖上哪一條關係是量測到的、哪一條只是有人提過，覆蓋率數字與 LLM 撰寫的報告也可能和圖互相矛盾。本文提出 DepWeaver，一個整合在 ChatOps 環境中的相依圖建構方法。它從服務網格的執行期觀測、tree-sitter 靜態分析與專案文件三個來源抽取關係，再融合成統一模型；模型中每條邊帶有逐條出處與三級信心等級（僅推測 < 有使用證據 < 量測到）。圖、覆蓋率與報告都由這個模型產生：相依關係清單由程式撰寫，不交給 LLM 重述；覆蓋率只計算量測機制能夠量測的關係；沒有量測的值明示為「未量測」。自動手段用盡時，才在對話中請操作者提供缺少的值，並確認對不上的服務名稱指的是哪個服務。在 21 個開源系統與 1 個私有系統上評估：靜態層對第三方 MicroDepGraph 參考邊集合的吻合率為 0.98（93/95）；作為假想敵，不給檔案的 LLM 直接畫圖 F1 為 0.70，給了檔案後為 0.90，但沒有出處、執行結果不穩定、名稱常對不上，而它贏過靜態層的地方正好指出規則的缺口。補上規則後，歸納用的 7 個系統 precision 全為 1.00、recall 0.99，但這些規則對 3 個未見過的 hold-out 系統一條邊都沒有改變；改從 hold-out 歸納、再以另外未見過的系統量測，才有部分轉移（其中一個系統的業務呼叫邊 recall 由 0.11 提高到 0.89；第四組的純 Kubernetes 系統 P 1.00、R 0.84 直接轉移）。靜態層的 recall 因此是寫法涵蓋率，不是靜態分析的極限。在真實部署的 Bank of Anthos 上，融合執行期觀測後業務呼叫覆蓋率 7/7、資料層 5/5；關閉 repo 範例來源再執行一次時，最後兩條業務邊由對話補齊；操作者回答 3 個名稱問題後，一個系統的吻合率由 24/26 提高到 26/26。

# 緒論

## 動機

微服務系統常由數十到數百個獨立部署的服務組成，服務之間透過 HTTP、gRPC、訊息佇列與共用資料庫彼此相依。這張相依圖決定了部署順序、變更的影響範圍，以及需要補強的測試，但它通常沒有完整的紀錄：架構圖在發布後容易逐漸過時，程式碼散落在不同的 repo 與語言裡，真正執行的流量又只覆蓋其中一部分。

自動重建相依圖的方法可依來源分成三類。動態方法從分散式追蹤、服務網格或網路流量看到的都是真的發生過的呼叫，但只看得到被觸發的路徑 [@almaruf2022; @tsubouchi2020]。靜態方法讀取原始碼、設定檔與部署描述檔，涵蓋範圍較廣，但受限於語言文法、動態分派與「宣告了卻沒用到」的設定 [@bushong2022; @code2dfd2023; @rahman2019]。文件或 LLM 方法能補充前兩者看不到的關係，但可靠度較低；例如讓 LLM agent 自行讀程式碼重建微服務架構，受測的兩個模型中較好的 GPT-4o 平均 F1 約 0.6 [@liljas2026]。已有研究量化了單一來源的不足：靜態呼叫圖相對於實際執行的 recall 中位數約 0.88 [@sui2020]；一份研究比較了 9 個靜態架構重建（architecture recovery）工具，表現最好的單一工具 F1 為 0.86，依特徵選出最佳組合（共四個工具）後 F1 達 0.91 [@schneider2025]。

這些結果顯示，有必要融合多個來源。但融合之後出現三個新問題，這是本文處理的問題：

1. **等級被抹平。**文件只提過一句的關係，和執行期量測到數千次的關係，在圖上的呈現方式相同，讀者無從判斷哪條可以據以決策。
2. **產出物互相矛盾。**圖、覆蓋率與 LLM 撰寫的報告各自從原始來源推導，報告把資料庫邊寫成「執行期是否觀測：未知」，圖卻畫實線；覆蓋率的分母混進無法量測的項目，使分數虛低或虛高。
3. **有些缺口只有人知道答案。**要觸發某條路徑，需要只有操作者知道的值（例如這個部署的密碼）；文件中的某個名稱指的是哪個服務，規則與 LLM 都只能推測。

## 方法概要與貢獻

DepWeaver 把相依圖的建構拆成「收集、融合、產出、補齊」四個階段，並遵守一條原則：能由程式從證據算出來的，就不交給 LLM；LLM 只處理規則未涵蓋的部分與報告的敘述。它以 ChatOps 的形式運作：操作者在 Discord 輸入一個斜線指令，工具在背景收集證據、產生流量、查詢量測指標，遇到只有人知道的事就在同一個對話中提問，最後貼回一張分層相依圖、覆蓋率與報告。本文的貢獻如下：

1. **三個來源、三級信心等級的融合模型**（第 III-B、III-C 節）：執行期觀測、靜態分析與文件以（來源，目標）為鍵合併；每條邊帶一個有序的信心等級與完整的出處（provenance）清單，合併時等級取最高、出處取聯集。
2. **由同一模型產生、彼此一致的產出物**（第 III-E 節）：列出相依關係的事實段落由程式產生後插入 LLM 撰寫的報告；覆蓋率的分母只計算量測機制能夠量測、且信心等級高於「僅推測」的關係，僅推測的邊的數量寫在分數旁邊；未量測的狀態以三值表示。
3. **對話式缺口補齊：自動手段用盡後才詢問操作者**（第 III-F 節）：流量參數依序從 repo 範例、錯誤回饋、詢問操作者取得；對不上的名稱不丟棄、不模糊比對，而是附排序過的候選請操作者確認，答案以 repo 為單位保存。
4. **在 21 個開源系統與 1 個私有系統上的評估**（第 IV 節）：包含一個純 LLM 直接畫圖的假想敵對照、一份非作者標註的第三方參考邊集合、逐條可複驗的作者參考邊集合、四輪「在一組系統上歸納規則、在下一組未見過的系統上量測轉移」的 hold-out 評估、每條規則在全部系統上的觸發次數、一個真實部署的執行期驗證，以及詢問操作者前後的對照。

## 研究問題

- **RQ0（假想敵）**：不用 DepWeaver，直接讓 LLM 畫相依圖，在不給事實與給事實兩種條件下各能畫得多正確？它的輸出缺什麼？
- **RQ1（靜態層的泛化）**：只用靜態來源，DepWeaver 在沒有調校過的系統上能重建多少相依關係？錯誤來自哪些原因？
- **RQ2（融合執行期觀測）**：加入執行期觀測後，信心等級與覆蓋率如何變化？
- **RQ3（對話式缺口補齊）**：自動手段用盡之後詢問操作者，能補回多少相依關係？需要詢問多少問題？
- **RQ4（產出物的一致性）**：第 III-C、III-E 節的設計規則防止了哪些實際發生過的錯誤？

# 背景與相關研究

## 微服務架構重建

靜態方法方面，Bushong 等人以靜態分析重建整個微服務系統的架構 [@bushong2022]；Code2DFD 在原始碼與設定檔中尋找關鍵字作為證據，產生資料流圖 [@code2dfd2023]；MicroDepGraph 從 docker-compose 中定義的相依關係與 Java 原始碼中的內部 API 呼叫取得相依關係 [@rahman2019]。動態方法從系統已在收集的日誌、追蹤與指標重建執行期視圖 [@almaruf2022]，相關的視覺化研究見 [@gortney2022]；也有方法直接觀察 socket，取得行程之間的網路相依關係 [@tsubouchi2020]。混合方法結合靜態來源與執行期資訊 [@mayer2018; @granchelli2017]，例如 Soldani 等人以 Kubernetes manifest 取得節點、以 Kiali 先前產生的執行期圖取得邊 [@soldani2022]；Mayer 與 Weinreich 的理由是有些關係只在執行期才看得到 [@mayer2018]。

既有的比較研究與文獻回顧顯示：37 個重建工具中 19 個純靜態、10 個純動態、只有 8 個結合兩者 [@bakhtin2023]；依特徵挑選四個靜態工具組合起來，比表現最好的單一工具好 [@schneider2025]；2026 年的文獻回顧把「可靠地融合異質證據」列為未解的問題 [@grinenko2026]。在微服務之外，SARIF 依各來源的相關性與品質，融合相依關係、程式碼文字與目錄結構 [@sarif2023]。本文的差別在於：上述融合方法多半只輸出邊的聯集或分群結果；DepWeaver 保留每條邊由哪個來源、以什麼信心等級支撐，並讓下游產出物依等級決定是否計分。

## 服務相依圖的分析與測試

Ma 等人提出以服務相依圖分析與測試微服務的 GMAT [@ma2018]，之後加入服務與情境之間的邊以支援回歸測試的案例檢索 [@ma2019]，並以版本為單位建構相依圖，在設計期標出設計問題、在執行期偵測異常 [@ma2019b]；MicroViSim 針對 Kubernetes 上的微服務系統，從使用者定義的 YAML 設定產生服務相依圖與負載模擬 [@lin2025]。這些工作以相依圖為輸入；本文處理的是如何從多個來源完整建構相依圖本身，並讓讀者知道每條邊有多可信。

## LLM 與架構重建

Quadri 等人結合從程式碼建構的知識圖譜與 LLM 推理做架構重建 [@quadri2026]。另一方面，讓 LLM agent 自行重建微服務架構時，受測的兩個模型中較好的 GPT-4o 平均 F1 約 0.6 [@liljas2026]；第 IV-B 節在本文的參考邊集合上重做這個對照，並區分「不給檔案」與「給檔案」兩種條件。在生成端，Satyrn 先以分析程式算出事實再交給 LLM 撰寫，報告中正確陳述的比例超過 86%，直接讓 GPT-4 Code Interpreter 撰寫只有 57% [@satyrn2024]；PAL 讓 LLM 寫程式、由直譯器計算答案 [@pal2023]。DepWeaver 採取同樣的分工。

## Human-in-the-Loop 與 ChatOps

Reflexion model 讓工程師定義高階模型與它到原始碼的對應，工具據此算出模型與程式碼一致和不一致之處 [@murphy1995; @murphy2001]；文獻回顧也指出，混合式的重建工具鏈必須允許人工驗證與修正不完整的結果 [@grinenko2026]。部分業界工具讓使用者事後撰寫改名、合併、拆分服務的規則，例如 Datadog 的 service remapping [@datadogremap]；DepWeaver 則在分析進行中、在同一個對話裡提出具體問題。ChatOps 方面，MSABot [@msabot2020] 與 MsdoBot [@msdobot2022] 以聊天機器人支援微服務的開發與維運；ChatOps4Msa 以低程式碼的服務組合建構微服務 ChatOps [@wang2023]，後續版本加入 LLM [@wang2024]；PipelineBot 以 LLM 驅動的 ChatOps 自動化部署管線與監控 [@lai2025]。DepWeaver 建在 ChatOps4Msa 之上，處理的是不同的問題：相依圖的建構，以及在建構中向操作者取得只有人知道的資訊。

## 呈現不確定性

Guo 等人以受控實驗比較在圖的邊上同時呈現主屬性與不確定性的視覺變數 [@guo2015]；partial models 主張模型應能表達建模者的不確定性 [@famelis2012]。部分業界服務圖會區分直接量測與推測的節點，例如 AWS X-Ray 以下游呼叫產生 inferred segment，等該服務自己送出資料時再取代它 [@xray]。DepWeaver 把這個二分擴充成三級，並把等級帶進覆蓋率與報告。

# 方法

## 整體流程

圖 1 是 DepWeaver 的流程。操作者以斜線指令給定 repo、namespace 與入口 URL；工具在背景執行收集管線，每個階段的結果寫入 JSON 檢查點。收集結束後，工具依確定性計算的覆蓋率，決定是否針對缺口再送一輪流量；需要只有人知道的資訊時暫停，並在對話中提問。收集期間會先合併一次，用來計算覆蓋率並找出要詢問的名稱；操作者按下 Generate report 後，再從檢查點建立統一模型（canonical model）並產生所有產出物。

!fig c_arch.png | DepWeaver 的流程。收集與產出以檢查點分開，缺口補齊與補送流量都可以多輪進行 | 3.3

兩個運作模式共用同一條流程。**有叢集**時，收集三個來源以及叢集的部署狀態；**沒有叢集**（namespace 為 none）時，需要叢集的步驟被跳過，只產出由靜態來源與文件構成的草圖（以下稱無叢集模式），並在每個受影響的產出物上註明「未量測」。

## 三個來源

**執行期觀測。**系統執行時，Istio 為每個服務部署一個 proxy（sidecar），服務之間的每一次呼叫都經過它；proxy 記下「誰呼叫了誰、幾次、成功與否」並寫入 Prometheus。DepWeaver 查詢三組計數：HTTP 與 gRPC 請求（istio_requests_total，以接收端回報為準）、服務網格內的 TCP 連線（istio_tcp_connections_opened_total；資料庫這類非 HTTP 的連線只在 TCP 層可見），以及目的地在網格外的 HTTP 與 TCP 流量（外部相依關係）。

**靜態分析。**以 tree-sitter 解析 Java 與 Python 原始碼，用查詢檔比對 HTTP client、Feign、RestTemplate、訊息佇列，以及持久化 annotation 與模型宣告（JPA 的 @Entity 與 Repository、SQLAlchemy、Django ORM）；其他語言則改由 LLM 閱讀程式片段。設定檔（Spring 的 application.yml、Spring Cloud Config 的設定 repo）、部署描述檔（Kubernetes manifest、Docker Compose）與反向代理設定（nginx、Apache）由確定性解析器讀取位址與連線設定。每條抽取到的關係附「檔案：行號」。

**專案文件。**透過 DeepWiki 對 repo 提出五個固定問題（服務職責、同步呼叫、非同步呼叫、外部相依關係、架構流程（入口、請求流程與相依樞紐）），再由 LLM 整理成結構化清單。有些呼叫只在罕見流程中發生，只有文件會提到；但文件也是最可能過時或錯誤的來源。

## 信心等級、出處與合併

**信心等級。**每條邊帶一個有序的三級信心等級（表 I），Graphviz 圖上以點線、虛線、實線呈現（圖 2）；Mermaid 沒有點線，僅推測的邊改以虛線加「?」標示。注意「有使用證據」（documented）指有程式碼或設定佐證，不是「文件提到」。等級與出處分開儲存：一條邊可以有多筆出處（程式碼的某一行、某個指標、文件的某一段），但只有一個等級。

!table 三級信心等級（由低到高）
!widths 1150,1700,2190
| 等級 | 條件 | 範例 |
| 僅推測（inferred） | 只有文件敘述而無設定佐證、只有資料庫連線設定而無持久化程式碼、workload 本身環境變數中的服務位址，或由變數名推得 | 有 datasource URL 但沒有持久化程式碼 |
| 有使用證據（documented） | 有會發出呼叫的程式碼，或設定檔中指向該服務的位址（workload 本身環境變數除外）；Compose 的 depends_on／links；文件中有設定佐證的關係；資料庫連線設定加上持久化程式碼 | Feign client 位於 CustomersServiceClient.java:36 |
| 量測到（observed） | 執行期觀測記錄到這條關係發生過 | istio_requests_total 記錄 ingress 到 api-gateway 共 121 次（petclinic，2026-07-29 執行期邊清單） |
!end

!fig c_levels.png | 三級信心等級在 Graphviz 圖上的呈現（示意）：點線（僅推測）、虛線（有使用證據）、實線（量測到） | 3.2

**合併規則**如演算法 1 所示：以（來源，目標）為鍵，等級取最高、出處取聯集。名稱對齊不在這一步進行：各合併器在呼叫 addEdge 之前先對齊名稱；正規化改名時，再透過同一個函式把邊合併回去。下游產出物只能沿用或降低等級，不能提高。我們選擇離散的三級而不是 0 到 1 的連續值，原因是不需要校準參數或加權公式，且可直接對應三種線型。代價是無法表達「兩個弱來源互相佐證」。

!algo 演算法 1：邊的合併（addEdge）
!code
輸入：模型 G，候選邊 e = (s, t, level, layers, refs, observed, count)；s、t 已由合併器對齊名稱
1: if (s, t) ∉ G.edges then
2:     G.edges[(s, t)] ← e; return
3: end if
4: old ← G.edges[(s, t)]
5: old.level ← max(old.level, e.level)       // inferred < documented < observed
6: old.layers ← old.layers ∪ e.layers         // runtime／code／doc
7: old.refs ← old.refs ∪ e.refs               // 出處取聯集
8: old.observed ← old.observed ∨ e.observed
9: old.count ← max(old.count, e.count)       // 只有量測來源帶次數
!endcode

**資料庫邊的升級條件。**資料庫邊只有連線設定時是「僅推測」；同一個服務同時找到持久化程式碼，才升為「有使用證據」；在服務網格內量測到 TCP 連線後，才升為「量測到」。Spring Boot 以環境變數 SPRING_DATASOURCE_URL 隱式綁定資料來源，程式碼裡沒有讀取這個值的行，因此 DepWeaver 也讀取 Deployment 的 envFrom 與 configMapKeyRef，把注入的位址當成連線設定。

**合併順序。**先以執行期觀測建立骨架；再依序疊加程式碼邊（先對齊節點，對不上的列入未對應清單）、文件邊（不新增服務節點，對不上的服務名稱改為詢問；但可新增資料庫、佇列與外部主機節點）、持久化證據，以及叢集的部署狀態。

## 正規化、未對應的邊與分層

合併後的圖帶有三類雜訊：框架函式庫被當成服務、同一服務的多種拼法（模組目錄名、部署名、文件中的名稱），以及控制平面元件。DepWeaver 以 56 條不含任何專案名稱的抽取與合併規則，加上框架函式庫與控制平面的名單處理；表 II 列出其中幾條代表性的規則；每條規則都是在第 IV-B 節的某個系統上逐條比對差異後歸納出來的，並有對應的單元測試（46 條全表見附錄；它們分四輪歸納，每一輪對未見過的系統轉移了多少，見第 IV-C 節）。

!table 抽取與合併規則（節錄）
!widths 2700,2340
| 規則 | 歸納出此規則的系統 |
| 無叢集時，以 Kubernetes workload 名稱作為服務名稱清單 | ewolff、TeaStore、Online Boutique |
| 模組目錄名與 workload 名稱完全相同，或以「-部署名」結尾時，視為同一服務 | ewolff、TeaStore |
| 佔位符依序查環境變數、屬性、預設值，最後才用變數名（標為僅推測） | piggymetrics、ewolff、robot-shop |
| 單獨的主機名變數（如 DB_HOST）也視為呼叫目標 | piggymetrics、TeaStore、robot-shop |
| 反向代理設定視為入口的邊清單 | ewolff、robot-shop |
| Compose 描述的是服務之間的連線設定，不是某個服務的設定；depends_on 的目標也建立節點 | TeaStore、robot-shop、ecommerce |
| localhost 永遠不是節點；未被引用的常數不算呼叫 | ecommerce |
| workload 本身環境變數中的服務位址畫成僅推測 | Online Boutique、Bank of Anthos、TeaStore |
!end

**未對應的邊交給 LLM。**只有規則未涵蓋的少數程式碼邊會交給 LLM 判斷目標節點。LLM 回傳的來源必須是圖上已存在的服務；目標必須是既有節點，或明確標為外部主機、訊息佇列的新節點；不符合時丟棄，並記成待詢問的名稱（第 III-F 節）。

**分層。**節點依序排成：入口層（gateway，或沒有被任何服務呼叫的服務）、依最長路徑深度排列的業務服務、資料層、外部主機、沒有任何邊的節點。使用最長路徑而非最短路徑，是因為一個既被入口直接呼叫、又在呼叫鏈末端被呼叫的服務應該排在鏈的下方，否則箭頭會往回指。以 Tarjan 演算法找出強連通元件，並把每個元件收縮成單一節點，同一個環的成員因此在同一層。在 train-ticket（51 條邊）上，分層後 51 條邊全部由上往下，沒有向上或同層的邊。

## 讓產出物彼此一致

**一個模型、多個視圖。**每次產出先建立一個統一模型，再由它產生所有產出物：Mermaid 與 Graphviz 圖、覆蓋率、報告的事實段落、問答用的存檔。衍生計算（覆蓋率、分層）只實作一次。模型可序列化；報告發出數天後在 Discord thread 追問時，讀回的是同一份模型，不重新查詢叢集。

**事實段落由程式產生。**報告中列出相依關係的兩節（服務間的同步相依關係、基礎設施與資料層的相依關係）稱為事實段落，由程式從模型產生，措辭固定（例如資料庫邊寫「連線數」而非「請求數」，因為量測到的是前者），以 LLM 報告中第 6 節的標題為錨點插入；LLM 若自己也寫了這兩節，丟棄它的版本；找不到錨點時附在報告最後。「由操作者解析的名稱」一節也由程式產生，固定附在報告最後。其餘章節（收集狀態、元件、非同步通訊、未解項目與信心摘要）由 LLM 依各來源的原始紀錄與圖上的服務名稱撰寫。

**只計可量測關係的覆蓋率分母。**覆蓋率回答「應該被觸發的業務呼叫，有多少已被量測到」。演算法 2 列出分母的條件：量測機制能夠量測（兩端都已部署；業務呼叫不涉及平台的控制平面；資料層的目標不是行程內（in-process）元件），而且信心等級高於「僅推測」。業務呼叫（服務之間的 HTTP 與 gRPC）與資料層（目標為資料庫）分開計算；僅推測的邊的數量寫在分數旁邊；這個數量多於計分的邊時，加上「計分基礎過小」的警告；未覆蓋的邊列成清單，直接成為下一輪流量的目標。

!algo 演算法 2：覆蓋率分母
!code
輸入：模型 G；輸出：計分集合 D_biz、D_db，僅推測邊數 M，未覆蓋集合 U
0: D_biz ← ∅；D_db ← ∅
1: M ← 所有 level = inferred 的邊的數量
2: for each e = (s, t) in G.edges do
3:     if e.level = inferred then continue
4:     if e 為服務間 HTTP／gRPC and deployed(s), deployed(t) and not controlPlane(s, t) then
5:         D_biz ← D_biz ∪ {e}
6:     else if kind(t) = db and deployed(s), deployed(t) and not inProcess(t) then
7:         D_db ← D_db ∪ {e}
8: end for
9: U ← {e ∈ D_biz ∪ D_db : ¬e.observed}
10: 報告 業務 |{e ∈ D_biz : e.observed}| / |D_biz|、資料層同理，附 M 與 U
11: if M > |D_biz| + |D_db| then 附加「計分基礎過小」警告
!endcode

**未量測不是零。**部署狀態以可為 null 的布林值表示，預設「未知」，只有取得叢集資料後才設為否。沒有連上叢集時，報告的覆蓋率寫「not measured」，交給問答 LLM 的字串是 NOT MEASURED，兩處都不寫成 0%。抽取步驟失敗時記錄失敗與原因，不回傳空清單。

## 對話式缺口補齊：最後才詢問操作者

**流量參數。**要讓執行期觀測看到一條呼叫，必須實際觸發它，而有些呼叫需要語意正確的輸入。DepWeaver 依序嘗試四層（表 III）。

!table 流量參數的四層缺口補齊方式
!widths 500,2400,2140
| 層 | 做法 | 範例 |
| 1 | 從 repo 擷取範例請求（負載產生器、端對端測試、OpenAPI 與 Postman 範例） | Bank of Anthos 的 loadgenerator 提供存款欄位 |
| 2 | 把 4xx 回應交回 LLM 修正請求 | 缺欄位、格式錯誤 |
| 3 | 在 Discord 詢問操作者 | 部署的密碼、一個存在的收款帳號 |
| 4 | 操作者也無法提供：標記為無法觸發，不送出請求，在流量報告中列為缺口（仍留在覆蓋率分母中） | — |
!end

第 3 層的問題宣告在 Postman collection 中（空值變數加上說明）。沒有回答的值不綁定，需要它的請求暫不送出並標記為等待，不由 LLM 自行產生值。憑證必須整組詢問（只問帳號不問密碼時，產生器會自行編造密碼）；值不進入 prompt（LLM 只看到變數名）；密碼類欄位以遮罩顯示。答案存入檢查點後，自動針對缺口重送流量。流量產生器的 prompt 另外規定：操作回傳 200 但預期的相依邊沒有出現時，視為被拒絕，因為有些伺服器端渲染的應用拒絕表單時也回傳 200。

**名稱對不上。**需要詢問的名稱有四種來源：文件中的服務名稱經所有對齊規則仍無對應；程式碼殘餘邊的目標或所在模組目錄，經規則與 LLM 都無法對應（短名稱同時符合多個節點時，也是先交給 LLM）；名稱命中函式庫名單，卻有來自程式碼或部署層的邊；兩個服務名稱只差三字以上的前後綴，可能是同一服務。DepWeaver 把這些名稱各記成一個問題，不直接丟棄。候選依三個訊號排序（去除 service、api、client 等通用詞後的包含關係、共用字詞、編輯距離），排序只用於呈現，不做決定。操作者在表單中回答候選編號、任一拼法的服務識別字、new（新節點）或 ignore。答案以確定性規則解析，無法解析時保留問題，不加以猜測。若在表單中填入圖上不存在的節點，視為無法解析並保留問題；保存的舊答案若指向這次圖上不存在的節點，則不建立新節點、略過該名稱，避免系統改名後舊答案憑空產生節點。答案以 repo 為單位保存，不隨檢查點過期而清除，下一次分析同一個 repo 只詢問新出現的名稱；答錯可用斜線指令清除。報告多一節「由操作者解析的名稱」，由程式產生。

**檢查點。**收集、缺口補齊與產出之間以 JSON 檢查點分開：收集結果寫入後暫停，並貼出按鈕（Apply ServiceEntries、Resolve names、Provide values、Generate report、Pause & supplement；暫停後以 Resume 繼續）；操作者回答後，由新的一輪讀回檢查點繼續。一次分析因此可以跨越數小時與多次對話，而不需要長時間持有執行緒。

## 實作

DepWeaver 是 ChatOps4Msa [@wang2024] 的一個 capability（Spring Boot 3.0、Java 17）：步驟宣告在 YAML 管線中，由既有的 orchestrator 依序呼叫；叢集操作透過 Kubernetes MCP server；LLM 使用 OpenAI 相容 API（實驗中為 gpt-4.1-mini，temperature 0）。測試套件共有 280 個測試案例（2026-10-20 執行）：270 個離線通過，9 個因需要外部環境或 API 金鑰而略過，1 個因需要連線至 MCP server 而失敗。原始碼、參考邊集合、15 份分析存檔（含 RQ2 五次執行期分析與 RQ3 五次實際執行的完整模型、覆蓋率訊息與報告）與重現指令將以匿名 artifact 提供。

**結果。**第一，不給事實時，LLM 畫不出正確的圖：零檔案組平均後沒有一個系統的 P 與 R 同時為 1.00。錯誤的型態有三種：套用別的系統的架構（robot-shop 把負載產生器畫成呼叫 6 個服務；TeaStore 把「全部裝在一個 pod」的部署變體畫成呼叫者）、資料庫接錯（Bank of Anthos 把 ledgerwriter 接到 accounts-db）、方向相反（piggymetrics 4 條）。這 7 個系統都公開在 GitHub 上、很可能在訓練資料裡，對私有系統這一組只會更差。第二，給了檔案之後，LLM 與當時的靜態層各有勝負：在靜態層 recall 較低的三個系統上它都較好（TeaStore 以 enum 常數指定目標的業務呼叫邊，LLM 3 次平均 recall 0.67（三次分別是 1.00、1.00、0.00），靜態層 0/7；ecommerce 只寫了 localhost 預設值的控制平面邊，0.81 對 0.28；robot-shop 的業務呼叫邊，1.00 對 0.40），但在 piggymetrics 較差（recall 0.71 對 1.00；3 次都遺漏的 7 條是 gateway 到 4 個服務、notification 與 statistics 到 auth-service 的業務呼叫邊，以及 turbine 到 rabbitmq）。第三，LLM 的輸出有三個分數看不出來的問題，而且都在這 63 次執行中出現：（i）沒有一條邊附出處，無法像 RQ1 那樣逐條查證；（ii）temperature 0 下同一個 prompt 三次結果不同（TeaStore 給檔案組 recall 0.46–1.00），Bank of Anthos 不給名稱組有兩次陷入迴圈，同樣 12 條邊重複輸出 1,417 次直到輸出上限；（iii）名稱由模型決定時，ecommerce 三次都用 Compose 的 container_name（user-service-container）而不是服務名，嚴格對名下 F1 為 0.00、寬鬆對名下為 0.96。分數的差距幾乎全部是名稱問題，而這正是第 III-F 節請操作者確認的問題。第四，事後逐條追查 LLM 贏過靜態層的那三個系統，靜態層輸的地方沒有一處是靜態分析的極限，都是規則缺口（第 IV-C 節的錯誤分析）；假想敵因此同時是找規則缺口的方法。第五，在 5 個 hold-out 系統上重複同一組對照（表 V 下半，45 次呼叫）：零檔案組 F1 只有 0.55，而且知名度越低越差（yas 0.37／0.29）；給檔案組 0.83，低於 7 個歸納用系統的 0.90，因為 yas 的 17 個模組加 Helm 與 Compose 超過預算、三次都只畫到一半（0.58／0.50）。LLM 唯一明顯勝過靜態層的是 hotelReservation（1.00 對 0.71）：它讀得懂 Go 程式碼裡的 Consul 名稱 srv-search 指的是 search，正是第 IV-C 節所說靜態層真正的邊界。第六，在不可能出現在訓練資料裡的私有系統 AICS 上（13 個 repo 的 polyrepo，Python），零檔案組 F1 0.42，而且畫對的幾乎都是從元件清單的名稱就猜得到的邊（服務到自己的資料庫、爬蟲到外部 API），服務到服務的呼叫 P 0.21、R 0.20：這是「不基於事實畫不出來」最直接的證據。給檔案組 0.60，仍低於靜態層的 0.74；三次都漏掉全部 6 條入口路由（Istio VirtualService）。

**RQ0 小結。**假想敵的答案分兩半：不基於事實的 LLM 畫不出正確的圖；基於事實的 LLM 畫得出來，但給的是一張沒有出處、每次不同、名稱未必對得上的圖。DepWeaver 的貢獻因此不在 P 與 R 本身，而在出處、確定性與名稱確認。反過來，LLM 在 enum 常數指定的目標、隱含預設值與尚未支援文法的語言上的表現，說明它適合作為管線中的一個來源（第 III-B 節已對無文法的語言這樣做），其輸出應進入同一套等級與出處框架（第 V-B 節）。

**錯誤分析（修正前）。**每一個非 1.00 的數字都能追溯到具體原因；而且逐條追查後，先前歸因於「靜態分析的極限」的三處，都是規則缺口。ecommerce 遺漏的 17 條全是控制平面：8 條到設定中心，repo 只寫了 optional:configserver:http://localhost:9296，而 cloud-config 的 server.port 正是 9296；9 條到服務註冊中心，repo 內外都沒有任何 eureka.client 設定，只有 Eureka client starter 與 @EnableEurekaClient，位址是 Spring Cloud 的隱含預設 localhost:8761。工具依「localhost 不是節點」丟掉它們，沒有編造，業務呼叫邊 P、R 皆 1.00（原參考邊集合另有 service-discovery → cloud-config 一條，查核時發現 service-discovery 沒有 config client 依賴，已刪除）。piggymetrics 的 8 條錯誤的邊來自同一個原因：共用 application.yml 中的 OAuth、RabbitMQ 與 Eureka 設定被攤到每一個 config client，實際上只有宣告了對應函式庫的服務會使用；其中 monitoring → registry 原本列在參考邊集合中，查核 monitoring 的建置檔沒有 Eureka client 後，改列為錯誤的邊並自參考邊集合刪除。TeaStore 遺漏的 7 條業務呼叫邊，呼叫都以 Service.PERSISTENCE 這類 enum 常數指定目標；但這不是動態分派：常數的字串值 tools.descartes.teastore.persistence 就是模組名，registry 在執行期只決定實例的位址，不決定目標是誰，靜態上可以解析。robot-shop 遺漏的 3 條中，2 條位於尚未支援文法的 Node 與 PHP 程式碼；第 3 條 shipping → cart 是 Java 的 String.format 加上 getenv("CART_ENDPOINT", "cart")，預設值與 Dockerfile 的 ENV 都可以靜態取得，同樣的寫法在 Python 已經會處理。

**規則的來源。**第一輪（修改前）6 個新系統全部有問題：TeaStore 整張圖縮減為 3 個節點（模組名以「.」分隔，被當成 DNS 後綴切掉）；ecommerce 近半的邊來自常數檔（56 條中的 25 條，其中 19 條的常數沒有被引用），另有 Feign contextId 造成的偽節點；piggymetrics 的資料層全部遺漏（設定位於 Config repo）。逐條比對第一輪的差異，歸納出 10 條規則；修改後 Bank of Anthos 既有圖的邊逐條不變，train-ticket 的既有邊全部保留。第三方對照又歸納出 3 條（第 11–13 條）；追查 Online Boutique 為什麼 recall 只有 2/16（約 0.13；參考邊集合後來補上一條，現為 17 條）時，再歸納出第 14 條「workload 本身環境變數中的服務位址畫成僅推測」，使其 recall 提高到 1.00。原本歸因於「語言尚未支援文法」的損失，大半是部署描述檔已經寫明、但工具沒有畫出的宣告。

**第二輪：由錯誤分析補規則，並以 hold-out 量測轉移。**依上述錯誤分析再歸納 9 條（第 15 至 23 條）：localhost:PORT 讀回唯一宣告該 port 的模組、Eureka 的隱含預設、字串值等於模組名的常數、String.format 與 getenv 的預設值，以及在私有系統 AICS 上逼出的 5 條（Deployment 的版本字尾、環境變數依讀取者的範圍解析、函式庫模組不是節點、Python 的宣告不等於使用、共用設定只在有對應函式庫的 client 生效）。修正後 7 個系統 precision 全為 1.00，recall 除 robot-shop（0.90）外皆 1.00（表 VII「修正後」）；Bank of Anthos 與 train-ticket 逐邊不變，第三方吻合率維持 93/95；AICS 由 P 0.42、R 0.10 提高到 0.89、0.63。但這些數字不是 hold-out：規則就是在這些系統上歸納的。為了量測規則對未見過系統的轉移，我們在歸納前另外選定 3 個不在任何歸納集合中的系統（表 IV 的 hold-out B），先寫好參考邊集合並記錄修正前的分數，再以修正後的工具重跑：**三個系統的邊一條都沒有改變**（表 VIII）。第 15 至 23 條描述的是 Spring Cloud 與 Python 的慣例，hold-out B 的錯與漏來自另一批寫法：Compose 只寫鍵名、值在 .env 的環境變數轉發；links 與 external_links 的別名；OpenAPI 中繼資料的 URL 被當成呼叫；Spring Cloud Alibaba 的 server-addr；Envoy 設定；Kotlin。

**第三輪：從 hold-out B 歸納，以 hold-out C 量測。**依 hold-out B 的差異再歸納 12 條（第 24 至 35 條），hold-out B 由 P 0.73、R 0.70 提高到 0.99、0.89（hotelReservation 的 9 條遺漏是 Go 經 Consul 以 srv-* 名稱解析、程式碼與部署描述檔都沒有主機字串，維持不畫）；7 個歸納用系統逐邊不變，train-ticket 少了一條 Swagger termsOfServiceUrl 造成的假外部邊。這一輪的轉移以再另外選定的 2 個系統量測（hold-out C）：yas 由 P 0.58、R 0.58 提高到 0.68、0.81，業務呼叫邊 recall 由 0.11 提高到 0.89，轉移的是 Compose 環境變數轉發那一條規則；run-aspnetcore-microservices 維持 0.00、0.00，因為它暴露的是另一個缺陷：Compose 服務名含「.」（catalog.api）被當成 DNS 後綴截斷。依 hold-out C 再歸納 11 條（第 36 至 46 條）後，hold-out C 為 1.00／1.00 與 0.83／0.96，hold-out B 不變；但這兩個數字已不是 hold-out 數字。

**第四輪：以 hold-out D 量測第三輪，再以機制而非規則補缺口。**第三輪規則以另外選定的 2 個系統量測（hold-out D）：kiali 的 travels（純 Kubernetes、三個 namespace、Istio、Go）P 1.00、R 0.84，第三輪完全轉移；Apache skywalking-showcase P 0.08、R 0.25，暴露四個前面各組沒有的部署形狀：只有 Helm template 的 Kubernetes 描述（整份被 YAML 解析例外吞掉）、Compose 用 image: 而非 build: 指名模組、Compose 的 network aliases，以及真正的目標寫在 command: 裡的 depends_on。這一輪我們刻意不再以「多一種寫法、多一條規則」補缺口，而是補通用機制：以 tree-sitter 文法取代 JavaScript、TypeScript、Go、PHP 的缺口與 Kotlin、C# 的正規表示式（6 個文法在 Linux x86-64 上實測可載入）；把「變數追到字面值」由 Python 專用的實作改為跨語言的單一解析器；以 values.yaml 的預設值渲染 Helm template；把 image 名稱、network aliases 併入既有的別名機制；把 command: 與容器 args 當成位址來源；同名而分屬不同 namespace 的資源保持為不同節點；一個值列出多個位址時逐一建邊；以 Istio VirtualService 與 APISIX 路由檔作為入口來源（共 10 條，第 47 至 56 條；另擴充第 2、5、25、36、42、44 條）。結果：歸納用的 7 個系統 recall 由 0.99 提高到 1.00（robot-shop 的 Node 與 PHP 兩條由文法補上）、precision 維持 1.00；hold-out D 由 0.44／0.67 提高到 0.71／1.00；AICS 由 0.89／0.63 提高到 0.90／0.76；hold-out B、C 逐邊不變；第三方吻合率維持 93/95。為了統一入口邊的標註方式，Online Boutique、Bank of Anthos 與 robot-shop 的參考邊集合各補上一條 istio-ingressgateway 的邊（repo 中都有綁定 Gateway 的 VirtualService），train-ticket 的固定邊數因 gateway 的 38 條入口路由由 120 變為 158，其餘逐邊不變。hotelReservation 的 9 條 Consul srv-* 呼叫現在由 Go 文法讀到，列為待確認的名稱而不畫：註冊中心的名稱對應到哪個服務，是規則不該猜、應交給操作者的問題（第 III-F 節）。

四輪的觀察一致：每一組未見過的系統都可能暴露工具沒學過的寫法，但轉移隨輪次增加（第一輪零轉移、第二輪部分轉移、第三輪在 travels 上完全轉移）；修正後，先前各組的分數都不退步。所以靜態層的 recall 不是靜態分析的極限，而是寫法涵蓋率；對一個未見過的系統，應預期 recall 落在各組 hold-out 修正前的水準（0.25 至 0.84），precision 的損失則集中在少數可以通用修正的錯誤類型（中繼資料 URL、別名、測試 fixture、名稱截斷、不可讀的描述檔）。這些規則是不是只是在窮舉寫法？我們以觸發追蹤量測每條規則在全部系統上實際改變結果的次數（附錄表 X 的「系統數」欄）：56 條中 23 條在 5 個以上的系統觸發、21 條在 2 至 4 個系統觸發（每條都包含至少一個非歸納系統）、11 條只在歸納它的系統觸發（其中多數綁定在語料中只出現一次的技術，如 Envoy、YARP、nginx 變數），1 條從未觸發。也就是說，多數規則描述的是跨系統的慣例，而不是單一系統的特例。

**RQ1 小結。**靜態層的 precision 高：歸納用的 7 個系統修正後 P、R 全為 1.00，第三方吻合率 0.98，hold-out B 修正後 0.99。recall 取決於寫法涵蓋率；四輪 hold-out 顯示新系統會暴露新寫法，但轉移隨輪次增加，而且 56 條規則中多數在多個系統觸發。真正需要執行期觀測或操作者補足的邊界剩下兩類：沒有文法的語言（本文語料中只剩 Rust 與 Ruby），以及目標只以 registry 名稱存在、程式碼與部署描述檔都沒有主機字串的呼叫（hotelReservation 的 9 條 Consul srv-*，靜態層讀得到名稱但不猜對應）。

## RQ3：對話式缺口補齊

**流量參數（Bank of Anthos）。**為了確認第 3 層確實是最後手段，我們關閉第 1 層再執行一次。工具自動觸發到 5/7 後無法繼續推進：剩下兩條（包含 ledgerwriter 到 balancereader）需要一筆實際寫入成功的轉帳，也就是需要這個部署的密碼，以及另一位使用者的收款帳號。工具在 Discord 詢問這兩個值，操作者回答後自動重跑，覆蓋率到 6/7；第一次提供的收款帳號是匯款人自己的帳號，轉帳不會觸發餘額檢查；產生器當時無法重問，只能把該邊宣告為無法觸發。修改 prompt、允許以新的變數名重問之後，換成他人帳號，覆蓋率到 7/7。這次執行（2026-08-26）的依據是當時對話中的覆蓋率訊息與操作者紀錄，分析存檔沒有保留下來；RQ2 的五次執行期分析與 RQ3 的名稱實驗則都有完整存檔（第 III-G 節）。

**名稱（spring-cloud-microservice-examples）。**RQ1 的第三方對照中，這個系統遺漏了 hystrix 到 discovery 與 hystrix 到 gateway 兩條邊。根因是 Compose 的 hystrix 服務（Hystrix dashboard）名稱命中函式庫名單，整個節點在正規化時被刪除。改為「名稱命中函式庫名單、卻有來自程式碼或部署層的邊時提問」之後，工具提出 3 個問題，回答後吻合率由 24/26 提高到 26/26，其他 6 個系統的結果逐條不變。

**在 Discord 上的五次實際執行。**同一個系統在實際的 Discord 環境中執行了五次，每一次都暴露介面或規則的問題並修正：表單只接受候選時，加入完整的詞彙表；同一服務的模組名與部署名重複出現時，改問「是否為同一個」；文件把 repo 名稱當成元件時，直接丟棄不問。從第二次起，圖穩定在 26/26；從第三次起，先前保存的答案開始生效：先前答過的 11 個名稱不再詢問，只詢問新出現的 5 個；第四、五次分別詢問 4 個（其中 2 個由程式錯誤造成）與 2 個。五次中有四次留下完整存檔，報告末節累計套用的操作者答案依序為 8、11、16、20 個，與上述詢問次數相符。我們也觀察到 DeepWiki 每次的用詞不同，因此每次執行都可能零星出現需要詢問的新名稱。

**限制。**五次實際執行與離線驗證的操作者都是作者本人，而且看過參考邊集合。這只顯示機制在實際環境中可以運作，無法說明不熟悉系統的操作者能否答對。

# 討論

## 適用範圍

DepWeaver 的設計假設三件事：證據來自可靠度不同的多個來源；產出物不只一種（圖、數字、報告）；讀者會依據產出物做決策。只有單一來源時（例如純追蹤產生的服務圖），信心分級沒有作用。

## 靜態與執行期的分工

RQ1 與 RQ2 顯示兩層互補而非互相替代：靜態層 precision 高，但 recall 受寫法涵蓋率限制，每組未見過的系統都會暴露新寫法（第 IV-C 節）；只以 registry 名稱解析、沒有任何主機字串的呼叫（hotelReservation 的 9 條）則是它真正的邊界。執行期觀測精確，但只看得到被觸發的路徑，需要產生流量與補齊缺口才能看到更多。piggymetrics 的 8 條錯誤的邊原本被當成另一個方向的互補（靜態層分不出共用設定誰在用，要靠執行期觀測以「未量測到」降級）；第 23 條規則改以建置檔的相依套件判斷後，靜態層就分得出來，執行期觀測退為第二道防線。RQ0 補上第三個方向：給了檔案的 LLM 讀得懂 enum 常數、隱含預設值與尚未支援文法的語言，正好落在規則缺口上，假想敵因此也是找規則缺口的方法；但它的輸出沒有出處、每次不同。合理的分工不是以 LLM 取代規則，而是把 LLM 的抽取結果當成一個來源併入融合模型，等級不高於「有使用證據」、出處記為「LLM 自某檔案推得」，名稱走同一個確認流程。

## 為什麼最後才詢問操作者

詢問操作者有成本：會打斷操作者，而且操作者可能答錯。所以 DepWeaver 只在前面的自動手段失敗時才問，而且問題必須具體到可以用一個值或一個選項回答。唯一的例外是登入憑證：猜錯的密碼不會明顯失敗，因此缺少時直接整組詢問。RQ3 的兩個情境都符合這個條件：密碼與收款帳號屬於部署的事實，在程式碼中找不到；一個名稱指哪個服務，是只有熟悉系統的人知道的對應。

## 效度威脅

**建構效度：**作者參考邊集合由作者整理；我們以第三方資料集、逐條可複驗的出處與第二位標註者降低這個風險；不過第二位標註者是 LLM 而非人類，無法完全取代獨立的人工標註。此外，第三方資料集對「相依關係」的定義與本工具不同，所以只報告吻合率。**內部效度：**RQ3 的流量參數實驗只有當時的對話紀錄，沒有可重讀的分析存檔，5/7、6/7、7/7 三個數字無法在事後由第三方重算；56 條抽取與合併規則都是在受測系統上歸納出來的；表 VII「修正後」與各組 hold-out 修正後的數字都不是 hold-out 結果，只有表 VIII 中粗體的格子是。每輪新增規則後，先前所有系統的節點與邊都逐項重算，沒有退步（邊的變動只有兩處，都是刻意的：train-ticket 少了一條 Swagger 中繼資料造成的假邊，以及第四輪加入入口路由後多出的 38 條 gateway 邊）。第四輪為統一入口邊的標註方式，修改了 3 份歸納用參考邊集合，各補一條入口邊。hold-out 的參考邊集合是在工具執行前寫好的，但同樣由作者整理。另外，RQ3 的操作者是作者本人且熟悉受測系統，可能高估名稱問題的回答正確率。**外部效度：**歸納用的系統以 Java 與 Spring 為主；hold-out 加入了 Go、.NET、Kotlin、Rust 等語言，但這些語言只有薄表面抽取。含缺口補齊的完整執行期驗證只有 Bank of Anthos 一個案例。RQ0 的假想敵在 7 個歸納用系統、5 個 hold-out 系統與 1 個私有系統上各執行一次，但後兩組比較的是第三輪規則後的靜態層；私有系統的結果只報告總分。**RQ0 的對照：**只用一個模型（gpt-4.1-mini）、每格 3 次；元件清單取自參考邊集合，偏袒 LLM；檔案預算由我們決定（但 6 個系統的原始碼全部給完，有截斷的 TeaStore 與 Bank of Anthos 的 recall 已達 0.82 與 1.00，預算不是瓶頸）。**LLM 輸出的變異：**報告與文件整理倚賴 LLM，DeepWiki 的用詞每次不同；事實段落由程式產生而不受影響，LLM 撰寫的章節與文件來源的邊則會受影響。

# 結論與未來工作

本文提出 DepWeaver，以三來源融合、三級信心等級與逐條出處建構微服務相依圖，讓圖、覆蓋率與報告由同一個模型產生而彼此一致，並在自動手段用盡時才於 ChatOps 對話中詢問操作者。在 21 個開源系統與 1 個私有系統上，靜態層對第三方參考邊集合的吻合率為 0.98；四輪「歸納、hold-out」的評估顯示規則的轉移隨輪次增加、多數規則在多個系統觸發，靜態層的 recall 是寫法涵蓋率而非分析的極限；作為假想敵，不給任何檔案的 LLM 直接畫圖 F1 為 0.70，給了 repo 檔案後為 0.90，但沒有出處、三次執行結果不同、自行決定的名稱有 85 個對不上；在一個真實部署（Bank of Anthos）上，融合執行期觀測後業務呼叫與資料層覆蓋率都達到 100%；關閉 repo 範例來源時，最後兩條業務邊由對話補齊。未來工作包括：請不熟悉受測系統的操作者回答名稱問題，量測詢問操作者的實際正確率；在 TeaStore 上完成執行期驗證，量化靜態與執行期的互補；以小型使用者研究檢驗信心分級是否改善讀者的決策；以及以相依圖產生部署順序，並以執行期證據驗證。
