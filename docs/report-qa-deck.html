02 / 10問題

報告的答案都在證據裡，但散在三個地方，而且產完就消失

checkpoint 產完報告就刪

報告貼出後 checkpoint 隨即清掉，事後沒有東西可以查。要問，就得另外留一份「報告的殘留物」。

原本的對話入口是 intent 分類

@bot → 分類成 capability → 按 Perform。一個「動作」按一次合理，一個「問題」按一次不合理。

沒有檢索基礎

repo 內只有關鍵字比對，沒有任何 embedding／向量。老師說的 RAG 要從零建。

讀者會問的是「ledgerwriter 什麼時候叫 balancereader」「哪些邊沒被流量跑到」「改 userservice 會影響誰」，答案分別在報告文字、覆蓋率、圖上。

講稿　三個阻礙都是現況造成的，不是 RAG 本身難。第一個最關鍵：報告產完 checkpoint 就刪，所以第一件事是在刪之前另存一份給問答用的知識庫。

03 / 10使用方式

報告底下自動開一條 thread，在裡面打字就是問

程式碼

1 · Generate report

報告、圖、覆蓋率照常貼出。刪 checkpoint 前，多存一份 archive：報告全文、graph JSON、覆蓋率、證據 notes。

程式碼

2 · 開 thread

bot 貼「💬 Ask DepWeaver about this report」並在下面開 public thread，thread 名 Ask DepWeaver · repo，開頭附幾個用真實節點名組的範例問題。

混合

3 · 問與答

thread 內任何訊息都是問題，不用 @bot、不用按鈕，中英文都行，可以連續追問。答案是一則 Discord 訊息。

使用者改 userservice 會影響誰？
DepWeaver直接呼叫 userservice 的只有 frontend（runtime 觀測到，6 requests）；再往上是 istio-ingressgateway。userservice 自己依賴 accounts-db（8187 TCP 連線，是連線數不是請求數）。所以 userservice 異常時受影響的是登入與首頁載入這條路徑。
講稿　為什麼用 thread 不加一個 capability：問題天然黏在它的報告底下，一個人跑兩個專案就是兩條 thread，各答各的；多輪追問有自然邊界；不用按鈕。

04 / 10① 流程 · 哪些是程式碼、哪些是 LLM

一個問題走六步，只有兩步是 LLM

1判定是不是問答 thread程式碼

thread id 對 archive 索引；不是就走原本流程。

2偵測節點、產事實表程式碼

問句裡的服務名 → 進出邊、證據等級、連線數、傳遞閉包、層級。

3NL → 圖查詢語意路由先、LLM 後

問句向量對每個意圖的例句算相似度，夠像就直接選算子，零額外呼叫；不確定才呼叫 LLM，只准輸出 JSON 計畫，參數經程式驗證。

4執行圖查詢程式碼

15 個算子：impact-of、uncovered、deploy-order…全是查表與 BFS。

5檢索報告段落程式碼 + embedding API

BM25 ∪ embedding cosine → RRF 融合 → 取前 8 段。

6講人話LLM（大）

只拿到上面的 context 與最近 6 輪對話；沒有的就說沒有。

給 LLM 的 context 有權威順序

1圖上的事實（步驟 2、4，程式碼算的）— 最高，段落與它衝突時以它為準 2覆蓋率（程式碼算的） 3檢索到的段落（報告文字是 LLM 寫的，會飄，只拿來補措辭、角色、限制）
講稿　重點一句話：事實由程式碼算，LLM 只負責理解問題和講人話。 這跟上次把報告第 5 節、覆蓋率分母從 LLM 手上拿走是同一條原則。步驟 3 是唯一讓 LLM「想」的地方，但它最壞只能選錯查詢，不可能說錯事實，因為它說的每個節點名都要通過驗證，執行的是程式。

05 / 10① 流程 · 兩層 RAG

老師說的 RAG，這裡做成兩路：文字 RAG 與 GraphRAG

文字 RAG · 步驟 5
  • 切段：報告與證據 notes 依 Markdown 標題切，每段帶標題路徑（report › 4. Sync Candidates › frontend -> userservice），超過 1800 字再拆。
  • BM25：永遠有。連字號 id 整個與拆開都索引（accounts-db → accounts、db）；中文用單字 + bigram，所以中文問句能命中英文報告。
  • Embedding：OpenAI text-embedding-3-small，archive 建立時整批算一次存檔；提問只 embed 問句。失敗就退回純 BM25。
  • 融合：Reciprocal Rank Fusion，不必校準 BM25 分數與 cosine。
GraphRAG · 步驟 2–4
  • 事實表（不經 LLM）：問句點名的節點 → 每條邊一行：a -> b [db]; confidence=documented; runtime observed: YES (8187 TCP connections)。
  • 查詢 DSL：LLM 產 [{"op":"impact-of","args":["userservice"]}]；算子固定 15 個，節點參數必須解析到圖上唯一 id。
  • 同源：uncovered 直接呼叫 CoverageAnalyzer，deploy-order 用畫圖的同一套分層，所以 thread 的答案不可能和頻道貼的覆蓋率、圖矛盾。
使用者哪些邊是程式碼有宣告但流量沒跑到的？
[DEBUG] graph query plan: [uncovered(), unobserved-edges()]
講稿　為什麼不只做向量 RAG：依賴問題多半是圖上的查詢，「誰依賴誰」用向量比對找段落是繞遠路，而且段落是 LLM 寫的報告，有可能飄。所以圖那一路直接查結構，文字那一路補措辭與 file:line。兩路都是「先找證據、再讓模型只依證據回答」，符合 RAG 的定義。

06 / 10② 限制 · 時間

時間上的限制

項目值說明
archive 保留7 天dependency.qa.ttl-days；過期後 thread 提問會回「已過期，請重跑分析」。存檔案，bot 重啟不丟。
對話記憶餵 6 輪 · 存 40 則模型每次看最近 6 輪問答；archive 最多留 40 則，再舊的丟。
一題耗時約 4–12 秒1 次 injection 檢查小呼叫 + 1 次 embedding + 1 次回答大呼叫；規則沒認出問法時多 1 次 planner 小呼叫。HTTP 呼叫設 timeout：連線 15 秒、讀取 180 秒，卡住會回錯誤而不是永遠等。
context 上限段落 24k 字 · 前 8 段事實表另計；gpt-4.1-mini 的 context 夠大，實務上不會撞到。
Discord thread 封存依伺服器設定（預設 24 小時閒置）封存只是收起來，任何人再貼訊息會自動打開，archive 仍在。
每題成本很低embedding 整份 archive 約數萬 token，一次性；每題兩次呼叫，context 約 6–15k token。
講稿　7 天是我定的，考量是「夠準備一次 meeting、又不會拿舊圖回答已經改掉的系統」。可調。timeout 那條是誠實講：不是新功能引入的，但這次順便注意到了。

07 / 10② 限制 · 人數與並行

可以幾個人同時問

情境行為
誰能問thread 裡的任何伺服器成員都能問，不限跑分析的那個人。整條 thread 共用一份對話歷史，像一場共同的討論。
不同 thread 同時問2 題並行（固定 2 條 worker），第 3 題起排隊，不會掉。
同一 thread 同時問依序回答，確保歷史是一段連貫對話、檔案不會被同時寫。
一個人多份報告每份報告一條 thread、一個 archive，互不干擾。
問答 vs 分析各自獨立的執行緒：問問題不會卡住正在跑的分析，分析也不會擋問答。
主頻道 @bot 問同樣的話走舊的 intent 流程，不會當成問答。問答只在 thread。
講稿　「2 條 worker」是刻意保守的：每題背後是兩次 LLM 呼叫，開太多只是把等待從我們這邊搬到 OpenAI 的 rate limit。研究室規模足夠，要放大改一個數字。

08 / 10③ 優缺點 · 優點

優點

不編造

事實由程式碼算，模型只講人話

節點名經驗證、查詢由程式執行、prompt 禁止升級證據等級；問不存在的服務會回「圖上沒有」並列相近 id。

同源

答案和圖、覆蓋率不會互相矛盾

未覆蓋邊用同一個 CoverageAnalyzer，部署順序用同一套分層。上次那個「報告說 unknown、圖畫實線」的病不會在 thread 重演。

可測

確定性的部分有 66 條測試

切段、檢索、節點偵測與角色詞、事實表、語意路由的決策邏輯、15 個算子、archive 往返、Spring 接線；另有對真實模型的校準測試。LLM 只剩措辭那一層要人工驗。

防護

thread 問題也過 prompt-injection 檢查，LLM 呼叫有 timeout

和主頻道同一道閘；prompt 另規定使用者訊息永遠是問題不是指令。卡住會在 180 秒內回錯誤，不再無聲等待。

好用

不用按鈕、不用 @bot、中英皆可、能追問、重啟不丟

問題黏在報告底下，一個人多份報告各自成 thread。

接軌

這就是 8/14 提的 A2 設計落地

NL → 圖查詢 DSL → 確定性執行 → LLM 講結果；deploy-order 就是接到部署生成那條線的點。

講稿　最想強調的是「不編造」和「同源」，這兩點延續上次報告的結論：能用規則算的不問模型。

09 / 10③ 優缺點 · 缺點與界線

缺點與界線（誠實版）

漏答

路由不確定的問法仍靠 LLM 選查詢，選錯就少一塊事實

意圖用例句的向量相似度判定，不是關鍵字窮舉：換個說法、換語言都能對上，加意圖只是加例句。門檻要用真實問句校準；不確定才問模型。不會說錯，但可能漏答。

別名有限

只認「前端／閘道」這類角色詞，其餘同義詞靠 planner 看 id 清單對上

planner 解出的 id 會回饋給事實表，所以「登入服務」對到 userservice 之後也有事實表；但沒有專案專屬的別名表。

證據上限

只能答報告收到的證據（刻意不改）

不存 raw Prometheus、不存 Tier 3 填的值；QPS、版本號、報告沒收的東西答不出，它會直說。要答就得擴充分析階段收什麼，不是讓問答猜。

成本

每題兩到三次 LLM 呼叫加一次 embedding

injection 檢查與回答固定兩次，planner 只在規則沒中時多一次；embedding 依賴 OpenAI，掛了退回純 BM25 但語意檢索變弱。

未真環境驗證

單元測試 66 條全過，真環境還沒跑完整輪

第一次部署撞到 Spring 接線 bug（已修）。下一步就是拿 BoA 跑測試問題集。

講稿　原本列了六條，做掉兩條：thread 訊息現在也過主頻道那個 injection 檢查，HTTP 呼叫也補了 timeout。第一條是設計上的取捨：把「想」限制在選查詢，代價是選錯就漏答。我認為漏答比編造好，這是刻意的；規則層就是把最常見的問法從「想」變成「查表」。

10 / 10驗證與下一步

怎麼驗、接下來做什麼

驗證計畫

  • 用 BoA runtime 跑出報告，照 docs/report-qa-test-questions.md 七組問題逐題問。
  • 每題記三欄：問題／log 裡選的算子／答案對錯。錯分兩種：編造（最嚴重）與漏答。
  • 最重要的一組是「不能編造」：問不存在的服務、問 QPS、問資料庫版本。

下一步

  • 在有額度的機器上跑校準測試，用 33 句 hold-out 問法定門檻；再從真環境 log 的 graph query plan (router|llm) 統計路由命中率。
  • 路由不確定的問法收集起來，補成例句。
  • 把 deploy-order 接到 DeployPlanner，讓「對話」真的走到部署生成。

一句話總結：報告產完不再是終點。讀者可以在它底下追問，而追問的答案來自同一張圖、同一份證據，程式碼負責事實，模型負責把它講清楚。

講稿　結尾回到老師的問題：可用 RAG，我們做了，而且做成兩路。請老師看一下算子清單有沒有想加的問法，那是最容易擴充的地方。
