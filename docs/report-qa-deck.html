阻礙說明
checkpoint 產完報告就刪報告貼出後 checkpoint 隨即清掉，事後沒有東西可查。要問，就得另外留一份「報告的殘留物」。

[碩論] 報告問答 2

使用方式

  • Generate report：報告、圖、覆蓋率照常貼出。刪 checkpoint 前多存一份 archive：報告全文、graph JSON、覆蓋率、證據 notes。
  • 自動開 thread：bot 貼「💬 Ask DepWeaver about this report」並在下面開 public thread，開頭附幾個用真實節點名組的範例問題。
  • 問與答：thread 內任何訊息都是問題，不用 @bot、不用按鈕，中英文都行，可以連續追問。

為什麼用 thread 不加 capability

  • 問題天然黏在它的報告底下，一人多份報告各自成 thread
  • 多輪追問有自然邊界（記最近 6 輪）
  • 不用按鈕

實際對話

使用者：改 userservice 會影響誰？

DepWeaver：直接呼叫 userservice 的只有 frontend（runtime 觀測到，6 requests）；再往上是 istio-ingressgateway。userservice 自己依賴 accounts-db（8187 TCP 連線，是連線數不是請求數）。所以 userservice 異常時受影響的是登入與首頁載入這條路徑。

講稿　示範時直接在 thread 打字就好。範例問題是半寫死：句型固定，服務名取圖上邊數最多的那個。

一個問題走六步，只有兩步是 LLM

步做什麼細節誰做
1判定是不是問答 threadthread id 對 archive 索引；不是就走原本流程程式碼
2偵測節點、產事實表問句裡的服務名 → 進出邊、證據等級、連線數、傳遞閉包、層級程式碼
3NL → 圖查詢語意路由：問句向量對意圖例句算相似度，夠像就選算子（零額外呼叫）；不確定才呼叫 LLM，只准輸出 JSON 計畫，參數經程式驗證路由先、LLM 後
4執行圖查詢15 個算子：impact-of、uncovered、deploy-order…全是查表與 BFS程式碼
5檢索報告段落BM25 ∪ embedding cosine → RRF 融合 → 取前 8 段程式碼＋embedding
6講人話只拿到上面的 context 與最近 6 輪對話；沒有的就說沒有LLM

給 LLM 的 context 有權威順序

  • 1 圖上的事實（步驟 2、4，程式碼算的）— 最高，段落與它衝突時以它為準
  • 2 覆蓋率（程式碼算的）
  • 3 檢索到的段落（報告文字是 LLM 寫的，會飄，只拿來補措辭、角色、限制）
講稿　一句話：事實由程式碼算，LLM 只負責理解問題和講人話。步驟 3 是唯一讓 LLM「想」的地方，但它最壞只能選錯查詢，不可能說錯事實。

老師說的 RAG，做成兩路

文字 RAG　步驟 5

  • 切段：報告與證據 notes 依 Markdown 標題切，每段帶標題路徑，超過 1800 字再拆
  • BM25：永遠有。連字號 id 整個與拆開都索引（accounts-db → accounts、db）；中文用單字＋bigram，中文問句能命中英文報告
  • Embedding：text-embedding-3-small，archive 建立時整批算一次；提問只 embed 問句。失敗退回純 BM25
  • 融合：Reciprocal Rank Fusion，不必校準兩種分數

GraphRAG　步驟 2–4

  • 事實表（不經 LLM）：每條邊一行 a -> b [db]; confidence=documented; runtime observed: YES (8187 TCP connections)
  • 語意路由：14 個意圖，各十來句中英例句；問句先把服務名換成 X／Y 再比對
  • 查詢 DSL：LLM 兜底時只准產 [{"op":"impact-of","args":["userservice"]}]，節點參數必須解析到圖上唯一 id
  • 同源：uncovered 直接呼叫 CoverageAnalyzer，deploy-order 用畫圖的同一套分層，thread 答案不會和頻道貼的覆蓋率、圖矛盾
講稿　為什麼不只做向量 RAG：依賴問題多半是圖上的查詢，用向量找段落是繞遠路，而且段落是 LLM 寫的報告。兩路都是「先找證據、再讓模型只依證據回答」。

事實表怎麼產（程式碼，零 LLM）

① 偵測問句點名的節點

  • 每個節點 id 展開成幾種拼法：accounts-db、accounts db、accountsdb；去 ts- 前綴／-service 後綴的核心名（ts-order-service → order）
  • 邊界只看 ASCII 字母數字，所以「請問frontend依賴誰」抓得到，frontends 不算
  • 角色詞：「前端」→ id 含 frontend 的節點、「閘道／入口」→ gateway 類節點

② 每個點名的節點一份事實表

  • kind、deployed、image／replicas、tier
  • outgoing／incoming 每條邊一行：型別、信心、來源、有無觀測、次數、證據
  • 兩個方向的傳遞閉包（BFS）：它壞了誰受影響、它要跑起來誰得先在
  • 點名兩個節點 → 直接邊，否則最短路徑，否則明講不可達

③ 全圖摘要永遠附上

  • 節點數依 kind、邊數依三層信心、未部署清單、零邊節點、tier 表與反推的啟動順序

實際餵給模型的一段

## Node: userservice
- Kind: service
- Deployed: yes (a matching Deployment is running)
- Tier: 2 (0 = entry; deeper tiers are called later)
- Depends on (outgoing edges): 1

    provenance=code; runtime observed: YES (8187 TCP

語意路由怎麼做

意圖卡：14 張，每張十來句中英例句

dependencies-of、dependents-of、impact-of、startup-needs、path、uncovered、observed-edges、db-users、deploy-order、undeployed、externals、async、mentioned-only、about-report（問報告本身，不查圖也不呼叫 LLM）

流程

  • 啟動後把所有例句 embed 一次，留在記憶體
  • 遮名：問句裡點名的服務換成 X／Y／Z，「frontend 依賴誰」→「X 依賴誰」，和例句同形
  • 問句向量對每句例句算 cosine，每張卡取最高分
  • 有把握的條件：最高分 ≥ 0.58 且領先第二名 ≥ 0.04，或最高分 ≥ 0.85
  • 需要節點的意圖若問句沒點名節點 → 視為沒把握
  • 沒把握 → 交給 LLM planner（它看得到 id 清單）

只剩兩條規則，都是向量會忽略的功能詞

  • 否定：「沒／未／never／not」讓 observed-edges 變 uncovered
  • 方向：「誰依賴／who calls」是 dependents-of、「依賴誰／depend on」是 dependencies-of

走一次：「前端依賴誰？」

步驟結果
偵測節點角色詞「前端」→ frontend
遮名「X 依賴誰？」
embed 後比對dependencies-of 1.00（例句原句）、dependents-of 0.86
方向規則「依賴誰」→ 維持 dependencies-of
信心1.00 ≥ 0.85 → 有把握，不呼叫 LLM
產出查詢dependencies-of(frontend)

為什麼不是 regex

  • regex 是窮舉：第一輪 12 題就有 2 句沒列到
  • 例句會泛化：換句話、換語言都對得上；加意圖是加句子
  • 用的是檢索本來就算好的向量，零額外呼叫（遮名時多一次 embedding，不是 chat）

為什麼要遮名

  • 第一次校準：帶服務名的問句分數普遍低 0.1–0.2，名字本身在向量裡佔了方向；遮掉之後 33 句全對
講稿　老師可能問「這不就是分類器？」——是，是一個不用訓練的分類器：類別的定義就是例句，改例句就改行為，錯了可以看是哪句例句害的。

圖查詢怎麼執行

算子怎麼算
dependencies-of(X)／dependents-of(X)直接篩 source＝X／target＝X 的邊
impact-of(X)／startup-needs(X)沿 incoming／outgoing 做 BFS，依 depth 分組
path(X, Y)兩個方向各做一次 BFS 最短路徑
uncovered直接呼叫 CoverageAnalyzer，和頻道貼的覆蓋率同一個數字；greenfield 明講「未量測」
observed-edges／unobserved-edges／mentioned-only依 runtimeObserved、confidence 篩邊
db-users／externals／async依目標節點 kind（db／external／queue）篩邊
undeployeddeployed＝false 的節點；greenfield 明講「沒查叢集」
deploy-order用畫圖的同一套 tier，最深層先；外部主機排除、註明假設可用

LLM 兜底時的驗證

  • 算子必須在目錄內、參數個數要對
  • 節點參數必須解析到圖上唯一 id（精確 → 不分大小寫 → 寬鬆拼法），對不上整條丟掉
  • 最多 3 條。模型最壞只能「選錯查詢」，不可能「說錯事實」

三個產物同源

圖、覆蓋率、thread 的回答都從同一個 DependencyGraph 物件算出來，所以不可能互相矛盾——上次「報告說 unknown、圖畫實線」的病不會在 thread 重演。

可以幾個人同時問

情境行為
誰能問thread 裡的任何伺服器成員都能問，不限跑分析的那個人；整條 thread 共用一份對話歷史

優點

不編造

  • 事實由程式碼算，模型只講人話；節點名經驗證、查詢由程式執行、prompt 禁止升級證據等級
  • 問不存在的服務會回「圖上沒有」並列相近 id

同源

  • 未覆蓋邊用同一個 CoverageAnalyzer、部署順序用同一套分層，答案不會和圖、覆蓋率矛盾

可測

  • 確定性的部分有 70 條單元測試，另有對真實模型的校準測試；LLM 只剩措辭那一層要人工驗

防護

  • thread 問題也過 prompt-injection 檢查，prompt 規定訊息永遠是問題不是指令
  • LLM 呼叫有 timeout，卡住會回錯誤，不再無聲等待

好用

  • 不用按鈕、不用 @bot、中英皆可、能追問、重啟不丟

接軌

  • 這就是 8/14 提的 A2 設計落地：NL → 圖查詢 → 確定性執行 → LLM 講結果；deploy-order 是接到部署生成那條線的點
講稿　最想強調「不編造」和「同源」，這兩點延續上次報告的結論：能用規則算的不問模型。

缺點與界線

漏答

  • 路由不確定的問法仍靠 LLM 選查詢，選錯就少一塊事實。不會說錯，但可能漏答

別名有限

  • 只認「前端／閘道」這類角色詞，其餘同義詞靠 LLM 看 id 清單對上；planner 解出的 id 會回饋給事實表

證據上限（刻意不改）

  • 只能答報告收到的證據：不存 raw Prometheus、不存 Tier 3 填的值；QPS、版本號答不出，它會直說

成本

  • 每題兩到三次 LLM 呼叫加一次 embedding；embedding 依賴 OpenAI，掛了退回純 BM25

只驗過 greenfield

  • BoA 兩輪、train-ticket（53 節點）一輪，各 12 題零編造；runtime 模式待機器 A 回來

業務流程問題

  • 「訂票流程會經過哪些服務」這種不在圖上，它用「推測」語氣答，節點都存在但語氣是猜的；它有說要驅動流量才準
講稿　第一條是設計取捨：把「想」限制在選查詢，代價是選錯就漏答。我認為漏答比編造好，這是刻意的。
