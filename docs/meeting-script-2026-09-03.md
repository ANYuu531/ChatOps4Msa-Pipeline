## P3 · ① 實際部署資料庫（上）：佈了也畫不出來

**要講的**

老師說測試的時候要實際部署資料庫。我一開始的理解是「去把 DB 佈上去」，結果查下去發現**問題不在那裡**——**就算佈了，圖上還是畫不出來**，因為工具這端本來就缺一條查詢。

原因是這樣：**Istio 只對它看得懂的協定產生 `istio_requests_total`**，也就是 HTTP 和 gRPC。PostgreSQL、MySQL 的連線對 Envoy 來說是一段不透明的 TCP，它解不開，所以**這種相依完全不在那個指標裡**。

那我們原本有沒有查 TCP？有，但用在別的地方——條件寫死了 `destination_app="unknown"`，那是專門查「離開 mesh 的外部呼叫」用的。**換句話說，叢集內部的資料庫，我們一條查詢都沒有。**

結果就是：db 的邊永遠只能是虛線，代表「程式碼宣告了」，不管它在真實世界多麼確實地一直在被使用。**三層信心裡最強的那層，對資料庫是完全空白的。**

**先堵住**

- **「那你之前的圖上為什麼有 db 的邊？」**——有，但都是虛線，來自程式碼抽取（datasource 設定、ORM 標記）。那是「宣告」，不是「觀測」。這次補的是最強的那層證據。
- **「這是這次才發現的嗎？」**——是。上次報告的時候我記的待辦是「service→db 箭頭還沒畫」，那時候以為是畫圖的問題，這次查根因才知道是**資料源本身就沒收**。

## P4 · ① 實際部署資料庫（下）：補一條查詢，順便解決兩個陷阱

**要講的**

修法就是加一條 in-mesh 的 TCP 查詢。四個設計決定我想講清楚：

**第一，用 `reporter="source"`。** 從呼叫端的 sidecar 取數據，而不是被呼叫端。這樣**資料庫 pod 有沒有 sidecar 都量得到**——沒有的話 `destination_workload` 會是 unknown，那就改用 Service 名字認身分。這點很實際：大多數人的資料庫是 StatefulSet，未必會進 mesh。

**第二，那個數字不是流量。** 圖上會看到 8187 這種數字，那是**連線數不是查詢數**。而且它怎麼長取決於 client：Java 的 HikariCP 那種連線池，啟動時建好就幾乎不動；BoA 是每次查詢開新連線，所以兩個禮拜累積到八千多。**但兩種都只證明同一件事：這個服務真的會連那個資料庫。** 而那正是相依圖要回答的問題，不是流量問題。

**第三，順序是有意義的。** 連線池只在服務啟動時建一次，所以資料庫必須**比應用先 Ready**。如果反過來，池子建在一個還沒活的 DB 上，sidecar 沒機會歸因，那條邊就永遠不會出現。這條我寫進 runbook 了。

**第四，覆蓋率分開算。** DB 邊算成獨立的 Data layer 百分比，**不混進業務邊那個比率**。

**先堵住**

- **「為什麼 DB 邊要分開算？加進去不是更完整嗎？」**——因為它們是不同性質的東西。業務邊是「使用者旅程有沒有踩到」，db 連線不是被旅程踩到的，它是服務處理請求時順帶發生的。混在一起會**改變那個百分比的意思**，而且會讓它跟我之前跟老師報告過的數字不能比較。分開算兩個數字，各自的意思都清楚。
- **「8187 這麼大，是不是壓力測試？」**——不是，我們從頭到尾要的是**覆蓋率不是負載**。八千多是兩個禮拜累積的連線數，因為 BoA 每次查詢開新連線。這個數字大小沒有意義，有沒有值才有意義。
- **「petclinic 那邊呢？」**——部署檔寫好了（MySQL，port 名稱要叫 `tcp-mysql` 讓 Istio 正確判定協定），還沒實際跑。那是 Java/JPA 這一側的第二個證據。

## P5 · ⑤ 對話問人（為什麼）：有一種值，自動化永遠拿不到

**要講的**

這是這次的主秀，我想先講**為什麼需要它**。

要讓 Istio 看到深層的邊，就得送出**語意正確**的請求。一個表單欄位填錯，服務在呼叫下游之前就把你擋掉，深層的邊就不會發生。所以「把 payload 弄對」是這條線最難的部分。

我們補 payload 有四層策略，前兩層是全自動的：

- **Tier 1**：去挖專案自己的壓測、e2e 測試、OpenAPI，直接抄它裡面的真實 payload。
- **Tier 2**：把 4xx 的回應內容餵回去給 LLM——那個回應通常會寫「哪個欄位錯了」——讓它自己修。

這兩層之前就做了。但實際跑下來會遇到一種值，**這兩層都拿不到**：

**這個部署的登入密碼、一個真的存在的收款帳號。**

它不在程式碼裡、不在文件裡、不在任何測試檔案裡——**它只在操作的人腦袋裡**。以前工具遇到這種，就直接標成 UNREACHABLE 放棄，那條邊就永遠是虛線。

所以第三層就是：**真的推不出來，才回頭問人**。

**先堵住**

- **「那第四層是什麼？」**——連人都給不了的，例如需要真實的信用卡 token、需要外部系統送 webhook 進來。那種就誠實標 UNREACHABLE，不假裝。
- **「為什麼不一開始就問人？那不是最快？」**——因為那樣就變成人工測試了。這個機制的價值在於它是**最後一層**：前面自動的手段都試過，剩下的才問。下一頁和第七頁我會用實際數據說明它確實沒有濫用。

## P6 · ⑤ 對話問人（怎麼做）：宣告在產物裡，不另外開一套格式

**要講的**

實作上有四個決定，我覺得每一個都值得講：

**第一，ask 就寫在 Postman collection 裡面。** 生成器缺值的時候，宣告一個**空值變數，描述用 `ASK:` 開頭**。這樣做的好處是——產物**仍然是一個合法的 Postman collection**，Newman 或 Postman app 照樣能跑。我們沒有為了這個功能另外發明一套格式。這跟之前 `UNREACHABLE:` 用名稱前綴標記是同一種手法。

**第二，沒答的值刻意不綁定。** 需要那個值的請求會被**扣住**，在報告裡標成 `[WAIT]`，**不會半填就送出去**。這點是刻意的：半填送出去只會拿到一個 4xx，而那個 4xx 會誤導下一輪，讓 LLM 跑去修一個根本沒錯的欄位。

**第三，值從不進 prompt。** 我們只告訴 LLM 這個變數**名字**存在，值是執行器自己代入的。密碼類的值在回顯的時候還會遮罩成點點點。這比「叮嚀模型不要外洩」可靠——它根本看不到。

**第四，表單欄位不是寫死的。** 幾格、叫什麼名字、問什麼問題、給什麼範例，**全都是生成器這一輪自己決定的**。右邊那三格是它實際問我的。換一個專案、甚至同一個專案的不同輪次，問的東西都不一樣。

答完之後**自動 resume**，不用再按任何按鈕；答案存進 checkpoint，所以整個分析**只會問一次**。

**先堵住**

- **「Discord 表單有沒有限制？」**——一次最多五格，這是 Discord 的限制。超過的會留到下一輪再問。
- **「如果人不回答呢？」**——那些邊就維持未覆蓋，報告會誠實標出來。不會卡住，也不會假裝有答案。
- **「答案存在哪？安全嗎？」**——存在 checkpoint 裡，跟這次分析的其他中間結果放在一起，24 小時過期。它不進 prompt、不寫進 log，密碼類的在畫面上也是遮罩的。

## P7 · ⑤ 對話問人（實際跑出來）

**要講的**

這頁是實際的過程，我想照著這條線講一次：

工具全自動跑到 **5/7** 就卡住了。卡住的是這兩條：`frontend → ledgerwriter`、`ledgerwriter → balancereader`。

這兩條有個共同點：**都要求真的成功寫入一筆交易**。因為 ledgerwriter 是在寫入成功之後，才會去問 balancereader「餘額夠不夠」。交易沒成功，這兩條邊就都不會發生。

那要讓交易成功，需要什麼？需要**登入密碼**，還需要**一個別人的帳號**——轉帳給自己不會觸發餘額檢查。這兩個值，再強的靜態分析也生不出來。

於是它問我，我填，它自動重跑 → **6/7**；再一輪 → **7/7**。

**Tier 3 補上的正好是最後兩條邊。** 這句話是這次最好的一句總結。

**先堵住**

- **「這樣不就是靠人工嗎？自動化的意義在哪？」**——我想強調一個實測結果：**第一輪 Tier 1 有效的時候，工具完全沒問我**。它抓到了 loadgenerator 裡面的 payload，所以不需要問。那才是它沒有濫用這個機制的證據。
  我還特別做了**對照實驗**：加一個開關把 Tier 1 關掉，同一個專案、同一段旅程再跑一次——關掉之後它才開始問。**這組對照就是「Tier 1 到底值多少」的量化答案。**
- **「它問的東西合理嗎？會不會亂問？」**——它問的是密碼和一個存在的帳號。這兩個東西**本來就只有操作的人知道**。而且第一次它只問了帳號沒問密碼、自己編了一個——那是個 bug，我修了，第 12 頁會講。

## P8 · ④ 依賴圖分層（原理）

**要講的**

老師說最後產生的依賴圖試著分層。原本是自由佈局，train-ticket 那張 52 條邊基本上是一團麻——**資料是對的，但看不出系統的形狀**。

分層的邏輯有四個決定：

**第一，用最長路徑而不是最短路徑。** 一個服務如果既被入口直接呼叫、又在某條鏈的尾巴被呼叫，它應該排在鏈的**下面**。如果用最短路徑，它會被排到上面去，然後箭頭就往回指了，層次反而讀不出來。

**第二，環是預期的，不是錯誤。** 微服務互相呼叫很常見，train-ticket 就有。我用 Tarjan 演算法把強連通分量縮成一個點再分層，**同一個環的成員落在同一層**——因為環裡面本來就沒有「誰先誰後」，硬要排出順序反而是騙人的。

**第三，沒有 gateway 也要能分。** greenfield 模式（純靜態、沒有叢集）根本沒有 ingress 這個節點。這時候就改用「沒有人呼叫它」的服務當入口，BoA 就是 frontend。

**第四個是驗證**：train-ticket 那張圖分層之後，**51 條邊 100% 由上往下**，0 條向上、0 條同層穿越。這是「層次是真的、不是排版錯覺」的量化證據。

**先堵住**

- **「這個分層有什麼用，只是好看嗎？」**——兩個用途。第一是可讀性，這是老師連續兩次提到的。第二個更實際：**這個分層結果就是部署順序的雛形**。依賴圖做拓樸排序就能算出「哪些服務要先部署」，那是後面 DeployPlanner 那條線的輸入。
- **「52 條邊為什麼講 51 條？」**——有一條在正規化階段被合併掉了，我算的是實際畫出來的那 51 條。

## P9 · ④ 依賴圖分層（結果）

**要講的**

這頁是 BoA 分層後的實際結果，六層，由上往下：ingress、frontend、四個後端服務、balancereader、兩個資料庫，最後一層是「無相依」。

我想特別講**最後那層**，它是個副產品但很有價值：

`no dependencies found` 裝的是**完全沒有任何邊的節點**。它們不是入口，是**抽取沒抽到東西**。train-ticket 有 19 個節點落在這一層——裡面有 `bin`、`json2shiviz` 這種本來就不是服務的東西，但也有 `ts-gateway-service`，**那是真的漏抽了**。

所以這一層等於是**圖自己指出來的缺口清單**，告訴我下一個該補的抽取目標是什麼。

右邊那張是順帶修掉的一個問題：image 的 sha256 digest，71 個字元，整串塞進了節點標籤，把圖拉到 **5051px 寬**。分層明明是對的，但沒有人看得出來——因為節點的寬度等於它最長那一行，一個囉嗦的 label 就撐開整個層。

**先堵住**

- **「digest 為什麼會跑進去？」**——原本的邏輯是取 image 名稱最後一個斜線之後的部分，但 digest 裡沒有斜線，所以整串留下來了。修法是先砍 digest，而且當 image 名字跟節點名字重複時（frontend 跑 frontend:v0.6.10）只留版本號，因為名字上一行已經有了。
- **「那 19 個節點怎麼辦？」**——非服務的那些（bin、測試工具）本來就該在那；`ts-gateway-service` 是真缺口，列在下一步。

## P10 · ② 取名字

**要講的**

工具定名 **DepWeaver**，中文全名是「**基於多源證據融合與對話式補值的微服務相依圖自動建構方法**」。

名字拆開看，每一段都對應一個實際的設計：

- **多源證據融合**：runtime（Istio 觀測）、code（tree-sitter 抽取）、doc（文件）三種證據**織成同一張圖**，不是三選一。這就是 Weaver 的由來。
- **對話式補值**：Tier 3，也就是這次的新貢獻。
- **自動建構**：全程自動，人只在真的推不出來的時候補一個值。

我想強調的是名字的**用法**：它不只寫在文件裡，而是**蓋在每一個產出物上**——Graphviz PNG 的標題列、`.mmd` 檔案的檔頭、Discord 上的報告和覆蓋率標題。定義在程式碼裡的一個常數，所以不會有兩處不一致。

這樣做的理由很實際：**圖貼進投影片或論文之後，還認得出來源。**

**先堵住**

- **「為什麼是 Weaver 不是別的？」**——因為核心設計就是「織」：三種證據合成一張圖。如果只有 runtime 就是監控工具，只有 code 就是靜態分析工具，這套的價值在於把它們疊起來，而且**標明每條邊的證據強度**。
- **「論文裡怎麼用？」**——照慣例全名先出現一次，之後用簡稱：「本研究提出基於多源證據融合與對話式補值的微服務相依圖自動建構方法（以下簡稱 DepWeaver）……」圖名則是「圖一　DepWeaver 端到端流程總覽」。

## P11 · 七步概覽

**要講的**

進圖之前先用這一頁把骨架講一次：**七個步驟，只有三步碰到 AI**——文件分析、驅動流量的「產情境」那半、以及產出的報告文字。其餘全是我們自己寫的確定性程式碼。

## P12 · 圖一　端到端流程總覽（Fig.1　Pipeline Overview）

> 這一頁和下一頁是**老師說要改成 Draw.io 的那兩張圖**。圖名固定成中英對照，以後討論直接叫「圖一」「圖二」。

**開場一句**

這就是那張流程圖，Draw.io 畫的。我想先講**怎麼看它**，再走一次流程。

**先講顏色——這是全圖最重要的編碼**

右上角圖例三格：

- **藍色〔程式碼〕**：我們自己寫的確定性邏輯。
- **紫色〔AI〕**：用 LLM，因為那一步需要讀或寫自然語言。
- **藍紫漸層〔混合〕**：情境由 AI 產生、但執行的是我們的程式碼。

**整張圖只有兩格是紫的、一格是漸層。** 所以「這整套是不是就靠一個 LLM」這個問題，看顏色就有答案。

**然後走主流程，從上到下**

- **使用者在 Discord 下指令**——給四個參數：repo、namespace、entry_url、auth_hint。
- **NLP 解析〔AI〕**——把一句自然語言變成 capability 加參數。這裡用 AI 是應該的，它就是在讀自然語言。
- **① ~ ③ 三來源抽取**（虛線框起來的那三格，代表它們是**平行**的）：
  - **① 靜態抽取〔程式碼〕**：clone 原始碼，用 tree-sitter 解析出呼叫、DB 使用、endpoint、服務根。純解析，不是 AI。
  - **② 文件分析〔AI〕**：問 DeepWiki 五題——職責、同步、非同步、外部、入口。要讀自然語言，所以用 AI。
  - **③ 叢集 / 路由〔程式碼〕**：kubectl 抓 Service、Deployment、Pod，還有 Istio 的 VirtualService。
  - 框上那行小字很重要：**各自存進 checkpoint**，所以 resume 的時候這些貴的步驟不會重跑。
- **④ 驅動流量〔混合〕**——整條線的關鍵。框裡第一行寫著「Istio 是被動的：一條邊只有在請求真的跨過去時才會被記錄」，那是這一步存在的理由。情境是 LLM 產的（要懂 API 語意），但**執行器是我們自己寫的**。補 payload 的三層也標在這裡。
- **⑤ 量測〔程式碼〕**——查 Prometheus。這格有三行，中間那行是**這次新加的**：`istio_tcp_connections_opened_total → DB 邊`，後面括號寫「非 HTTP，只在 TCP 層看得到」。
- **checkpoint（橘色菱形）**——暫停，貼按鈕。菱形代表這是**決策點**，等使用者。
- **⑥ 建圖合併〔程式碼〕**——細節在圖二。
- **⑦ 產出**——圖和覆蓋率是程式碼算的，文字報告是 AI 寫的。
- 最後**貼回 Discord**。

**再講右邊三個分支**——那是 checkpoint 之後，使用者可以按的三顆按鈕：

- **Provide values（Tier 3 · 對話問人）**——這次新加的。框裡寫「只有在真的推不出來時才出現這顆按鈕」。
- **Apply ServiceEntries**——唯一會改叢集的動作，只在點擊後執行。
- **resume：覆蓋率導向迴圈**——用確定性覆蓋率算出「還沒被觀測到的邊」當目標。

**最後兩個細節**

- **橘色那條線**寫「再導一輪（可多輪）」，從 resume 繞回到第 ④ 步。那就是迭代迴圈——**只針對缺的邊再導一輪**，不是整條重跑。
- **左下角的圓柱**是 checkpoint 的持久化儲存，在 host volume 上，**重啟不丟**。虛線箭頭表示「讀回、不重跑」。
- **右邊黃色便條**講 greenfield：沒給 namespace 的話，③④⑤ 整段會被 gate 掉，只剩 ①②⑥⑦ 純靜態出圖。

**先堵住**

- **「為什麼 NLP 那步要用 AI？不能用關鍵字比對嗎？」**——可以，但那樣使用者就得記指令格式。用 LLM 是為了讓他能用自己的話講。而且那一步就算解析錯，使用者馬上看得出來（參數不對），不會污染後面的圖。
- **「三來源真的是平行的嗎？」**——邏輯上平行、實作上依序跑。虛線框是要表達「它們互相獨立、各存各的 checkpoint」，不是在講執行緒。

## P13 · 圖二　證據合併鏈（Fig.2　Evidence Merge Chain）

**開場一句**

這張是上一張第 ⑥ 步「建圖合併」的細節。標題那行就是全圖的觀念：**由強到弱一層層疊**。

**先講那個觀念**

證據有強弱之分：**runtime 真的觀測到（實線）＞ code/doc 宣告（虛線）＞ 只宣告、沒有使用證據（點線）**。合併的順序就是照這個強弱來的——先鋪最強的，後面的疊上去。

右上角那格圖例把三層寫清楚了，最後一行特別重要：**addEdge 取 max，疊上去只會變強，不會變弱**。所以先後順序不會讓證據被稀釋。

**左邊六個圓柱是輸入**——都是 checkpoint 裡存的原始證據：traffic_raw、egress_raw、tcp_raw、code_edges、merged_notes、k8s_raw。它們各自餵給右邊對應的步驟。

**中間九步，從上到下**

1. **runtime 骨架**——先用 Istio 觀測到的邊當骨架，因為那是最強的證據。之後所有東西疊在這上面。
2. **併 egress 邊**——已經被 ServiceEntry 歸因的外部 host 併進來，例如 config-server → github.com。
3. **併 in-mesh TCP 邊（DB）**——**這是這次新加的**。框裡寫得很清楚：Istio 只對 HTTP/gRPC 產 requests 指標，資料庫連線是不透明 TCP，只在這裡看得到，所以**原本只能是虛線的 db 邊，升級成實線**。
4. **併程式碼邊**——runtime 也看到就合併；只有 code 宣告就加一條虛線。host 是變數的時候用 env-address 或路徑段解出目標，**那是確定性的、不是 AI**。
5. **併文件邊、提升「真用」DB**——文件只 enrich、不 invent。服務有 ORM 標記就把 db 邊從「只宣告」升級成「真的有用」。
6. **標部署狀態**——宣告了但叢集其實沒在跑的，畫成灰底紅框虛線。
7. **正規化**——清掉框架 lib 造成的幽靈節點、合併別名。
8. **LLM 補殘餘〔AI〕**——**整張圖只有這一格是紫的**。只有確定性都解不掉的殘餘才丟給 LLM 猜，而且嚴格驗證它給的 source 和 target 真的存在。框裡最後一句是這條線的原則：**能用規則解的絕不丟給 AI，圖才可重現、不亂猜**。
9. **分層**——就是老師說的那點，入口 → 依呼叫深度 → 資料層 → 外部 → 無相依。

**中間偏下的綠色框**是 `DependencyGraph`，也就是最終的資料模型。**右邊三個輸出**都從它來：Mermaid、Graphviz PNG、覆蓋率。這一點很關鍵——**三個產物同源**，所以它們不可能互相矛盾。

**右邊黃色便條**回答一個常見疑問：**greenfield 為什麼全是虛線**？因為沒有第 1~3 步的 runtime 骨架，所有邊都落在第 4、5 步的 code/doc，自然全是虛線。**這是誠實的**：它老實說「這些是宣告出來的，還沒被 runtime 驗證過」。

**接著講界線（這頁下方那段小字）**

這一點我想先講清楚一條**界線**，免得誤會成「整套繪圖換掉了」：

**只有說明用的流程圖改成 Draw.io 手畫**——就是 Fig.1 端到端流程總覽和 Fig.2 證據合併鏈。這兩張是給人看的文件圖，本來就該手工排版。

**工具自動產出的依賴圖維持 Graphviz 和 Mermaid**。那是程式即時生成的，一次可能 50 個節點、每次執行結果都不同——不可能也不該用 Draw.io 畫。

Fig.1 上我做了一件事想特別說：**每個節點都標了是〔程式碼〕還是〔AI〕**，兩種顏色。這樣「這整套是不是就靠一個 LLM」這個問題，**答案直接在圖裡**——骨幹是確定性程式碼，AI 只用在三個地方：讀文件、產流量情境、補確定性解不掉的殘餘。

**先堵住**

- **「Draw.io 的檔案在哪、怎麼改？」**——`docs/diagrams/` 下面兩個 `.drawio` 檔，用 VS Code 的 Draw.io 擴充、桌面版、或 app.diagrams.net 都能開。
- **「有 PNG 嗎？」**——還沒有。匯出需要 Draw.io 本身，開發機上沒裝。匯出步驟寫在 `docs/diagrams/README.md`，這件事列在下一步。
- **「為什麼不全部統一用一種？」**——因為兩者的性質不同。一個是人手排版的說明圖，一個是程式輸出的資料視覺化。硬要統一只會兩邊都做不好。

**先堵住**

- **「九步為什麼只有一步用 AI？其他不能也用嗎？」**——可以，但沒必要，而且會更差。前七步都是規則明確的合併與清理，用程式碼寫出來**每次結果都一樣**；交給 LLM 只會讓圖變得不可重現。第 8 步之所以留給 AI，是因為那裡剩下的東西**規則真的解不掉**（host 是變數、又沒有範本可對）。

## P14 · ★ 七個 bug（上）

**要講的**

接下來是我覺得這次最有價值的部分。這七個 bug **全都是 BoA 這種真系統才逼得出來的**，在單元測試裡永遠不會出現。

前四個是關於**流量驅動**：

**第一，半組憑證。** 工具問了我 username，卻**自己編了密碼**。結果登入回 200——因為 redirect 回登入頁會被自動跟隨，看起來跟成功一模一樣——然後每一個需要登入的步驟都 401。修法：憑證必須整組問，不准編造密碼或 token。這是 ASK 的唯一例外，不是最後手段，因為猜錯的密碼**不會明顯失敗**。

**第二，200 不等於成功。** 這是上面那個陷阱的通則。SSR 應用拒絕表單的時候會 redirect 回原頁，失敗和成功長得一樣。修法：如果一個動作回 200，但它應該造成的那條邊沒有出現，就當它被拒絕了。

**第三，值錯了改不掉。** 我第一次填的收款帳號是自己的帳號，而轉給自己不會觸發餘額檢查。但 prompt 裡寫死了「已提供的值不准再問」，所以生成器沒辦法說「你給的帳號不對」，只好把那條邊宣告成 UNREACHABLE。修法：當值明顯是問題來源時，可以用**新的變數名**重新問，並說明為什麼舊值不行。

**第四，內部邊被當成不可觸發。** 它的理由是「這是 service 之間的內部邊，外部請求無法觸發」。但**幾乎所有深層邊都是內部的**，那正是它「深」的原因。它不是靠直接呼叫觸發，是靠**逼得呼叫方需要被呼叫方的那個業務動作**。修法：要先想出是哪個動作，並確認那個動作真的成功了，才准放棄。

**先堵住**

- **「這些是 prompt 改一改就好的東西嗎？」**——前四個是，而且改的都是**通用規則**不是 BoA 專用的判斷。但後面三個不是，下一頁講。

## P15 · ★ 七個 bug（下）

**要講的**

後三個都是關於**「數字和圖說了不一樣的話」**，性質更嚴重：

**第五，報告和圖互相矛盾。** 報告裡寫 db 邊 `Runtime observed: Unknown`，可是旁邊的圖畫的是實線，覆蓋率還說 5/5。**三個產物出自同一輪，互相打架**——讀的人完全不知道該信哪個。

**第六，文件幻覺污染覆蓋率。** 同一個叢集、同一批流量，隔一輪 **7/7 變成 7/10**。系統沒變、流量沒變，只是 DeepWiki 這一輪多講了幾句 `userservice → ledgerwriter`——**那條在程式碼裡根本不存在**。

**第七，程序內的快取被當成資料庫。** `balancereader → in-memory-cache`，那是服務**程序裡面**的 Guava cache，沒有網路端點，**永遠不可能被觀測到**。它把資料層卡在 5/6，而且被列在「可能是 pod 啟動順序問題」底下——**給了一個做不到的補救建議**。

第七個的修法是既有原則的延伸：CoverageAnalyzer 本來就會排除「不可能被驅動的邊」，例如沒有部署的節點——只是漏了「程序內」這一類。

**先堵住**

- **「第七個你怎麼知道它是程序內的？」**——老實說，**現在是靠名字判斷的**（名字裡有 in-memory、embedded 這些字）。這比較弱，我在程式碼裡註明了。**真正穩健的做法是看它有沒有對應的 Kubernetes Service**——真的資料庫有網路身分，程序內的沒有。那需要把 Service 清單存成結構化的資料，現在還沒有，是下一步。
- **「第六個那三條假的邊，圖上還在嗎？」**——在，但畫成**點線**，代表「只被提到過、沒有使用證據」。**圖照畫，只是不計分。** 這是刻意的：把它擦掉等於幫文件圓謊，留著並標示最弱等級才誠實。

## P16 · ★ 第 5、6 個是同一個病

**要講的**

這頁是我這次最想講的一個觀點。

第五個和第六個看起來無關，其實是**同一個病：我們把確定性的東西，交給了非確定性的元件。**

**先看報告那個。** 第 5 節的內容——誰依賴哪個資料庫、觀測到沒有、信心多高——**graph 裡面全都有**，而且圖也畫對了。我卻請一個看不到那張表的模型去複述它。那只是多給它一次講錯的機會。

我改了兩次 prompt，它每次換一種錯法：第一次說 Unknown，第二次乾脆去列 Micrometer、Log4j2、Cloud SQL——那些是**函式庫和雲端替代方案**，根本不是這個部署的相依。

所以**最後的解法不是再改 prompt，是把那一節從 LLM 手上拿走**：改由程式碼從 graph 直接產生。而且順便讓報告和圖**共用同一個 graph 物件**——以前它們是各自從 checkpoint 推導的，兩條路本來就可能給出不同答案。現在它們不可能再描述不同的圖。

**再看覆蓋率那個。** 我們一直宣稱覆蓋率是「確定性算出來的」，但它的**分母**有一部分來自 LLM 讀文件的產物。**一個會隨著 wiki 寫得多不多而變動的分數，量的就不是流量。**

修法：只有「有證據是真的呼叫」的邊才進分母；只被提到過的照樣畫在圖上，但不計分。

**一句話總結**：「確定性優先、LLM 只補殘餘」不是口號，是**有邊界的**。報告和覆蓋率分母，是整條線上最後兩個還沒套用這條原則的地方——結果它們就是唯二會飄的產物。

**先堵住**

- **「那報告裡還有哪些是 LLM 寫的？會不會也不可靠？」**——服務職責、收集狀態、矛盾點、建議這些**需要語言**的部分還是 LLM 寫的，那是它擅長的。被拿走的只有「純粹是事實、而且我們已經算出來」的那一節。分界線很清楚：**能用規則算出來的，就不該問模型。**
- **「權威順序是什麼？」**——覆蓋率 > 圖 > 報告文字。前兩個是確定性程式碼算的，最後一個是 LLM 寫的。這不是幫報告找藉口，是這套設計本來的立場。

## P17 · ★ 可能被問：這些修正只對這個 repo 有效嗎？

**要講的**

這題我想**自己先答**，因為答案有兩半，而且我不想假裝它全部通用。

**通用的那半**：憑證整組問、200 不等於成功、內部邊不是放棄的理由、值可以重問、報告第 5 節由 graph 產生、程序內快取不計分、digest 截斷——**這些都是規則層面，沒有任何專案知識**，換到 sock-shop 或 train-ticket 同樣成立。

**不通用的兩處，我不會說它們通用：**

**第一，library 名單是寫死的。** 這次為了清掉 `lettuce`（Redis 的 client library 被誤當成服務），我在名單裡加了一批。它對 Java 和 Python 生態有效，換成 Go 或 Rust 就漏。**這正是老師之前指出的「三份寫死名單要設定檔化」那個技術債，我等於把其中一份加長了。**

**第二，排除「只被提到過」的邊，對抽取品質差的專案會虛高。** BoA 是 Java 加 Python，有 tree-sitter grammar，真實的邊都抽在 code 層，被排除的只有文件幻覺。但**沒有 grammar 的語言**——Go、Rust——抽取會退回 LLM 閱讀，真實的邊可能**全部落在最弱那層**，分母就縮到剩一兩條，然後印出一個 100%，其實什麼都沒抽到。

第二點我當場修了，做法**不是取消排除，是不准靜默**：一律報出「Not scored: N 條」，而且**未計分的邊比計分的還多時直接標警告**。

這跟這條線一貫的作法是同一個標準——圖會說「declared, not verified」而不是畫一條有自信的線，greenfield 報告會說「N/A，沒有叢集」而不是編造 pod 數，**那覆蓋率也該說出它沒在算什麼**。

**先堵住**

- **「那你怎麼知道還有沒有別的不通用的地方？」**——不知道，只能靠再測。這也是為什麼我認為「換一個專案再跑」比「同一個專案跑得更順」有價值。BoA 逼出七個 bug，下一個專案——Go 或 Node 的——大概率會再逼出一批，那是預期中的。
- **「那 library 名單什麼時候修？」**——列在下一步第二項。

## 附錄 · 沒放進投影片但可能被問到的

| 問題 | 答案 |
|---|---|
| 為什麼 checkpoint 要存？ | 收集階段很貴（clone repo、DeepWiki 問五題），暫停補流量再回來時不該重跑。按「Generate report」會清掉 checkpoint，所以要迭代得按「Pause & supplement」。 |
| Tier 1 的開關怎麼開？ | 一個環境變數 `DEPENDENCY_EXAMPLE_REQUESTS_ENABLED=false`。它不是為了 demo 硬湊的，是**對照實驗的另一組**——同專案同旅程，量「repo 自己的範例請求」值多少。 |
| greenfield 是什麼？ | 不給 namespace 就走純靜態：不碰叢集、零 port，只跑程式碼和文件。圖全是虛線，誠實表示「還沒被 runtime 驗證」。適用還沒部署的專案。 |
| 三層信心怎麼分？ | 實線＝runtime 觀測到；虛線＝code/doc 有使用證據；點線＝只宣告、未證實。合併時取最強的那層，疊上去只會變強不會變弱。 |
| 為什麼 BoA 的 db 顯示「Deployed: 未確定」？ | 因為它是 StatefulSet，而部署狀態的判定只讀 Deployment。這是誠實的「未確定」，不是「沒部署」。 |
| 一次分析要跑多久？ | 收集階段數分鐘（clone + DeepWiki + 導流量 + 等 Prometheus scrape）。導完流量會等一個 scrape 週期再查，否則最深的邊還沒落地就被快照漏掉。 |
| 為什麼不用現成的 APM / 追蹤工具？ | 那些能看 runtime，但看不到「程式碼宣告了卻沒跑到」的邊，也看不到還沒部署的專案。這套的價值在把三種證據疊起來，並標明每條邊的證據強度。 |
