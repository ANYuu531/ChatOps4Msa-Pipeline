## P3 · ① 實際部署資料庫 —— 根因比我原本想的更具體

您說要實際部署資料庫，我一開始以為只是「去把 DB 佈上去」。但查下去發現**就算佈了也畫不出來**，因為工具那邊有個更根本的缺口：

**Istio 只對它看得懂的協定（HTTP/gRPC）產 `istio_requests_total`。** 資料庫連線是不透明的 TCP，完全不在那個指標裡。

而我們原本**只有一條** TCP 查詢，條件寫死 `destination_app="unknown"`——那是專門查「離開 mesh 的外部呼叫」用的。**叢集內的資料庫，一條查詢都沒有。** 所以 db 邊永遠只能是虛線（程式碼宣告），不管它多真實。

修法：加一條 in-mesh 的 TCP 查詢，用 `reporter="source"`（呼叫端的 sidecar 報的），這樣**資料庫 pod 有沒有 sidecar 都量得到**——沒有的話 `destination_workload` 是 unknown，改用 Service 名認身分。

### 【可能被問】「那個數字 8187 是什麼？流量嗎？」

**是連線數，不是查詢數，絕對不能當流量讀。** 而且怎麼長取決於 client：Java 的 HikariCP 那種連線池在啟動時建好就幾乎不動；BoA 是每次查詢開新連線，所以兩週累積到 8000 多。**兩種都只證明一件事：這個服務真的會連那個資料庫。** 那正是相依圖要的答案。

### 【可能被問】「加了 DB 邊，業務覆蓋率怎麼沒變？」

刻意的。DB 邊算成**獨立的 Data layer 百分比**，不混進業務邊那個比率。因為 db 連線不是被使用者旅程「踩到」的（它是服務處理請求時順帶發生的），混在一起會改變那個數字的意思，也會讓它跟我之前跟您報告過的數字不能比。

## P4 · ⑤ 對話問人（Tier 3）—— 這次的主秀

### 先講為什麼需要

驅動流量要打到**深層的邊**，就得送出語意正確的請求。我們原本有兩層自動的辦法：
- **Tier 1**：去挖專案自己的壓測 / e2e / OpenAPI，抄它的真實 payload
- **Tier 2**：把 4xx 的回應內容餵回去，讓 LLM 自己修欄位

但有一種值，這兩層都拿不到——**這個部署的登入密碼、一個真的存在的收款帳號**。它不在程式碼裡、不在文件裡，只在操作的人腦袋裡。以前工具遇到這種就直接標 UNREACHABLE 放棄。

### 怎麼做

- 生成器缺值時，在 Postman collection 裡宣告一個**空值變數 + `ASK:` 描述**。這樣產物**仍然是合法的 Postman collection**（和 `UNREACHABLE:` 用同一種手法）。
- **沒答的值刻意不綁定**：需要它的請求被扣住標 `[WAIT]`，**不會半填就送出**——半填只會拿到一個誤導人的 4xx。
- Discord 跳出**表單**收值 → 存進 checkpoint → **自動重跑**，不用再按任何按鈕。
- 表單的欄位**不是寫死的**：幾格、叫什麼名字、問什麼，全都是生成器這輪自己決定的。換個專案問的就不一樣。
- 值**從不進 prompt**（只給 LLM 變數名），密碼類的值回顯時**遮罩**。

### 實際跑出來的樣子（demo）

工具自動跑到 **5/7** 就卡住了。卡住的兩條邊都需要「真的成功寫入一筆交易」。於是它問我：

```
• username — a valid username for login
• password — the password for the username
• account_num — an existing account number to send payment to
```

我填 `testuser` / `bankofanthos` / `1033623433`，它自動重跑 → **6/7** → 再一輪 → **7/7**。

【口頭補充】**Tier 3 補上的正好是最後兩條邊。** 這句話是這次最好的一句總結。

### 【可能被問】「這樣不就是靠人工嗎？那自動化的意義在哪？」

反過來看：**問人是最後一層，不是第一層。** 第一輪 Tier 1 有效的時候，工具**完全沒問我**——那才是它沒有濫用這個機制的證據。我還特別做了對照實驗（加一個開關把 Tier 1 關掉），關掉之後它才開始問。而且它問的是**真的推不出來的東西**：密碼和一個存在的帳號，這兩個值再厲害的靜態分析也生不出來。

## P5 · ④ 依賴圖分層

原本是自由佈局，train-ticket 那張 52 條邊基本上是一團麻。現在按**角色 + 呼叫深度**排成上下層：入口 → 業務服務（依深度）→ 資料層 → 外部 → 無相依。

兩個設計決定值得講：

- **用最長路徑不是最短**：一個服務如果既被直接呼叫、又在某條鏈的尾巴被呼叫，它要排在鏈的**下面**，否則箭頭會往回指、層次就讀不出來。
- **環是預期的，不是錯誤**：微服務互相呼叫很常見（train-ticket 就有），用 Tarjan SCC 縮點後再分層，同一個環的成員放同一層——環裡本來就沒有「誰先誰後」。

驗證數字：train-ticket 那張圖分層後 **51 條邊 100% 由上往下**（0 條向上、0 條同層穿越）。這是「層次是真的、不是排版錯覺」的量化證據。

還有一個副產品：最底下那層叫 **`no dependencies found`**——完全沒有邊的節點。它不是入口，是「抽取沒抽到東西」。**這層本身就是一份誠實的缺口清單**：train-ticket 有 19 個節點落在那裡，其中 `ts-gateway-service` 是真的漏抽，是下一個該補的目標。

## P6 · ②③ 命名與 draw.io

**DepWeaver** — Multi-Evidence Dependency Weaver。*weave*（織）就是核心設計：runtime / code / doc 三種證據**織成同一張圖**，不是三選一。

重點是它**蓋在產出物上**，不只寫在文件裡：Graphviz PNG 的標題、`.mmd` 檔頭、Discord 上的報告與覆蓋率標題都帶著它。所以圖貼進投影片或論文之後，還認得出來源。

圖號也定了：Fig.1 端到端流程、Fig.2 證據合併鏈、Fig.3 分層相依圖、Fig.4 對話補值迴圈。

draw.io 那邊我想先講清楚一條界線：**只有「說明用的流程圖」（Fig.1 / Fig.2）改成 draw.io 手畫**。工具**自動產出**的依賴圖維持 Graphviz / Mermaid——那是程式即時生成的，一次可能 50 個節點、每次結果都不同，不可能也不該用 draw.io 畫。

## P7 · ★ 真環境逼出來的七個 bug（我覺得這頁最重要）

這七個全都是 BoA 這種真系統才逼得出來的，在單元測試裡永遠不會出現：

1. **半組憑證** — 工具問了我 username，卻**自己編了密碼**。登入回 200（因為 redirect 回登入頁被自動跟隨，看起來跟成功一模一樣），然後每個需要登入的步驟都 401。**修**：憑證必須整組問，不准編造密碼/token。
2. **200 不等於成功** — 上面那個陷阱的通則。SSR 應用拒絕表單時會 redirect 回原頁，失敗和成功長得一樣。**修**：動作回 200 但該出現的邊沒出現 → 就當它被拒絕。
3. **值錯了改不掉** — 我第一次填的收款帳號是「自己的帳號」，轉給自己不會觸發餘額檢查。但 prompt 寫死「已提供的值不准再問」，生成器只好把那條邊宣告成 UNREACHABLE。**修**：值明顯是問題來源時，可以用新的變數名重問。
4. **報告和圖互相矛盾** — 報告說 db 邊 `Runtime observed: Unknown`，旁邊的圖卻畫實線。我改了兩次 prompt，它每次換一種錯法（第二次變成列 Micrometer、Log4j2、Cloud SQL 這些**函式庫和雲端替代方案**）。
5. **文件幻覺污染覆蓋率** — 同一個叢集、同一批流量，隔一輪 **7/7 變成 7/10**。系統沒變，只是 DeepWiki 這輪多講了幾句 `userservice → ledgerwriter`（實際上不存在）。
6. **一個 label 撐爆整張圖** — image 的 sha256 digest（71 個字元）進了節點標籤，圖被拉到 5000px 寬。分層是對的，但沒人看得出來。
7. **把程序內的快取當成資料庫** — `balancereader → in-memory-cache` 是服務**程序裡**的 Guava cache，沒有網路端點，**永遠不可能被觀測到**。它把資料層分數卡在 5/6，還被列在「可能是 pod 啟動順序問題」底下——給了一個做不到的補救建議。**修**：不可能被流量踩到的邊，不該進覆蓋率分母（這條規則本來就有，只是漏了程序內這一類）。

### 第 4、5 個的修法是同一個道理，值得展開講

這兩個看起來無關，其實是同一個病：**我們把確定性的東西，交給了非確定性的元件。**

- 第 4 個：第 5 節的內容（誰依賴哪個資料庫、觀測到沒有）**graph 裡全都有**，圖也畫對了。請一個看不到那張表的模型去複述它，只是多給它一次講錯的機會。**最終解法不是再改 prompt，是把那一節從 LLM 手上拿走**——改由程式碼從 graph 直接產生，並讓報告和圖**共用同一個 graph 物件**，這樣它們不可能再描述不同的圖。
- 第 5 個：覆蓋率號稱是「確定性算出來的」，但它的**分母**有一部分來自 LLM 讀文件的產物。**一個會隨著 wiki 寫得多不多而變動的分數，量的就不是流量。** 修法：只有「有證據是真的呼叫」的邊才進分母；只被提到過的（圖上的點線）照樣畫出來，但不計分。

【口頭補充】所以這兩個 bug 其實在說同一句話：**「確定性優先、LLM 只補殘餘」不是口號，是有邊界的**。報告和覆蓋率分母是整條線上最後兩個還沒套用這條原則的地方，結果它們就是唯二會飄的產物。

## P8 · ★【可能被問】「這些修正只對這個 repo 有效嗎？」

這題我先自己答，因為答案有兩半：

**通用的（規則層面，零專案知識）**：憑證整組問、200 不等於成功、內部邊不是放棄的理由、值可以重問、報告第 5 節由 graph 產生、digest 截斷。這些換到 sock-shop 或 train-ticket 同樣成立。

**兩處我不會說它通用：**

- **library 名單是寫死的**。這次為了清掉 `lettuce`（Redis 的 client library 被誤當服務），我在名單裡加了一批。它對 Java / Python 生態有效，換成 Go 或 Rust 就漏。**這正是老師之前指出的「三份寫死名單要設定檔化」那個技術債，我等於把其中一份加長了。**
- **排除「只被提到過」的邊，對抽取品質差的專案會虛高**。BoA 是 Java + Python，有 tree-sitter grammar，真實的邊都抽在 code 層，被排除的只有文件幻覺。但**沒有 grammar 的語言**（Go、Rust）抽取會退回 LLM 閱讀，真實的邊可能全都只到最弱那層 → 分母縮到剩一兩條 → 印出 100%，其實什麼都沒抽到。

  第二點我當場修了，做法**不是取消排除，是不准靜默**：一律報出「Not scored: N 條」，而且**未計分的邊比計分的還多時直接標警告**。這和這條線一貫的作法是同一個標準——圖會說「declared, not verified」而不是畫一條有自信的線，greenfield 報告會說「N/A，沒有叢集」而不是編造 pod 數，**覆蓋率也該說出它沒在算什麼**。

【口頭補充】其實「只對這個 repo 有效嗎」這個問題本身，就是這次驗證最有價值的產出方式。BoA 逼出七個 bug，多數修法通用、一個暴露既有技術債。這比「在 petclinic 上跑得很順」更能說明工具真實的狀態。**而且下一個專案（Go 或 Node 的）大概率會再逼出一批，那也是預期中的。**
