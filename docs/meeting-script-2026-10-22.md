### 1-1　§1.1 情境與表 1

📍 §1.1 第一段，再**圈**表 1「各個來源看得到與看不到的東西」，最後**劃**表 1 下面「執行期觀測是什麼」那一段。

💬
> 整篇的出發點是表 1。要畫一張微服務的相依圖，有四種來源：部署描述檔，像 Kubernetes 的 manifest、Docker Compose，它知道有哪些服務、設定上誰連到誰，但不知道程式碼有沒有真的呼叫；程式碼與設定檔，看得到寫在那裡的呼叫，但看不到動態分派，寫了也不代表會跑到；執行期觀測，看得到這段期間真的發生過的呼叫，但沒被走到的路徑看不到；最後是人，知道名稱怎麼對應、知道只有部署的人才知道的值，例如密碼，但規模大了問不完。
>
> 表 1 下面那段是上次老師要求的：「執行期觀測」用白話定義一次。系統跑起來以後，每個服務旁邊掛一個 proxy，Istio 叫 sidecar，每一次呼叫都經過它，它記下誰呼叫誰、幾次、成功與否，送到 Prometheus。因為是呼叫真的發生時記下來的，所以精確，但只有真的被呼叫過的關係才會出現。這段之後全文就用「執行期觀測」四個字，不再寫遙測。

### 1-2　§1.2 問題

📍 **劃**引文框「來源有好幾個、可靠度各不相同，要怎麼拼出一張讀者能拿來做決策的圖？」，再**指**下面那段的三個數字。

💬
> 問題一句話：來源好幾個、可靠度不一樣，怎麼拼出一張能拿來做決策的圖。下面三個數字說明這個問題不是我們自己覺得難：一份比較研究找到 13 個靜態架構重建工具、實際比較 9 個，最好的單一工具 F1 是 0.86，四個工具組合起來 0.91，也就是單一來源不夠；37 個重建工具裡 19 個純靜態、10 個純動態、只有 8 個兩者都用；2026 年的文獻回顧直接寫「沒有任何單一來源足夠」，把「可靠地融合異質證據」列為未解的問題。這三篇這次都上網對過原文，數字沒錯。

🛡
- 「F1 是什麼？」→ precision 與 recall 的調和平均：precision 是畫出來的邊有多少是對的，recall 是該有的邊有多少被畫出來，F1 把兩個合成一個數字，1 是滿分。

### 1-3　§1.3 納入標準：兩個條件（上次反饋的核心）

📍 **圈**表 2「本文的納入標準」，再**劃**表 2 下面那段「兩個條件之外，還有一個區分 pattern 與步驟的判準」。

💬
> 這張表直接回應上次的兩點。原本三個條件：論文、業界、我們的工具。「我們的工具也實作」這一條拿掉了，因為它只是在說我們自己有做，對「這是大家都在用的做法」沒有證明力，而且會提到還沒發表的 DepWeaver。剩下兩個：至少兩篇已發表的論文描述或評估過；至少兩個業界工具採用、而且寫在官方文件裡。缺一就不收。
>
> 表 2 下面那段是新加的判準，也是這次砍 pattern 的依據：一個做法除了過兩個條件，還要有自己互相拉扯的 forces，讓人需要在幾種做法之間取捨，才寫成 pattern；只有一種顯而易見做法的，寫成背景或某個 pattern 的前提。「以流量走遍路徑」就是這樣被改成前提的：送流量、看哪些邊還沒出現、再送，沒有第二種做法可選。
>
> 再下面一段是每個 pattern 的欄位：名稱、別名、一句話摘要、Context、Problem、Forces、Solution、實作要點、Resulting Context、Consequences、Known Uses、Related Patterns，和上次一樣。實作要點保留，但不再說是誰的經驗，寫成「實作時會遇到的細節」。

🛡
- 「兩個條件會不會太鬆？」→ 篩選力本來就在這兩個；第 6 節表 9 有一個候選「覆蓋率的分母只算量測得到的項目」就是因為找不到論文、業界只有程式碼覆蓋率工具而不收，證明兩個條件還是篩得掉東西。
- 「forces 是什麼？」→ pattern 寫作的術語，指套用解法時彼此衝突、必須取捨的需求。例如要完整就得收弱來源、收了弱來源就會帶進假邊，這兩個拉扯就是一組 forces。

📍 **指**三段粗體：讀部署描述檔、抽取程式碼呼叫點、看執行期服務圖；再**劃**最後一段「這三個做法都通過本文的兩個條件，但我們沒有把它們寫成 pattern」。

💬

> 它們都過兩個條件，但沒寫成 pattern，理由和剛才的判準一樣：各自只有一種顯而易見的做法，沒有互相拉扯的 forces，而且表 1 已經講完它們的取捨。所以當背景。四個 pattern 處理的是三個來源都有了之後的問題。

### 1-7　§5.1 ① 混合重建（這版新寫的第一處）

📍 標題「混合重建（Hybrid Reconstruction）」。依序**指**：別名 → 一句話摘要 → Context → **圈**粗體「前提：先以流量走遍路徑」整段 → Problem 引文 → Forces 四條 → Solution 五步 → 例子 → 實作要點 → Resulting Context → Consequences → 表 5 Known Uses → Related Patterns。

💬
> 別名：靜態加動態分析、多來源融合，ServiceNow 叫 pattern-based 與 traffic-based mapping，vFunction 叫 dynamic 與 static analysis。一句話摘要現在是兩句：先主動產生流量讓執行期觀測看到平常沒走到的路徑，再把各來源的結果以「來源服務到目標服務」為鍵合併，每條邊保留它來自哪些來源。
>
> **前提那一段**是原本整個「以流量走遍路徑」pattern 壓成的。內容：三個來源裡執行期觀測最可信，但只有被走過的路徑，測試環境可能根本沒人用、正式環境的罕見流程一週才走一次；所以合併前先用負載產生器、端對端測試或合成監控腳本送流量，把「靜態有、執行期還沒量測到」的邊列成清單，用它決定下一輪送什麼，清單不再縮短就停。附三個引用：Cornelissen 等人說動態分析本質上不完整、難處在決定要執行哪些情境；Istio 的 Kiali 教學要使用者先反覆送流量，因為圖呈現的是一段時間內流經網格的流量；Online Boutique 內建負載產生器。段末明講這一步為什麼不是 pattern：只有一種顯而易見的做法。最後三件注意事項：流量要語意正確才走得到深處，需要只有人知道的值就請人提供，接到第三個 pattern；寫入類流量在測試環境跑；判斷走到了沒要看邊有沒有出現，不只看 HTTP 狀態碼，因為有些應用拒絕表單也回 200。
>
> Problem：每個來源都不完整，而且看不到的地方各不相同；只用一個一定漏，全合在一起又要決定名稱不一致與說法衝突時聽誰的。Forces 四條：來源確實互補，有量化研究支持；名稱不一致；合併規則要能解釋，加權投票、機率模型很難向讀者說明一條邊為什麼在圖上；弱來源會帶進雜訊。
>
> Solution 五步：以部署描述檔的服務清單為主確定節點，對不上的另外處理；以（來源、目標）為鍵合併；每條邊保留所有支持它的來源和出處，檔案與行號、指標名稱、文件段落；較弱的來源只補強既有節點，不憑空新增服務；記錄哪些來源這次有收集、哪些沒有，接到第四個 pattern。例子就是表 3 那幾條。
>
> 實作要點：合併順序影響可解釋性，先用最可靠的來源建骨架再疊弱的，每一步只做加法；框架函式庫的名字常被誤認成服務，要用可設定的排除清單濾掉；流量腳本不用從零寫，repo 裡常有現成的。Resulting Context：圖比任何單一來源完整，但畫出來每條邊長一樣，量到 95 次的和只有一個連線設定的分不出來，接第二個 pattern。
>
> Consequences 多了兩條代價：要維護流量腳本、寫入類流量需要測試環境、流量永遠不會到 100% 所以需要停止條件。表 5 Known Uses 五列：Mayer 與 Weinreich、Schneider 等人、Grinenko 等人三篇論文，ServiceNow、vFunction 兩個業界工具。沒有我們的工具。

🛡
- 「前提那段會不會太長？」→ 它把原本一整個 pattern 的 Context、Solution、Known Uses、注意事項壓成一段，大約 400 字。可以再砍成只留做法與三個引用，注意事項移到實作要點；今天想聽老師覺得哪個版本好。
- 「為什麼不把前提寫在 §2 背景？」→ 背景三個是「來源怎麼收」，流量是「收執行期這個來源之前要先做的事」，和混合重建綁在一起才看得出它在流程裡的位置。

### 1-8　§5.2 ② 實測優先於推測

📍 標題，**指**別名與 Solution 五步，**指**表 6，**劃** Related Patterns 最後一句「容易和 ④ 的未知混淆」。

💬
> 這個 pattern 內容沒變，只改編號和交叉引用。重點三句：每條邊帶一個標記，實測是執行期觀測記錄到的，推測是只來自程式碼、設定或文件的；標記和出處分開存，一條邊可以有多筆出處但只有一個標記；合併時更強的證據取代較弱的，同一條邊一旦被量測到就不再顯示為推測。畫法是把最醒目的視覺通道、實線與虛線，給這個標記。
>
> 實作要點多了一句：兩級是底線，要再細分，例如把「程式碼裡有呼叫」和「只有連線設定」分開，每多一級都要在圖例交代。這一句是為 COMPSAC 那邊的三級留的接口，但這裡不提工具。
>
> Related Patterns 最後一句要注意：這個 pattern 講「多可信」，第四個 pattern 最後一條規則講「有沒有查過」。一條推測的邊是有弱證據的，一個部署狀態「未知」的節點是完全沒查過的，兩者不能共用同一個欄位。表 6 Known Uses：Guo 等人的視覺變數實驗、Famelis 等人的 partial models，AWS X-Ray、CloudWatch Application Map、Datadog inferred services。

🛡
- 「實測和量測到是同一件事嗎？」→ 是。「實測／推測」是標記的名字，當名詞用；句子裡講動作寫「量測到」。兩篇稿都這樣分。

### 1-9　§5.3 ③ 請人確認名稱對應

📍 標題，**指** Context 最後一句「① 的前提要觸發某條路徑時，可能需要一組只有負責部署的人才知道的值」，**指** Solution 六步，**指**表 7。

💬
> 內容沒變。Context 裡那句把流量要的值也接進來：規則判斷不了的名稱、和流量需要的密碼帳號，都是「自動手段用盡才問人」的同一件事。
>
> Solution 六步：先用所有規則對齊，只有規則真的判斷不了的才記成問題；每個問題附排序過的候選，排序只給人看不替人決定，加上「新節點」「忽略」兩個選項；在使用者平常用的地方問，一次問完；答案以確定性規則解析，看不懂就保留問題不猜；答案以 repo 為單位存下來，下次只問新出現的；報告裡標出哪些邊是靠人的回答畫上去的。表 7 Known Uses：Murphy 等人的 reflexion model 這次補引了 1995 年 FSE 會議版，因為稿裡那句「工程師定義高階模型並指定對應」逐字出自會議版；Sarawagi 與 Bhamidipaty 的互動式重複資料比對；ServiceNow 讓使用者審查建議的連線；Datadog 的 service remapping。

🛡
- 「業界的做法是事後寫規則，和這個 pattern 一樣嗎？」→ 不完全一樣，第 6 節有寫：業界多半是使用者事後寫改名、合併、拆分的規則，不是工具在分析中主動問；ServiceNow 讓使用者審查建議的連線是最接近的。這是這個 pattern 證據最弱的地方，稿裡標成「中」。

### 1-10　§5.4 ④ 先算事實，再讓 AI 解釋（這版新寫的第二處）

📍 標題。依序**指**：別名那段 → 一句話摘要 → Context → Problem 引文與下面那行「0% 看起來像量了很糟」 → Forces 七條 → **圈** Solution 六步 → 例子 → 實作要點 → Resulting Context → Consequences → 表 8 Known Uses 九列 → Related Patterns。

💬
> 這是三個 pattern 合成的：一份目錄多個視圖、先算事實再讓 AI 解釋、無資料不等於零。別名那段把三者的業界叫法都列了：analytics augmented generation、PAL、Dynatrace 的 hypermodal AI、K8sGPT 的 analyzer 加 explain；事實所出自的那份模型，業界叫 Software Catalog 或拓樸模型，學界叫 metamodel 或中間表示法；「沒有資料」的狀態，監控工具叫 No Data，Kubernetes 叫 Unknown condition，runtime verification 叫 inconclusive。
>
> 一句話摘要：每次分析先建一份統一模型；能由程式從模型算出的事實由程式產生，LLM 只負責解釋、提出詮釋與建議，不讓它重述事實；沒收集到的資料在模型裡是「未知」，程式照寫「未量測」而不是 0，也不交給 LLM 猜。
>
> Problem 把三個合在一起：圖、數字與報告各自從原始來源推導就會說不同的話；報告交給 LLM 寫，它重述事實時會漏、會加、會換詞，prompt 寫更嚴也不一定解決；沒收集的資料在程式裡變成 0 或 false，在 LLM 手上變成猜測。下面那行是具體的樣子：0% 看起來像量了很糟，deployed: false 看起來像查了沒部署，空清單看起來像找過了沒有。
>
> Forces 七條，念標題就好：每個產出物都想要最順手的輸入；讀者要連貫的文字；改 prompt 很便宜所以很誘人；LLM 自己算事實的準確度不夠，引 Liljas 等人的 F1 約 0.6；詮釋需要事實；空白容易被填上；有些視圖很晚才需要產生。
>
> **Solution 六步**是這一版的核心：一，每次分析先建一個統一模型，所有視圖都從它產生，衍生計算只實作一次，模型可以存檔讀回；二，「這次收集了哪些來源」當成模型的中繼資料，狀態欄位用三值、預設未知；三，報告內容分成事實與詮釋；四，事實由程式從模型產生、措辭固定，遇到未知就寫一句「為什麼未知、補什麼才會知道」，絕不用 0 代表未量測；五，讓 LLM 也看得到事實，但事實段落以程式那份為準，LLM 自己寫了就丟掉，交給 LLM 的字串裡未量測就寫未量測；六，讓讀者看得出哪段是程式產生的，步驟失敗要留紀錄。
>
> 例子把商店的三個情況串起來：圖上 orders 到 orders-db 是實線、覆蓋率算它已量測、報告由程式寫「量測到 12 次連線」、三天後問答也這樣答，因為讀同一個物件；LLM 只寫風險；cart 沒有 sidecar，它的執行期欄位是「未知：這次收集不到」而不是 0 次。
>
> 實作要點三段：視圖完全由模型決定，所以「報告與圖是否一致」可以寫成單元測試；「丟掉 LLM 的版本」比「請它不要寫」可靠，程式段落用結構錨點拼進報告；三值最簡單是可為 null 的布林值，重點是預設必須是未知，而且這條規則要在每一條路徑上實施，只要有一條 prompt 沒帶「這次沒收集什麼」，空白就會從那裡被填回來。
>
> Resulting Context 是 language 的終點，留下一個後續問題：讀者拿到報告會追問，自然語言的問題怎麼變成對模型的確定性查詢。表 8 Known Uses 九列：論文四篇，Alshuqayran 等人的 metamodel、Satyrn、PAL、Bauer 等人的三值判定；業界五個，Backstage、Dynatrace、K8sGPT、Grafana 的 No Data 狀態、Datadog 監控的 Evaluate as zero 選項。

🛡
- 「三個合一個會不會太大？」→ 判準是它們解同一個問題「產出物不走樣」的三個面向：事實從哪裡算、由誰寫、算不出來時寫什麼；拆開寫，每一篇的 Solution 都要引用另外兩篇才完整。如果老師還是覺得大，最自然的切法是把「無資料不等於零」切回去當第五個，§6 表 9 的那一列改回「納入」就好。

### P3 · RQ0 假想敵：怎麼設計

💬
> 這頁講實驗怎麼設計。老師的問題是：不讓 AI 基於事實，它是不是真的畫不出正確的圖。

💬

>
> 第一組零檔案：只給 repo 網址和元件清單，一個檔案都不給。這就是「不基於事實」。
