[碩論] ① 20 個節點 3

「可以到 21」精確的意思

上限完整畫出被截
15（規則選出的值）95%11／242
20（採用）100%（四捨五入）1／242
21 以上100%0／242
先講一個讀法問題：這 242 組起點集合是程式窮舉的（單點、兩兩組合、3／4／6／8 個成員的滑動視窗），不是問句的機率樣本。所以 p90 與最大值不能讀成「多少比例的問句會被截」。21 只是窮舉出來的最大值，出現在「一次餵 8 個種子」那一列，而 8 是查詢的工程上限，不是觀察到的問句寬度。

一句點名幾個節點（102 句 hold-out）句數比例
0 個（例如「哪些依賴還沒有流量佐證？」）5958%
1 個3332%

3 個（最寬）——沒有任何一句點名到 8 個11%

但這 102 句也是我自己寫的。「問句有多寬」的三個資料來源（hold-out、242 組窮舉、流程成員標註）全部經過我的手；真實使用者問句的樣本只能來自已部署實例的 thread log，還沒收集。所以右邊兩個理由刻意寫成不依賴問句分布。

為什麼停在 20

理由內容
① 極端值
不可外推		21 是「我們這次枚舉裡的最大值」。拿它當上限等於宣告「上限＝我目前算過最大的那個切片」，換一個系統（train-ticket 的閘道有 46 條路由）馬上又破，而且破的時候沒有原則可以決定新值。20 有出處，21 只有我們的枚舉結果
② 這個參數
不敏感		15 到 25 之間只影響 242 組裡的 1 組。與其把它調準，不如承認它不需要調準——這也是為什麼沒有為它做使用者實驗：實驗成本很高，而可量到的差別是 1／242
③ 它是安全閥
不是最佳化目標		規則選出的其實是 15（比 20 更緊）；採用 20 是因為在文獻安全區內多畫一個節點沒有壞處、少畫一個就少一個事實

所以真正該補的是「截斷看得見」

誠實的做法不是把上限推到剛好不截，而是讓被截這件事無法被忽略：截斷寫進圖本身的標題（20 of 23 nodes shown, limit 20）——因為圖會被複製到簡報或論文，訊息裡的說明不會跟著走；訊息裡點名被省略的節點而不只報數量。兩處都有測試釘住。
講稿　先解釋「可以到 21」是什麼：上限設 21 的話 242 組全部不被截，設 20 截掉 1 組。但這裡有個讀法問題我要先講：那 242 組是程式窮舉的，不是問句的機率樣本，所以 p90 跟最大值不能讀成「多少比例的問句會被截」——這點我之前寫得不夠清楚。21 只是窮舉的最大值，而且出現在「一次餵 8 個種子」那一列，8 是查詢的工程上限。左下那張表是我唯一有的問句樣本：102 句裡最寬只點名 3 個節點，沒有一句到 8 個。但那 102 句也是我寫的，這點要自己先講，所以右邊兩個理由我刻意寫成不依賴問句分布。右邊三個理由，最重要的是第二個：這個參數在 15 到 25 之間只差一組，它不需要被調準。所以我改的不是數字，是讓截斷看得見——特別是寫進圖的標題，因為圖會被單獨複製出去。

共用 ConfigMap 的 envFrom不畫不畫（理由不變）

[碩論] ③ 一個 pattern 是怎麼寫的 1

① 證據分級的關係（Evidence-Graded Relations）——八個欄位逐一走一遍

Context你從多個來源收集元件之間的關係：執行期遙測、程式碼、設定檔與部署描述、專案文件。你準備把它們畫成一張圖給人看。
Problem來源的可靠度差很多。全部畫成同一種線，讀者會以為每條都一樣真；只畫最可靠的（量測到的），又會丟掉那些量測不到、但確實存在的依賴。
Forces
（只列真的互相拉扯的，每條寫「不這樣做會怎樣」）		 · 可靠度與完整度方向相反：遙測 precision 高 recall 低、結構分析反過來、文字兩者都低——只取一個一定犧牲另一個
· 讀者要一眼看懂：分級太多看不懂；只有兩級又把「有程式碼證據但沒跑到」和「文件隨口提過」混為一談
· 下游會偷偷升級：摘要、報告、問答很容易把「只被提到」講成「確定存在」——尤其下游是 LLM
· 視覺通道有限：線型、顏色、粗細要分給等級、類型、流量；Guo 等人（TVCG 2015）指出同時編碼主屬性與不確定性的視覺變數會互相干擾
· 誠實揭露可能反過來降低信任：不確定性視覺化是雙面刃，可能被讀成「這份東西不可靠」
Solution
（五條，寫成可以照做的步驟）		 ① 定義小而有序的三級：量測到／有使用證據／只被提到
② 等級（多可信）與來源（誰說的）分開存——一條關係可以有多個來源，但只有一個等級
③ 以（來源, 目標）為鍵合併：等級取最高、來源與佐證取聯集
④ 把最醒目的視覺通道給等級（實線／虛線／點線），類型用顏色、流量降級成線寬
⑤ 所有下游只能照抄或降級，不能升級
Resulting
Context		每條關係都有等級了。但一次分析有好幾個產物，各自推導就會對同一條關係說出不同的話 → 這就是 ② 的情境
Consequences
（代價要跟好處一樣具體）		 ＋ 量測不到的真依賴仍在圖上，但不會被誤認為已確認；合併只需要「取最高」，沒有參數要調
－ 「什麼算使用證據」需要領域知識，每種語言與框架各要一份判準
－ 強來源誤判會蓋掉弱來源的正確判斷（取最高沒有降級機制）
－ 三級無法表達「兩個弱來源互相佐證」
Known Uses
（工具以外至少兩個，查證過）		 本工具：三級 ＋ 取最高合併 ＋ 三種線型；附兩個事件（被指出「比較像流量圖」而改成以等級為主要編碼；同一條邊三次實驗從「不存在」→「虛線」→「實線 5 191 次」）
Admiralty Code（NATO）：來源可靠度 A–F 與資訊可信度 1–6 分兩個軸——「等級與來源分開存」最古老的先例
Kiali 的 idle edges、CycloneDX 的 confidence 0–1、SLSA 等級、W3C PROV
講稿　與其說「寫完了幾行」，不如把一個 pattern 攤開來看怎麼寫的。我選第一個。Context 是情境，Problem 我一律寫成「兩難」——全部畫一樣讀者分不出真假，只畫最可靠的又會丟掉真的依賴，兩邊都不行，這才叫 problem。Forces 是這個格式最容易寫壞的地方：我只列真的互相拉扯的，而且每條都寫「不這樣做會怎樣」，沒有張力的就移到實作要點去。像「視覺通道有限」那條我引了一篇 TVCG 的實驗，它說同時編碼主屬性跟不確定性的視覺變數會互相干擾，所以通道分配是有代價的選擇。Solution 寫成五個可以照做的步驟。Resulting Context 一定要接到下一個 pattern 的情境，這是 language 跟 catalog 的差別。Consequences 我要求代價寫得跟好處一樣具體——像「取最高沒有降級機制」「三級表達不了兩個弱來源互相佐證」，這些都是真的限制。Known Uses 除了自己的工具，至少要兩個查證過的外部實例，而自己的工具那段我附了事件，因為 pattern 的力量來自它解掉的真實失敗。

⑤ 未量測不是零
Unmeasured
Is Not Zero		沒收集的資料在程式裡變成 0 或 false，在 LLM 手上變成猜測；失敗的步驟看起來和「什麼都沒找到」一模一樣狀態用三值、預設是「未知」；執行模式當中繼資料傳到每個視圖；遇到未知就寫一句話說為什麼、補什麼會知道；絕不用 0／0% 當佔位交給 LLM；步驟失敗記失敗狀態而不是空結果每個讀取點都要處理三值；漏一個地方沒傳模式資訊，幻覺就從那裡回來（最脆弱，要求全面實施）SQL 的 NULL 與三值邏輯、Kubernetes 的 Unknown、Grafana 的 No Data、Prometheus 的 absent()
為什麼是 language 不是 catalog：每個 Resulting Context 都接到下一個的 Context。分級之後才會出現「多個產物怎麼一致」；一致之後才會出現「LLM 重述會漂移」；事實由程式寫之後才會出現「分母算什麼」；分母收斂之後才會出現「整個指標沒量測時顯示什麼」。

全文除了五個 pattern 還有：摘要與緒論（為什麼現在——LLM 進入產出鏈）、中性的 running example（線上商店，每個 pattern 都用它說明「沒套用會怎樣」）、相關研究四條線、討論與限制（每個 pattern 的證據強度評估）、附錄（pattern ↔ 程式碼與測試的對應表，給審稿人查證）。共 647 行；下一步是翻英文、套 ACM 模板。

講稿　另外四個用同一個格式逐一講。②的 Problem 是產物互相矛盾而讀者無從判斷誰對，解法是先建一個模型再產所有視圖，代價是 schema 變成共同介面、而且模型失敗所有視圖一起失敗。③是這五個裡最有量化外部支撐的：Satyrn 那篇先由程式算事實再讓模型寫，正確主張 86%，直接讓模型寫只有 57%；我們自己的事件是改了兩次 prompt 都只是換一種錯法，最後那一節改由程式產生。④的三個代價我寫得很具體，而且我特別放了兩個反例——JaCoCo 排除但不揭露、Istanbul 排除但灌進分子，這兩個反例把紅線劃出來。⑤最脆弱，因為它要求全面實施，漏一個地方沒傳執行模式，幻覺就從那裡回來。下面左邊那格是 language 跟 catalog 的差別，右邊是全文除了 pattern 還有什麼。

[碩論] 還空著的地方 1

三個缺口，都是我自己標出來的

缺口為什麼還空著最小的補法
沒有真實使用者問句的樣本「問句有多寬」的三個資料來源（102 句 hold-out、242 組窮舉、流程成員標註）全部經過我的手已部署實例的 thread log 裡每次路由都留了紀錄，撈出來就是第一份真實樣本；它同時補掉路由門檻那 102 句也是我寫的問題
沒有我們自己的使用者實驗所以命題 A（超過 20 就理解變弱）不主張先做小的那個：同一張被截的部分圖，一組有標題揭露、一組沒有，問「這張圖有沒有把相關服務都畫出來」——直接驗證這次做的改動，10–12 人、between-subject
第二標註者的材料是摘錄它看到的是摘錄，我看到的是整個 repo；這個不對等無法完全消除（prompt 有預算）。它也看不到圖片不打算補——改成在論文裡寫清楚它只能回答一個方向的問題：「作者有沒有標出別人也看得到的東西」
為什麼要自己先講：這三個缺口都是別人一問就會問到的地方。第一個影響的是「問句有多寬」這個前提，第二個決定我們能不能主張命題 A，第三個限制了第二標註者能回答的問題方向。與其被問出來，不如寫在文件裡並附上補法——前兩個的補法都很便宜。

另外三件需要換機器或叢集的

  • TeaStore 跑 runtime：靜態層在它身上只有 0.46，而那是 enum 動態分派造成的——這正是 runtime 層存在的理由，目標是「靜態 6/13 → runtime 全中，工具與 TeaStore 都不改」
  • 純 AI 對照第四輪：第三輪的數字是圖修正之前的，要在修好的圖上重跑才一致
  • top-k 與路由門檻換一份別的專案的 archive：現在的選 k 規則是看過那條曲線才定的，換一份重跑才是真正的檢驗
講稿　這頁是我自己列的缺口，不等被問。第一個最重要：問句有多寬這件事，三個資料來源全部經過我的手，真實使用者問句我沒有樣本。補法很便宜——已部署實例的 log 裡每次路由都有紀錄，撈出來就有了，而且順便補掉路由那 102 句也是我寫的問題。第二個是使用者實驗，我建議先做小的那個，直接驗證「截斷揭露有沒有用」，因為那才是我們主張的命題。第三個我不打算補，改成在論文裡寫清楚它的方向性。下面三件是要換機器的，其中 TeaStore 跑 runtime 最有價值，因為它剛好是靜態層做不到、runtime 層應該做得到的那種案例。
