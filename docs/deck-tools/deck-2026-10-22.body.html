[碩論] RQ0 假想敵：怎麼設計 1

同一批專案、同一份參考邊集、同一套計分，比四組

組別輸入對應的條件
零檔案repo 網址＋元件清單，無任何檔案不基於事實（僅靠模型記憶）
給檔案元件清單＋預算內的部署描述檔、設定檔、原始碼有事實、無工具
給檔案、不給名稱同上，元件名稱由模型自訂有事實、無名稱；不匹配的名稱另列
DepWeaver 靜態層14 條規則，不呼叫 LLM現行工具；數字取自 scores.md

三項設計決定

  • 元件清單提供給 LLM：排除節點辨識的影響，只比較邊；比較條件對 LLM 有利
  • 輸入預算固定於程式：描述檔與設定檔 300 KB、原始碼 500 KB、單檔 20 KB；7 個專案中 6 個原始碼全數納入；每專案的檔案清單留檔
  • 計分與 RQ1 同一套：以 DepWeaver 自身的圖自我檢查，與 scores.md 逐格相等

模型與參數

  • gpt-4.1-mini（與問答對照相同），temperature 0，JSON mode
  • max_tokens 12,000（首批 9 次未設；2 次達模型上限 32,768，為同組邊重複輸出 1,417 次）
  • 每組每專案 3 次；報平均與最小–最大
  • 63 次呼叫、326 萬 prompt token

參考邊集

RQ1 那 7 個有作者參考邊集的專案（Bank of Anthos、ewolff、ecommerce、piggymetrics、TeaStore、Online Boutique、robot-shop）；variant 類不計；邊＝（來源，目標）。

文獻對照：Liljas 等人（ESEM 2026）以 LLM agent 重建微服務架構，GPT-4o 平均 F1 0.604。

講稿　四組。關鍵是左下三個刻意的設計：元件清單給 LLM 是偏袒它，預算寫死而且六個專案原始碼全給，計分器先自我檢查過。右邊是模型和參數，第一批沒設輸出上限，兩次撞到迴圈，後來補上。

[碩論] RQ0 逐案看：零檔案怎麼錯、給檔案在哪贏在哪輸 3

零檔案組的三類錯誤

錯法例子
套別人的架構robot-shop 畫了 11 條錯邊，6 條是 load → 每個服務（把負載產生器當入口）；TeaStore 把 teastore-all（全部裝在一個 pod 的部署變體）畫成呼叫者
資料庫接錯Bank of Anthos 把 ledgerwriter、balancereader 接到 accounts-db（實際是 ledger-db）；robot-shop 把 ratings 接到 mongodb（實際是 mysql）
方向反piggymetrics 4 條、ecommerce 2 條：gateway → service 畫成 service → gateway

遺漏的是最常見的邊（Bank of Anthos：frontend → ledgerwriter、userservice → accounts-db）。7 個皆為公開專案；私有系統的結果預期更差。

給檔案組 vs 靜態層：三個已知邊界

專案與邊界LLM 給檔案DepWeaver
TeaStore：enum 動態分派（業務邊）1.00 / 1.000 / 7
ecommerce：localhost 預設值（控制面 R）0.960.28
robot-shop：Node／PHP（業務邊 R）1.000.40
piggymetrics：共用設定套到每個服務（R）0.711.00

LLM 能解析 enum 常數 Service.PERSISTENCE、${EUREKA_HOST:localhost} 的預設值，以及無文法支援的 Node 與 PHP；未將共用 application.yml 套用到各 config client。

三個邊界即靜態規則的已知極限 → LLM 宜作為管線中的一個來源（無文法語言層已如此），而非取代管線。
講稿　左邊是零檔案組怎麼錯：套別的系統的架構、資料庫接錯、方向反。右邊是給檔案組贏在哪：正好是靜態層三個已知邊界，enum、localhost、Node/PHP；輸在 piggymetrics 的共用設定。結論是 LLM 應該當管線裡的一個來源。

[碩論] RQ0 分數未呈現的三點：DepWeaver 的貢獻所在 4

沒有出處

63 次輸出無一條邊附檔案與行號；DepWeaver 每條邊附出處，114 筆經測試可開啟。要求 LLM 附行號，即回到「重述事實會錯」的問題。

不穩定

temperature 0、同一 prompt：TeaStore 給檔案組 recall 0.46–1.00；一次將元件命名為 registry／db／persistence（缺 teastore- 前綴）致整組不匹配；Bank of Anthos 兩次迴圈輸出 1,417 條。DepWeaver 同一 checkout 結果確定。

名稱

不給元件清單時 ecommerce 三次皆 0.00：採用 Compose 的 container_name（user-service-container）；寬鬆對名後 0.96。共 85 個名稱不匹配。即 pattern ③「請人確認名稱對應」的問題。

論文主張因此調整

LLM 需要事實；給事實後的圖無法查證、不穩定、名稱不匹配，對應 DepWeaver 的出處、確定性規則、名稱確認。LLM 在動態分派與無文法語言的表現，支持將其作為管線中的一個來源：等級不高於「有使用證據」、出處標示為 LLM 推得、名稱走同一確認流程。

講稿　三個框是分數看不到、但 63 次裡都發生了的事：沒出處、不穩定、名字。這三件正好對應我們的出處、確定性規則、問人確認。所以 RQ0 的結論寫成下面那段：DepWeaver 的貢獻不在 P/R，在這三件事；LLM 則該當一個來源併進來。
