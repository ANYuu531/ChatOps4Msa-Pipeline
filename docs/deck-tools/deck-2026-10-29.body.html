precision 高，是因為保守

  • 不唯一不畫：port、Eureka server、常數值都要對到唯一的模組
  • 宣告不等於使用：ecommerce 常數檔 25 條位址，19 條沒被引用 → 不畫

純程式碼做不到的，交給另外兩個來源

  • repo 裡找不到登記者的名稱、沒有文法的語言 → 問人（pattern ③）

講稿　為什麼純程式碼可以到這麼高？因為相依關係大部分本來就寫在部署描述檔、設定檔和程式碼裡，工具只是讀出來、對名字。LLM 給檔案能到 0.90、不給只有 0.70 也說明了這點。precision 高是因為規則很保守，不唯一就不畫。做不到的部分，本來就設計成交給執行期觀測和問人。

[碩論] 新增的 42 條規則在做什麼（一）：找到位址、對上名字 5

規則 1–14 是之前報告過的基本讀法（讀部署檔的服務清單、設定檔裡的位址、Compose）。這次新增的 15–56 依「在解決什麼問題」分四類，括號是第一次遇到的系統。

找到位址：位址不在呼叫旁邊，去它真正寫的地方找

15localhost:9296 → 找唯一用 9296 的服務（ecommerce → 設定中心）
16裝了 Eureka 卻沒寫位址 → 連 repo 裡唯一的註冊中心（ecommerce）
17常數的值等於某個服務的資料夾名 → 就是呼叫那個服務（TeaStore）
18、48拼網址用的環境變數：先查部署檔，沒設才用程式寫的預設值（robot-shop）
20環境變數只在讀它的那個服務自己的設定裡找，不拿別人的來套（AICS）
24、50Compose 只寫變數名、值放在 .env 檔 → 去 .env 找（opentelemetry-demo、yas）
27、32Nacos、Kafka 的「主機:port」清單、.NET 的 Host=db;… 連線字串也是位址（mall-swarm、opentelemetry-demo）
46nginx 先 set $x 再轉發 → 把變數值填回去（yas）
47網址先存進變數、隔幾行才呼叫 → 所有語言都往回追（通用機制）
53寫在容器啟動指令裡的位址（skywalking）
55一個設定寫了好幾個網址 → 每個都是一條線（travels）

對上名字：同一個服務有好幾種叫法

19order-v1、order-v2 是 order 的兩個版本，不是兩個服務（AICS）
25、37Compose 的別名：mysql 在某個服務裡被叫成 db（mall-swarm、.NET 系統）
36只切真正的網域字尾：catalog.api 是服務名，不是網域（.NET 系統）
44Compose 的 build 指向哪個資料夾，那份程式碼就是這個服務（yas）

不該畫的不畫：看起來像連線，其實不是

每條規則都是看 1–3 個系統的錯誤寫出來的。如果它在其他系統也會改變畫出來的圖，就代表它抓到的是大家共通的寫法，不是某個系統的特例。程式裡記錄了每條規則在每個系統上實際改變了什麼：多畫一條線、少畫一條線、實線改虛線、或把兩個名字合成一個節點。
