[碩論] ③ 純 AI 對照 1

三組比較：同一批題目、同一個模型、temperature = 0

組別模型看得到什麼代表什麼
report-only報告全文（最多 60 000 字），沒有檢索、沒有路由、沒有圖「直接把報告丟給 LLM 問」
rag正式環境檢索器取回的段落，僅此而已一般 RAG 基線
depweaver正式流程：語意路由（沒把握才叫 planner）→ 圖查詢 → 確定性結果 ＋ 同一批段落現行系統

怎麼評分：不靠人判斷、不靠 LLM 當裁判

  • 每一題的答案都是一組節點（誰呼叫 X、X 掛掉影響誰、哪些服務真的用資料庫、哪些邊沒有執行期證據……）
  • 標準答案 ＝ 圖查詢引擎對該題標註查詢的輸出——我只標「這題用哪條查詢」，答案由程式在圖上算；所以三組同一份 gold、我改不了，但也代表圖錯 gold 就錯
  • 評分程式從回答文字裡抓出圖上存在的節點，算 precision／recall／F1
  • 另記兩個指標：off-graph（像服務名但圖上沒有）與圖與報告都沒有（最接近「憑空捏造」的訊號）
  • 指標是近似值：抓的是 a-b 形式的小寫詞，英文連字詞可能誤抓，所以只看比例、不當成謊言計數

這個比較內建的偏袒，寫在結果旁邊

標準答案 ＝ 在圖上跑標註的那條查詢。而 depweaver 的正式流程也是在圖上跑同一條查詢再讓模型講成人話——它收到的輸入就是標準答案本身。
像考試把答案卷發給其中一組，再用那張答案卷改考卷。
所以 1.000 要讀成「路由選對查詢 ＋ 模型忠實轉述」這個下限檢查，不是「我們比較強」。公平的比法要讓標準答案來自管線之外（例如專案自己的架構文件）。

評分程式自己踩過的三個坑

  • 圖答「沒有」的題目標準答案是空集合 → 答對反而 0 分。改成不自動計分、逐題列出讓人判讀
  • 引擎的否定句與 Query: 回音污染標準答案 → 複誦問句裡的名字就能拿滿分
  • 查詢運算子名被當成「編造的服務名」

第一輪的原始數字因此不可用——是評分程式的錯，不是系統的錯。

講稿　三組、同一批十題、同一個模型、temperature 零。先解釋「接地」＝回答前先去確定的地方查事實、模型只負責講成人話；三組就是照接地程度排的。偏袒那格一定要把兩條線接起來講：標準答案＝在圖上跑標註的那條查詢；depweaver 的正式流程也是在圖上跑同一條查詢——**它收到的輸入就是標準答案本身**。用考試比喻：另外兩組讀課本自己推，我把答案卷發給第三組，再拿那張答案卷改考卷。所以 1.000 要讀成「路由選對查詢＋模型忠實轉述」的**下限檢查**（拿不到 1.0 代表管線壞了），不是我們比較強。公平的比法要讓標準答案來自管線之外。評分程式的三個界線也要講：量的是點名了哪些服務不是說法對不對、否定句只在 gold 端過濾、off-graph 清單手動維護。

  • 純讀報告：不胡說，但少講。precision 一直很高，失分幾乎都在 recall（0.72–0.94，隨報告裡「硬句子」的多寡起伏）。執行期報告有「TCP 5 191 次」這種句子，它就答得好；靜態報告沒有，它就漏。不完整而語氣肯定，讀者看不出少了什麼——這是沒有接地最危險的形態。
  • 多跳推理必失手：「accounts-db 掛掉會影響誰」5 個只答 3 個。傳遞閉包正是圖查詢的價值，也符合 GraphRAG 文獻的觀察。
  • RAG 在「答案是沒有」的題目上壞得最明顯：沒有叢集資料時列了 11 個服務、沒有外部主機時列出 GKE／Cloud SQL／Cloud Trace。不是幻覺（報告多半提過），但回答的不是問題。
{{CHART:baseline-arms}}
整節的結論：對照實驗量到的不是 LLM 的好壞，是圖的好壞。接地組每一輪的失分都能追到圖上一個具體缺陷，修掉就消失——第三輪唯一的失分追到「文件層用去連字號的拼法又造了一份資料庫」，已修。

樣本限制：10 題、一個專案、一份 archive、一個模型，F1 差距不做統計檢定。最省的強化是把題目擴到 train-ticket 的 archive 再跑一次。

講稿　接地那一欄很漂亮但我不主打，因為前一頁講過它內建偏袒。有內容的是三個失分型態：純讀報告不胡說但少講，而且少講的程度取決於報告裡有沒有硬數字；多跳推理一定失手；RAG 在「答案是沒有」的題目填清單。第二輪 RAG 那 0.30 多半是評分的近似誤差不是幻覺，那兩個名字是真實的初始化 Job。第三輪我們是 0.963，因為標準答案被重複拼法污染，已修但這一輪的數字是修正前的，我不想事後重算一個好看的數字。結論：量到的是圖不是 LLM；範圍：這個實驗不證明工具整體有用。
