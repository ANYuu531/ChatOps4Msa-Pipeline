[碩論] ① 這個驗證能主張什麼、不能主張什麼 4

先講最重要的：操作者是我

五次真跑的答案都是我填的，而且我看過資料集的期望邊。所以這些結果證明的是機制走得通：問題會被提出、答案會被套用、只有被答的邊出現、答錯了可以改、下次不再問。

它不證明「問人會得到正確答案」。那是上次「標準答案是我給的」同一類問題。要主張那一點，得找沒看過這個 repo 的人照同樣步驟答一次——這是下一步，不是這次做到的。

機制本身的界線

  • DeepWiki 每次用詞都不一樣（ZooKeeper ServerSets → ZooKeeper），新名字會零星一直冒出來；答案累積、問得越來越少，但不保證某次之後完全不問
  • 問的是「這個名字是哪個服務」，不問「這條邊存不存在」；邊的存在仍由來源決定
  • 答 new 時無法指定節點名（ZooKeeper 會變成 zoo-keeper），還沒修
  • Discord 一張表單最多五格；超過分輪

測試釘住的性質（26 個，離線）

  • 對不上的名字變問題而不是消失，圖上不多出節點或邊；函式庫名有邊才問、沒邊照舊靜默刪
  • 答案三種效力：對應既有節點（邊帶 doc 出處）／new 建節點／ignore；答一個圖上沒有的 id 不會造節點；答案也套用到既有節點
  • 只差前後綴的兩個服務名 → 問「是不是同一個」，兩個都留著直到回答
  • 看不懂的答案（9、空白、maybe）→ 不是合併；答題目自己的名字＝new
  • wiki 一欄多個名字拆開逐個對；repo 自己的名字不問；前端相對 URL 不算呼叫別的服務
  • 專案層級記憶：另一個使用者、檢查點過期後同一 repo 不再問；reset 可忘掉重問
  • 報告第 4／5 節由程式從圖產生；greenfield 寫「未量測」不寫 0％／No／HTTP

全套 280 個測試，唯一失敗的是要連 MCP server 的那個（跟之前一樣）。探針 GreenfieldProbeTest 吃 -Dprobe.aliases= 答案檔，是「Resolve names」的離線形式；對照用的答案檔與輸出在 docs/generalization/external/aliases/。

分級由低到高

定義小而有序的信心等級。建議三級，由低到高：

  • 只被提到（inferred）：只有設定值、文件敘述，或由名字推測。圖上畫點線。
  • 有使用證據（documented）：有真的會發出呼叫的程式碼、有持久化程式碼搭配連線設定。圖上畫虛線。
  • 量測到（observed）：執行期觀測直接記到這個關係發生過。圖上畫實線。

由低到高講，是因為每往上一級都多了一種來源的佐證：被提到 → 程式碼裡真的有呼叫 → 呼叫真的發生了。

「執行期觀測」是什麼（§1.1 新增；原本寫「遙測」）

「量測」指的是執行期觀測：系統跑起來之後，每個服務旁邊都有一個代理（Istio 的 sidecar），服務之間每一次呼叫都會經過它，它自動記下「誰呼叫了誰、幾次、成功與否」，寫進 Prometheus。我們查的就是這些計數，例如 istio_requests_total{source="web", destination="orders"} = 95。它不是讀程式碼推出來的，是呼叫真的發生時被記下來的，所以精確；但只有真的被呼叫過的關係才會出現，所以看不全。
用詞：這類資料英文叫 telemetry，國教院譯「遙測」——「遙」是量測在系統裡發生、讀數送到外面讀，不是機器遠近；文獻把這一側叫動態分析。本文一律用「執行期觀測」。

講稿　左邊：改名之前先查，發現 confidence 早就在，evidence 其實是出處清單，所以是三個概念分清楚。右邊是上次兩個提醒：分級改成由低到高講，理由是每往上一級多一種佐證；執行期觀測在第一次出現就白話定義——每個服務旁邊有個代理，每次呼叫經過它就記一筆，我們查的是這些計數。

Context

你在做一個會自動產出依賴視圖的工具，正在做第一件事：把系統元件之間的關係收集起來，畫成一張圖給人看。關係來自好幾個來源，而且你刻意要用多個來源，因為單一來源已經被證明不夠（§1.1）：執行期觀測告訴你這段期間真的發生過哪些呼叫；程式碼與設定檔告訴你哪些呼叫寫在那裡、不管有沒有跑到；部署描述告訴你誰被佈線到誰；專案文件（README、架構說明，可能經過 LLM 整理）告訴你前三者都看不到的東西，例如一條只在特殊流程才走的呼叫。

[碩論] pattern ① 草稿 · Problem 3/9
Problem
來源的可靠度差很多。全部畫成同一種線，讀者會以為每條都一樣真；只畫最可靠的（量測到的），又會丟掉那些量測不到、但確實存在的依賴。

兩個顯而易見的做法都不行。第一個是「全部畫上去」：把每個來源找到的關係聯集起來畫成一樣的線。這張圖最完整，但等級被抹平了——文件裡提過一句的關係和執行期觀測量到幾千次的關係長得一模一樣，讀者沒有辦法分辨哪一條可以據以決策、哪一條只是有人這樣寫過。更糟的是，這張圖會被下游當成事實：產部署順序的程式會把文件幻覺出來的邊當成硬依賴，LLM 寫報告時會把「只被提到」講成「確認存在」。

第二個是「只畫量測到的」：只信執行期觀測。這張圖每一條都是真的，但它是流量圖而不是依賴圖——沒走到的路徑、非 HTTP 的協定、這次沒部署的元件全都不在上面。它回答「這段期間誰呼叫了誰」，而讀者要的是「誰依賴誰」。工具開發早期我們正是交出這樣的圖，被看圖的人一句話點破：這比較像流量圖。

所以問題不是「選哪個來源」，而是：同一張圖上要同時容納可靠度不同的關係，又要讓讀者一眼分得出哪條是哪種，而且這個差別要能活過合併、摘要、報告、問答這些下游步驟。

重點

  • 第一句是兩難：全畫 → 分不出真假；只畫最可靠的 → 丟掉真的依賴。兩邊都不行，才叫 problem。
  • 後面兩段各走一個「顯而易見的做法」到底，說它為什麼不行。這是 9 月版沒有的；只有一句兩難，審稿人會問「那為什麼不乾脆…」。
  • 「只畫量測到的」那段的例子就是我們自己：7 月那張只有執行期觀測的圖被說「比較像流量圖」。
  • 最後一句把問題重述成 Solution 要回答的形狀：容納、分得出、活過下游。第三點是 ② 的伏筆。
想問：「被看圖的人一句話點破」——這是老師說的話，寫進論文時用「the first reader of the graph」這種第三人稱可以嗎？Known Uses 那邊也有同一件事。
講稿　Problem 第一句是兩難。後面兩段各走一個顯而易見的做法到底，這是九月版沒有的。第二段的例子就是我們自己七月那張流量圖。最後一句重述成 Solution 要回答的形狀，「活過下游」是第二個 pattern 的伏筆。想問的是論文裡怎麼稱呼說那句話的人。

[碩論] pattern ① 草稿 · Forces 4/9
Forces
  • 可靠度與完整度方向相反。執行期觀測 precision 高、recall 低；結構分析 recall 高、precision 中等；文字兩者都低。只取其中一個，一定犧牲另一個。
  • 讀者要一眼看懂。分級太多看不懂；只有兩級（真／假）又把「有程式碼證據但這次沒跑到」和「文件隨口提過」混為一談。
  • 同一條關係會被多個來源重複提到。不能畫成多條平行線，也不能讓後到的弱來源蓋掉先到的強來源。
  • 下游會偷偷升級。摘要、報告、問答都很容易把「只被提到」講成「確定存在」——尤其當下游是 LLM。
  • 視覺通道有限。線型、顏色、粗細、標籤要分給信心等級、關係類型（同步呼叫／資料庫／佇列／外部）、流量大小。研究指出同時編碼「主屬性」與「不確定性」的視覺變數會互相干擾（Guo et al., IEEE TVCG 2015），所以通道的分配是有代價的選擇，不是想加就加。
  • 誠實揭露不確定性可能反過來降低信任。主題地圖的研究顯示不確定性視覺化是雙面刃：可能因為誠實而提升可信度，也可能被讀成「這份東西不可靠」（CHI 2026）。所以分級要能被讀懂，而不只是把懷疑丟給讀者。

重點

  • 六條，每條都是兩個東西在拉：可靠 vs 完整、看懂 vs 分細、合併 vs 覆蓋、誠實 vs 信任。沒有張力的條目（例如「三級要離散」）移到實作要點。
  • 每條都寫「不這樣做會怎樣」：犧牲另一個、混為一談、蓋掉、偷偷升級、互相干擾、被讀成不可靠。
  • 兩條有文獻：視覺通道（TVCG 2015 的受控實驗）、誠實的代價（CHI 2026）。後者對我們不利，刻意放進來。
  • 「下游會偷偷升級」這條是 Solution 第 5 步「只能照抄或降級」的來源。
想問：第一條用 precision／recall 講，是不是太像評估術語？可以換成「看得準 vs 看得全」。
講稿　六條 forces，每條都是兩個東西在拉，每條都寫不這樣做會怎樣。沒有張力的條目移到實作要點。兩條有文獻，其中誠實的代價那篇對我們不利，刻意放。想問的是第一條用 precision／recall 會不會太像評估術語。

[碩論] pattern ① 草稿 · Solution、實作要點 5/9
Solution

因此：

  1. 定義小而有序的信心等級。建議三級，由低到高：只被提到（inferred；點線）、有使用證據（documented；虛線）、量測到（observed；實線）。由低到高講，是因為每往上一級都多了一種來源的佐證。
  2. 等級（有多可信）與來源（誰說的）分開存。一條關係可以有多個來源，但只有一個等級。
  3. 以（來源元件, 目標元件）為鍵合併：等級取最高，來源與佐證取聯集。
  4. 視覺上把最醒目的通道給信心等級：實線／虛線／點線。關係類型用顏色或短標籤，流量大小降級成線寬或不畫。
  5. 所有下游讀取等級時，只能照抄或降級，不能升級。
實作要點
  • 三級是離散的而不是 0–1 的連續信心值。離散的好處是沒有自由參數要校準、可以直接對應三種線型、「取最高」不需要加權公式。代價是無法表達「兩個弱來源互相佐證」——這一點要寫進 Consequences。
  • 「什麼算使用證據」是領域知識：每種語言與框架各要一份判準（例如資料庫要同時看到連線設定與持久化標記）。這份判準會成為工具最需要維護的部分。

重點

  • 五步，可以照著做：定等級 → 分開存 → 合併規則 → 通道分配 → 下游規則。
  • 第 1 步照上次說的由低到高，而且每級附圖上的線型，讀者看圖時順序一樣。
  • 第 2 步是整個 pattern 的核心：等級與來源是兩個欄位。這也是 evidence 改 confidence 的根據——等級講多可信，來源講誰說的。
  • 第 3 步「取最高、取聯集」簡單到沒有參數，這是刻意的；代價寫在實作要點與 Consequences。
  • 實作要點放的是沒有張力的工程細節：離散 vs 連續、判準是領域知識。

講稿　五步可以照著做。第一步由低到高，每級附線型。第二步是核心：等級與來源是兩個欄位，這也是改名的根據。第三步取最高取聯集沒有參數，代價寫在後面。想問的是英文名要不要改成 mentioned／used／observed，跟中文對齊。

Consequences

[碩論] pattern ② 草稿（精簡） 1/4

② 單一標準模型、多個視圖（One Model, Many Views）

別名

Single Canonical Model, Many Views（目錄 P6）；分析快照（Analysis Snapshot）；祈使句版：先建模型，再產視圖。

一句話

每次分析先建一個可序列化的標準模型，圖、指標、報告裡的事實段落、問答、匯出全都是這個模型的純函式；衍生計算只實作一次。

Problem
每個產物各自從原始證據推導時，推導邏輯會分岔；讀者會看到「報告說 A、圖畫 B」，而且無從判斷誰對。
Solution
  1. 每次執行先建一個標準模型，再產所有視圖；模型只建一次。
  2. 每個視圖都是模型的純函式：繪圖、指標、事實段落（→ ③）、查詢、匯出。
  3. 衍生計算只實作一次（分數、分層、拓樸排序），所有視圖呼叫同一個實作。
  4. 模型可以序列化與還原。晚發生的視圖（幾天後的追問）讀回同一份模型。
  5. 需要給 LLM 的事實，也由模型產生文字給它，不讓它讀原始證據自己推。

重點

  • Problem 的兩難：各自推導 → 分岔；事後對齊 → 永遠修不完；只交一個產物 → 讀者需要三種。
  • Known Uses：Pandoc 的 AST、MVC（Reenskaug 1978）、Backstage catalog。和 MVC 的差別要講清楚：這裡的 model 是一次執行的快照，不是長駐狀態，而且要能序列化給晚到的視圖。
  • 沒解掉的事：schema 是共同介面、模型沒收的資訊所有視圖都拿不到、模型失敗全部失敗（→ ⑤）。
  • 這次真跑的佐證：報告第 4、5 節改由程式從圖產生之後，報告和圖不可能再對不起來。
想問：§6.2 說 ② 最接近既有知識（MVC 的變體）。新的部分寫成「一次性分析產物的快照模型 ＋ 晚到的視圖讀回同一份」夠不夠？
講稿　②只放名稱、一句話、Problem、Solution。重點是和 MVC 的差別：這裡的 model 是一次執行的快照，要能序列化給晚到的視圖。這次真跑第四第五節改由程式產生就是它的佐證。

③ 事實由程式寫（Code-Authored Facts）

別名

權威段落由程式碼產生（目錄 P7）；先算後寫（Compute, Then Narrate）；事實段落不給 LLM；祈使句版：讓程式寫事實，讓模型寫詮釋。

一句話

把報告分成事實段落與詮釋段落；事實段落由程式從模型產生、措辭固定，再以結構錨點拼進 LLM 寫的報告；LLM 拿到同一份事實清單只負責詮釋，它若自己也寫了事實段落，丟掉它的版本。

Problem
LLM 重述事實時會漂移，而且收緊 prompt 通常只是把錯誤換個樣子。怎麼保有 LLM 報告的可讀性，又讓事實不出錯？
Solution
  1. 把報告段落分成事實型（有正確答案、模型裡都有）與詮釋型。
  2. 事實型段落由程式從模型產生，措辭固定且精確（寫「連線數」不寫「請求數」）。
  3. 告訴 LLM 跳過事實段落；同時把同樣的事實以「已確認清單」給它，讓詮釋不會和事實矛盾。
  4. 用結構錨點把程式段落拼進報告；LLM 若自己也寫了，丟掉它的版本；找不到錨點就附在最後。
  5. 段落末尾註明「本段由程式從模型產生」。

重點

  • 漂移三種形態都真的發生過：漏（五條寫四條）、加（把函式庫列成依賴）、改措辭（連線數寫成請求數）。
  • 這次真跑的第二個事件：報告第 4 節 prompt 明說「不要列 ignore 的名字」，LLM 還是列了 MyAppThriftClient → FooService。改 prompt 沒用，改成程式產生才有用——pattern 的 Known Uses 多了一條。
  • 代價也真的付了：程式產生的第 4 節沒有 LLM 原本會寫的 Method／Endpoint，因為圖沒記這些。
  • 外部實例：Satyrn（先算後寫，正確主張 86% vs 57%）、SymGen、knitr、OpenAPI 文件。

講稿　③最有這次真跑的佐證：第四節 prompt 明說不要列 ignore 的名字，LLM 還是列，改成程式產生才有用。代價也付了：程式產生的段落沒有 Method、Endpoint。想問的是程式段落把沒量的寫成確定值這件事該歸三還是五。

[碩論] pattern ④ 草稿（精簡） 3/4

④ 誠實分母（Honest Denominator）

別名

排除但揭露（Exclude but Disclose）；分母只算量得到的；祈使句版：說清楚你沒算進去的（Say What You Left Out）。

一句話

比率的分母只算「量測機制做得到、而且信心高於只被提到」的項目；性質不同的項目分開算；被排除的數量與理由一定寫在分數旁邊，排除的比計分的多時加警告。

Problem
把量不到的項目算進分母，分數會被永久壓低，讀者被推去修一個修不好的缺口；把弱證據的項目算進去，文件多說幾句就會稀釋分數；排除太多又會虛高。而讀者只看到一個百分比，分不出是哪一種。
Solution
  1. 分母只算同時滿足兩個條件的項目：量測機制做得到，且信心高於「只被提到」（①）。已經量測到的一律算。
  2. 性質不同的項目用獨立的比率（業務呼叫、資料層分開報）。
  3. 分數旁邊一定揭露「未計分：N 項，理由」。
  4. 被排除的比計分的多時，加「此分數建立在很小的基礎上」的警告。
  5. 同時列出未覆蓋清單，讓分數可以直接變成下一步行動。
  6. 排除規則寫在一處，所有產生這個數字的視圖共用（②）。

重點

  • 三次分母事故對應三種錯：45% 假分數（控制面混進來）、7/7 → 7/10（文件多講三條）、5/6 卡住（程序內快取）。每次都是分母錯，不是量測錯。
  • 紅線用兩個反例劃：JaCoCo（排除就消失）、Istanbul（排除灌進分子）。正例：CONSORT 逐階段寫排除人數與理由、coverage.py 的 excluded_lines。
  • 沒解掉的事：排除規則是會長大的清單；分母定義改了歷史數字不可比；讀者可能只看百分比。
  • 和 ① 的關係：「信心高於只被提到」是分母的過濾條件之一。
想問：警告的門檻「未計分的比計分的多」刻意不用百分比（沒有自由參數）。這個理由寫在實作要點夠嗎，還是該升到 Solution？
講稿　④的三次事故每次都是分母錯不是量測錯。紅線用兩個反例劃。想問的是警告門檻不用百分比的理由放實作要點夠不夠。

[碩論] pattern ⑤ 草稿（精簡） 4/4

⑤ 未量測不是零（Unmeasured Is Not Zero）

別名

未知是一個值（Unknown Is a Value）；三值狀態；沒查過不是沒有；祈使句版：預設為未知（Default to Unknown）。

一句話

狀態欄位預設是「未知」而不是 false 或 0，只在證據明確時才設為否定；這次沒收集哪些證據當成執行模式隨模型傳到每個視圖；視圖遇到未知寫一句話說明為什麼未知、補什麼才會知道，而且絕不把數值佔位交給 LLM。

Problem
沒收集的資料在程式裡變成 0 或 false，在 LLM 手上變成猜測；失敗的步驟看起來和「什麼都沒找到」一模一樣。讀者把一個從未發生的量測當成結果。
Solution
  1. 狀態欄位用三值，預設是「未知」而不是 false。
  2. 執行模式（這次沒收集哪些證據）當成中繼資料，隨模型傳到每一個視圖。
  3. 視圖遇到未知時寫一句話：為什麼未知，以及補什麼證據才會知道。
  4. 絕不用 0、0/N、0% 這種數值佔位代表未量測，尤其不要交給 LLM。
  5. 步驟失敗時記錄失敗狀態與原因，不要回傳空結果。
  6. 空段落寫成「無，原因是……」，不留白。

重點

  • 這次真跑的第一個事件就是它：greenfield 什麼都沒量，覆蓋率訊息寫「Istio observed 0 / 23 — 0% runtime coverage」「the datastore is deployed」。修成「Not measured… unknown, not 0%」。
  • 而且不只 LLM 會犯：程式產生的段落也把沒量的寫成 Protocol: HTTP、Runtime observed: No——標著 deterministic 反而更像真的。這條要加進 Known Uses 的事件。
  • 外部實例三個領域各自得到同一結論：SQL 的 NULL、Kubernetes 的 Unknown、Grafana 的 No Data。
